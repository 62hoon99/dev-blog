# DI와 테스트 어노테이션 활용
### 컨테이너 인프라스트럭처 빈

- 컨테이너가 직접 등록하는 빈

### 애플리케이션 빈
- 개발자가 구성 정보를 제공해야 하는 빈
- 애플리케이션 로직 빈, 애플리케이션 인프라스트럭처 빈 으로 나뉜다.
    - 애플리케이션 로직 빈은 우리가 개발할 때 만드는 빈
    - 애플리케이션 인프라스트럭처 빈은 보통 만들어져 있는 빈을 사용
- 사용자 구성정보 (ComponentScan)
    - controller, decorator, service .. bean
- 자동 구성정보 (AutoConfiguration)
    - TomcatServletWebServerFactory, DispatcherServlet

# 자동 구성 기반 애플리케이션
## 메타 에너테이션
에너테이션에 적용한 에너테이션을 메타 에너테이션이라고 부른다. 스프링은 메타 에너테이션의 효력을 적용해준다. @Service 어노테이션을 보면 @Component가 붙어 있는 걸 볼 수 있다. 그래서 @Service 어노테이션을 붙이면 컴포넌트 스캔 대상에 포함되어 컴포넌트로 등록 되었던 것이다.

## 합성 에너테이션
하나 이상의 메타 애노테이션이 적용된 애노테이션을 합성 에너테이션이라고 부른다. 합성 애노테이션을 사용하면 모든 메타 애노테이션이 적용된 것과 동일한 효과를 갖는다.

## 인프라 빈 구성 정보의 분리
@Import를 사용하면 컴포넌트 스캔 대상이 아닌 클래스도 빈으로 등록할 수 있다.
예를 들어 비동기 프로그래밍을 위해 @Async를 사용하려면 @EnableAsync를 @Configuration 클래스에 추가해야 한다. @EnableAsync를 확인해보면 내부에서 @Import를 사용하고 있는데, 이는 스프링이 기본적으로 비동기 기능을 제공하더라도 **비동기 기능을 실제로 사용할 때만 관련 빈을 등록**하도록 의도한 설계임을 보여준다.

``` java
@Target(ElementType.TYPE)  
@Retention(RetentionPolicy.RUNTIME)  
@Documented  
@Import(AsyncConfigurationSelector.class)  
public @interface EnableAsync { ... }
```

# @Configuration 클래스의 동작 방식
## **proxyBeanMethods**
@Configuration 클래스의 proxyBeanMethods 기본값은 true이다. 이 경우 스프링은 CGLIB 프록시를 생성해 @Bean 메서드 호출을 가로채고, 같은 빈을 여러 번 요청해도 항상 동일한 객체를 반환하도록 하여 싱글톤을 보장한다. 즉, @Bean 메서드를 직접 호출해 의존 관계를 구성하더라도 매번 동일한 빈을 참조할 수 있다.

``` java
@Configuration
public class AppConfig {

    @Bean
    public ServiceA serviceA() {
        return new ServiceA();
    }

    // Bean 생성 시 serviceA()를 직접 호출해서 의존성 주입
    @Bean
    public ServiceB serviceB() {
        return new ServiceB(serviceA());
    }
}
```


만약 @Bean 메서드를 직접 호출해 빈 의존 관계를 만들 필요가 없다면 굳이 프록시를 생성할 필요가 없다. 이때는 proxyBeanMethods = false로 지정하면 된다. 이 경우 @Bean 메서드는 단순한 팩토리 메서드처럼 동작한다.

proxyBeanMethods는 스프링 5.2부터 도입되었으며 현재 많은 설정 클래스에 적용되고 있다. 

@Bean(proxyBeanMethods = false) 일 때 올바른 


또한 @Bean은 반드시 @Configuration 클래스 내부에서만 사용할 필요는 없다. 일반 빈 클래스에서도 사용할 수 있으며, 이를 @Bean 라이트 모드라 한다. 이 경우 단순한 빈 생성용 팩토리 메서드로 동작한다.
