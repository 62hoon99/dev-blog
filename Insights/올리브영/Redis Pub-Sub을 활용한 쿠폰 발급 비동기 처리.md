# 문제
대량의 트래픽이 몰리는 경우 선착순 쿠폰 발급 기능에 지연이 발생한다.

# 원인
쿠폰 발급을 위한 일련의 과정이 모두 동기(Sync)로 진행된다.

# 해결
쿠폰 발급을 비동기(Async)로 진행하여 사용자 경험을 개선한다.

# **Redis Pub-Sub 방식 설계의 문제점과 내가 생각해본 설계**

## **Redis Pub-Sub을 활용한 설계가 잘못된 이유**
### **1. Redis Pub-Sub 사용**
글에서도 언급되어 있지만, Redis Pub-Sub은 발행자가 메시지를 한 번 발행하면 구독자가 그걸 한 번 받고 끝나는 구조다. 구독자가 메시지를 받지 못하든, 중간에 유실되든, 그건 시스템이 감수해야 하는 전제다. 그래서 원래는 **유실되어도 크게 문제 없는 이벤트**에서만 사용하는 게 맞다. 예를 들어 알림, 로그성 이벤트 같은 것들.

그런데 이걸 **선착순 쿠폰 발급** 같은, 메시지 유실이 절대 허용되면 안 되는 핵심 로직에 적용한 시점에서 이미 설계가 잘못되었다고 생각한다. 그리고 이 문제를 보완하기 위해 추가 로직을 덕지덕지 붙이면서, 시스템 복잡도만 괜히 올라간 구조가 되었다.

### **2. 2배로 늘어난 네트워크 구간**
기존 구조는 단순했다. 
- **클라이언트 → 백엔드 서버 → DB**

하지만 개선안에서는 이렇게 바뀌었다.
- **클라이언트 → 백엔드 서버 → Redis → 쿠폰 발급 Worker → DB**

네트워크 홉이 2개에서 4개로 늘어났고, 그만큼 지연 가능성도 커졌다.

또 네트워크 구간이 늘어났다는 건 곧 **실패 가능성이 늘어났다는 의미**이기 때문에, 그에 대한 예외 처리와 복구 로직까지 추가로 신경 써야 한다. 결국 성능 개선을 한다며 도입한 구조가, 오히려 지연과 복잡도를 키운 셈이다.

### **3. 실패에 대한 처리 미흡**
글 본문에는 쿠폰 발급 Worker 실패 시 대응에 대한 내용이 없다. 댓글을 보면 Datadog에서 로그를 확인해서, 쿠폰 요청이 정상적으로 들어왔는데도 발급되지 않은 사용자를 찾아 **수작업으로 보정**한다고 한다. 최소한 주기적으로 데이터를 보정하는 자동화 후처리라도 있을 줄 알았는데, 이 부분이 수작업이라는 점은 꽤 놀라웠다.

## **내가 생각해본 설계**

### **1. 백엔드 서버에서 비동기 처리**
사용자 경험을 개선하고 응답 속도를 빠르게 하기 위해 비동기를 쓰는 건 충분히 이해된다. 그런데 굳이 Redis Pub-Sub과 별도 Worker까지 두면서 구조를 복잡하게 만들 필요가 있었을까? 정말 Worker를 써야만 하는 이유가 없었다면, **백엔드 서버 내부에서 비동기 처리만으로도 충분히 해결 가능**했을 것 같다.

쿠폰 발급이 필요한 경우:
- 먼저 유효성 검사를 수행하고
- 발급 대상이라면 요청 정보를 DB에 기록한 뒤
- 사용자에게 빠르게 응답을 반환한다.

그 후 별도의 비동기 로직에서 새로운 트랜잭션으로 실제 쿠폰 발급을 처리하고, 정상 처리되면 요청 정보를 삭제한다. 만약 중간에 장애가 발생하면 DB에 남아 있는 요청 정보를 기반으로 재처리하거나 보정 작업을 수행할 수 있다. 이렇게 하면 사용자 경험을 해치지 않으면서도 안정적인 발급 보장이 가능하다.

### **2. Redis Pub-Sub → Kafka**
메시지 브로커를 쓴다면 Redis Pub-Sub이 아니라 **Kafka 같은 진짜 브로커를 쓰는 게 맞다**고 본다. Kafka를 사용하는 구조는 쿠폰 발급 요청을 메시지 큐에 적재하고, 별도의 Consumer(Worker)가 비동기로 발급을 처리하는 방식이다. API 서버는 빠르게 응답을 반환하고, 발급 로직은 백그라운드에서 안정적으로 처리된다.

**왜 Kafka여야 하는가**
- 메시지 유실을 기본 가정으로 하는 Redis Pub-Sub과 달리, Kafka는 **메시지 영속성**을 보장한다.
- Consumer 장애가 발생해도 메시지가 사라지지 않기 때문에, 재처리가 가능하다.
- 대량 트래픽에서도 안정적으로 처리할 수 있고, 확장성이 뛰어나다.
- 파티셔닝을 통해 순서 보장, 처리량 증가, 스케일 아웃 모두 가능하다.

물론 단점도 있다.

Kafka를 운영해야 하니 인프라 비용과 운영 부담이 커지고, 시스템 구조가 복잡해진다. 모니터링, 파이프라인 관리, 장애 대응 설계까지 신경 써야 한다.

그럼에도 불구하고 메시지 큐를 쓰면, 일시적인 트래픽 폭증이나 지연 상황에서도 요청이 유실되지 않고 안전하게 처리되며, 쿠폰 발급 지연 문제를 훨씬 안정적으로 완화할 수 있다.

그리고 여기서 한 가지 더 중요한 점이 있다.

Kafka로 바꿨다고 끝이 아니다. **쿠폰 발급 Worker가 실패했을 때를 확실히 처리할 수 있는 후처리 모듈**이 반드시 필요하다. Worker가 장애로 죽었는지, 특정 메시지를 계속 실패하는지, 재시도를 몇 번 해야 하는지 등:
- 재시도 메커니즘
- 실패 메시지 보관
- 자동 보정 또는 관리자 개입 프로세스

이런 후처리 체계까지 함께 설계되어야 진짜 안정적인 구조라고 할 수 있을 것 같다.
