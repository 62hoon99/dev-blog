# 문제
대량의 트래픽이 몰리는 경우 선착순 쿠폰 발급 기능에 지연이 발생한다.

![[Pasted image 20251214131801.png]]
# 원인
대량의 트래픽이 몰리는 경우 쿠폰 발급 처리를 위한 조건 체크 중 **발급 수량 부분**에서 DB와 경합이 발생한다.
- 글에는 나와있지 않으나, 선착순 쿠폰 발급 시 발급된 쿠폰 개수를 확인해야 하고, 한 사용자가 중복 발급하지 않도록 해야 하는데 이 과정은 원자적으로 이루어져야 하다보니 지연이 발생한다는 것으로 이해된다.

# 해결
![[Pasted image 20251214132920.png]]
DB에서 쿠폰 발급 수량을 확인하지 않고, 쿠폰 발급 수량을  캐싱하여(Redis 이용) 지연 현상을 완화했다.
- **선착순 쿠폰 발급 자체는 여전히 경합 구간이 존재하지만, Redis를 통해 발급 불가능한 요청을 초기에 차단함으로써 대부분의 요청이 DB에 도달하지 않도록 개선**되었다.
- 그리고 캐시를 추가했더라면 아래와 같은 이슈에 대해서는 어떻게 해결했는지에 대해서는 언급되지 않는다.
	- DB와 Redis 간의 일관성(트랜잭션 경계)
	- 동시성 제어 및 경쟁 조건 처리 전략
- 그래서 이러한 문제들을 직접 확인하고 테스트 해보고자 한다.

# 쿠폰 발급 시스템 직접 만들어보기
## 목적
선착순 쿠폰 발급 시스템에서 DB 경합을 줄이기 위해 메모리 기반 저장소를 도입한다고 가정하고, 동시성 및 트랜잭션 이슈를 고려한 발급 로직을 설계·구현·검증한다.

## 요구사항 및 제약사항
### 요구사항
- 이벤트 시작 시점(2025-12-16 00:00:00)부터 **조건을 만족한 사용자에 한해 선착순으로 정확히 100개의 쿠폰을 발급**한다.
###  조건
- 쿠폰 발급 대상은 **SNS/이벤트 알림 수신에 동의했으며 회원가입 30일 이내인 신규 회원**으로 제한하고, 동일 회원에게는 중복 발급하지 않는다.
### 제약 사항
- 본 프로젝트는 학습 목적의 구현으로, **실제 분산 인프라를 구축하지는 않지만 API 서버가 분산되어 있다고 가정하고 설계 및 개발을 진행**하며, 테스트는 **Tomcat 기반 Spring Boot 단일 인스턴스 환경**에서 수행한다.
- 단일 인스턴스 테스트 시에는 **동시성 경합을 충분히 유발하기 위해 1,000개의 동시 요청을 생성**하고, 이는 Tomcat 스레드 풀 최대 크기(200) 대비 **요청 수가 스레드 수를 초과하는 상황을 인위적으로 만들어 대기·경합·락 충돌 상황을 재현하기 위함**이다. 이를 통해 실제 대규모 트래픽 환경에서 발생할 수 있는 선착순 보장, 정합성, 중복 발급 방지 로직을 검증한다.

## 설계
### 쿠폰 발급 로직
1. client 요청
2. 쿠폰 정보 조회 (캐싱)
3. 쿠폰 발급 개수 확인 from Redis
4. 쿠폰 발급 가능 기간 확인 / 회원 SNS 수신 여부 / 가입일 DB 확인
5. 쿠폰 발급 from Redis
	- 요청한 회원의 중복 발급 여부
	- 수량 남아 있는지 확인
	- 쿠폰 발급 기록
	- Redis Lua Script 로실행 (원자적으로 발급)
6. 결과 반환
7. 쿠폰 발급 결과 주기적으로 DB에 insert

### 요구사항 부합 검증
- 요구사항: 선착순으로 정확히 100개의 쿠폰을 발급한다.
	- Redis 를 사용해 원자적으로 발급하기 때문에 가능하다.
- 요구사항: 쿠폰 발급 조건 검증
	- 가능하다.
	- 더불어, 올리브영에서 발생했던 DB 경합 문제를 올리브영의 해결방법과 동일하게 Redis를 사용하여 쿠폰 발급 개수를 미리 확인하여 발생하지 않도록 했다.
	- 레디스에 쿠폰 발급 결과를 저장하기 때문에 동시성 문제도 발생하지 않는다. (Redis는 싱글 스레드 이며, 원자적 계산을 위해 Lua Script를 사용하기 때문)
