# 올리브영 결제 이야기 Part - 1
링크: https://oliveyoung.tech/2022-04-20/Oliveyoung-Order-Payment-Process/

## 문제
- 결제 미매칭 현상 빈도 증가
- 고객들의 불편 증가
	- PG사 결제 완료 후 올리브영 결제 완료까지 대기 시간이 증가
	- PG사에서는 결제 완료했는데 올리브영에서는 최종적으로 결제 실패하는 현상 증가

## 원인
- 올리브영은 기존에 결제 로직이 Async 방식이었다.
	- Async 방식의 결제 로직:
		1. 클라이언트가 PG사와 직접 통신하여 결제
		2. 결제완료되면 클라이언트는 올리브영에서 등록된 결제 완료 화면으로 redirect
		3. PG사는 올리브영 백엔드 서버로 결제 내역 전달 (웹 훅 방식)
		4. 클라이언트는 백엔드 서버에 폴링 방식으로 결제 완료 여부 확인
		5. 백엔드 서버는 결제 내역 저장
		6. 클라이언트에서는 백엔드 서버에서 결제 완료 여부 확인 후 결제 내역 화면 출력
- Async 방식의 문제
	- 트래픽이 몰리는 경우 PG사와 올리브영 백엔드 서버간의 통신 실패

## 해결
- Sync 방식으로 전환
	1. 클라이언트가 PG사와 직접 통신하여 결제
	2. 결제완료되면 클라이언트는 올리브영에서 등록된 결제 완료 화면으로 redirect (redirect url에 결제 승인을 위한 쿼리 파라미터 존재)
	3. 클라이언트가 올리브영 백엔드 서버 API 호출
	4. 올리브영 백엔드 서버가 PG사의 결제 승인 API 호출
	5. 올리브영 백엔드 서버가 클라이언트에게 결제 결과 응답
- Sync 방식으로 전환하니까 해결되는 이유
	- 제어권이 올리브영으로 넘어감
		- 클라이언트 <-> 서버 <-> PG사간의 통신이 안되면 올리브영 서버에서 retry를 하거나 성능 최적화를 통해 개선할 수 있음. (Async 방식에서는 PG사로부터 웹훅이 올 때 까지 대기할 수 밖에 없음)
	- 불필요한 통신이 줄어듦
		- Async방식에서는 클라이언트에서 폴링 방식으로 결제 완료 여부를 확인해야 됐으나 Sync 방식에서는 클라이언트가 백엔드 서버한테 결제 승인 요청 한 번만 보내면 됨

### 웹훅 방식을 꼭 사용해야 하는 결제방식

가상계좌 결제는 **즉시 결제가 확정되지 않기 때문에 웹훅 방식이 필수적**이다. 올리브영 기술 블로그에서도 언급되었듯, **PG사와 서버 간 통신은 언제든 실패할 수 있어** 결제 결과를 서버가 직접 보장할 수 없다. 이를 보완하기 위해 토스는 **웹훅 재전송 정책**을 제공한다.

- 가상계좌 연동 설명: https://docs.tosspayments.com/blog/virtual-account-webhook
- 웹훅 연동 설명: https://docs.tosspayments.com/guides/webhook

추가적으로 PG사에 등록할 웹훅 API는 반드시 멱등성을 고려해야 한다고 생각한다. 결제 완료 웹훅이 여러 번 호출되더라도 추가 결제가 발생하지는 않지만, 멱등하게 처리하지 않으면 **데이터 정합성 문제**, **중복 로그**, **불필요한 레코드 생성**이 발생할 수 있다.

또한 PUB/SUB 메시지 큐 환경에서도 발행자가 동일 메시지를 여러 번 보낼 수 있으므로 **수신자는 항상 멱등성을 보장하도록** 설계해야 한다.

즉, 사용자 요청이 아닌 시스템 간 연동에서는 멱등성이 필수적인 고려 요소가 아닐까 싶다.

# 올리브영 결제 이야기 Part - 3
링크: https://oliveyoung.tech/2022-12-13/oliveyoung-transaction-orderstock/

## 문제
주문 요청부터 완료까지 걸리는 시간이 지연되는 일이 잦아짐.

## 원인
- 주문을 순차적으로 처리하기 때문
	- A, B, C 주문 요청이 오면 A에 대한 처리가 모두 완료된 후에 B를 처리한다.
- 순차적으로 처리하는 이유는 재고 관리, 이벤트 등 복잡한 비즈니스 로직 때문이다.

## 해결
- 병렬 방식으로 처리

### 병렬 방식의 문제점
#### Dead lock
Dead lock 발생 케이스
- 올리브영에서는 DB 에 비관적 락을 건다.
- 아래와 같은 케이스에서 Dead lock이 걸린다.
	- 요청자A, 요청자B가 아이템1, 아이템2를 구매한다고 하자.
	- 요청자A 주문 트랜잭션이 시작되고 아이템1에 exclusive lock 을 건다.
	- 요청자B 주문 트랜잭션이 시작되고 아이템2에 exclusive lock을 건다.
	- 요청자A 트랜잭션에서 아이템1에 대해 처리 완료하고 아이템2를 처리하려는데 exclusive lock이 걸려있어서 lock을 기다린다.
	- 요청자B 트랜잭션에서 아이템2에 대해 처리 완료하고 아이템1을 처리하려는데 exclusive lock이 걸려 있어서 lock을 기다린다.
		- exclusive lock 은 커밋 또는 롤백되기 전까지 유지된다.
	- Dead lock에 빠진다.

Dead lock 해결 방법
- Item 별로 별도의 트랜잭션을 부여한다.
	- 5개 주문했는데 3개만 주문 정상 처리되고, 2개는 안되는 상황과 같은 복잡한 상황이 발생할 수 있지만 Dead lock 보다는 나을 것이다.

## 나의 생각
1. 글에서 테스트 중에 Dead lock에 빠져 DBA분께 SOS 요청해서 Dead Lock을 kill 하기까지 했다고 한다. 이 문제는 트랜잭션 타임아웃 또는 DB에 락 타임아웃 설정이 되어 있었다면 DB에 Dead lock이 남아서 추가적인 문제가 발생되지 않았을 것 같다.
2. 왜 비관적 락(exclusive lock)을 썼는지 궁금하다. 글에서 언급한 것 처럼 비관적 락을 사용하게 되면 Dead lock에 빠질 수도 있고, 주문이라는 정말 중요한 DB에 직접적인 영향을 주는 거라서 부정적으로 생각한다. 근데 아마 주문 DB에 직접 접근해서 작업을 하는 다른 모듈이 있기 때문에 다른 모듈
	1. DB lock을 대신해서 redis를 활용해서 lock 관리하는 방법도 있다.
