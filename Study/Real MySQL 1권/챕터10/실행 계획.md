# MySQL 실행 계획 (Execution Plan)

> 실무에서 **언제**, **왜**, **어떻게** 사용하는가에 초점을 맞춘 학습 정리

---

## 1. 실행 계획이란? 왜 봐야 하는가?

MySQL은 쿼리를 실행하기 전에 **옵티마이저(Optimizer)** 가 가장 효율적인 실행 방법을 결정한다. 이 결정 결과를 **실행 계획(Execution Plan)** 이라고 한다.

### 실행 계획을 보는 이유

- 인덱스가 제대로 타고 있는지 확인
- 풀 테이블 스캔(Full Table Scan)이 발생하는지 감지
- 조인 순서나 방식이 의도대로인지 검증
- 쿼리 튜닝 전후 성능 비교

### 언제 봐야 하나?

|상황|설명|
|---|---|
|슬로우 쿼리 발생 시|slow query log에 잡힌 쿼리 분석|
|대용량 테이블 조회|수십만 건 이상 테이블의 조인/집계 쿼리|
|배포 전 성능 검토|새 기능의 쿼리가 인덱스를 제대로 쓰는지|
|인덱스 설계 검토|인덱스 추가/변경 효과 사전 검증|

---

## 2. 실행 계획 확인 방법

### 기본 사용법

```sql
-- 기본 실행 계획 (테이블 형식)
EXPLAIN SELECT * FROM orders WHERE user_id = 1;

-- 더 자세한 정보 포함 (MySQL 8.0+)
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 1;

-- JSON 형식 (중첩 구조로 더 상세)
EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE user_id = 1;

-- 트리 형식 (MySQL 8.0.16+, 가장 읽기 쉬움)
EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE user_id = 1;
```

### EXPLAIN vs EXPLAIN ANALYZE

|구분|EXPLAIN|EXPLAIN ANALYZE|
|---|---|---|
|실제 실행 여부|❌ 실행 안 함|✅ 실제 실행함|
|실행 시간|없음|실제 소요 시간 표시|
|주의사항|없음|INSERT/UPDATE/DELETE는 실제 반영됨|
|활용|빠른 계획 확인|추정치 vs 실제치 비교|

> **실무 팁**: `EXPLAIN ANALYZE`는 실제 쿼리가 실행되므로 DML 쿼리에는 트랜잭션 안에서 사용 후 롤백하거나, SELECT로 변환 후 확인할 것

## 3. 실행 계획 핵심 컬럼 분석

### 3.1 `type` 컬럼 — 가장 중요한 지표

접근 방식을 나타내며, **성능을 가장 직관적으로 판단**할 수 있는 컬럼이다.

#### 성능 순서 (좋음 → 나쁨)

```
system > const > eq_ref > ref > range > index > ALL
```

|type|설명|예시 상황|
|---|---|---|
|`system`|테이블에 행이 1개|거의 볼 일 없음|
|`const`|PK나 Unique 인덱스로 1건 조회|`WHERE id = 1`|
|`eq_ref`|조인에서 Unique 인덱스로 1건씩 매칭|PK 기반 JOIN|
|`ref`|일반 인덱스로 조회 (여러 건 가능)|`WHERE user_id = ?`|
|`range`|인덱스 범위 스캔|`WHERE created_at BETWEEN ...`|
|`index`|인덱스 풀 스캔 ⚠️|인덱스는 타지만 전체 스캔|
|`ALL`|테이블 풀 스캔 🚨|인덱스를 전혀 못 씀|

#### 실무 판단 기준

- `const`, `eq_ref`, `ref` → ✅ 정상
- `range` → ✅ 일반적으로 허용 (범위가 크면 주의)
- `index` → ⚠️ 커버링 인덱스인지 확인 필요
- `ALL` → 🚨 튜닝 필요. 수천 건 이상 테이블이면 반드시 개선

---

### 3.2 `key` / `possible_keys` 컬럼

```
possible_keys: user_idx, created_at_idx
key: user_idx
```

- `possible_keys`: 옵티마이저가 고려한 인덱스 후보
- `key`: 실제 선택된 인덱스
- `key`가 `NULL`이면 인덱스를 아예 안 씀 → `type`이 `ALL`인 경우

> **실무 팁**: `possible_keys`에 있어도 `key`가 다른 인덱스면 옵티마이저가 판단했다는 것. 힌트(`USE INDEX`, `FORCE INDEX`)로 강제할 수도 있지만, 먼저 왜 선택 안 했는지 파악할 것.

---

### 3.3 `rows` 컬럼

옵티마이저가 **예측하는 스캔 행 수**. 실제 값이 아닌 통계 기반 추정치다.

```sql
-- rows가 100만이면 100만 건을 읽어서 필터링한다는 의미
-- filtered가 10%면 실제 결과는 10만 건
```

- `rows * (filtered / 100)` = 다음 단계로 넘기는 예상 행 수
- `rows`가 크고 `filtered`가 낮으면 → 인덱스 설계 재검토 필요

---

### 3.4 `filtered` 컬럼

인덱스로 읽은 행 중 **WHERE 조건에 의해 필터링 후 남는 비율(%)**.

|filtered|의미|
|---|---|
|100%|WHERE 조건이 인덱스에서 완전히 처리됨|
|10%|읽은 행의 10%만 실제 결과에 포함 → 90%는 낭비|

> **실무 팁**: `filtered`가 낮으면 복합 인덱스 추가를 검토. 예: `(user_id)` 인덱스만 있고 `status='ACTIVE'` 조건이 있다면, `(user_id, status)` 복합 인덱스로 개선 가능.

---

### 3.5 `Extra` 컬럼 — 중요한 추가 정보

#### 좋은 신호 ✅

|Extra|의미|
|---|---|
|`Using index`|커버링 인덱스 사용. 테이블 접근 없이 인덱스만으로 처리|
|`Using index condition`|ICP(Index Condition Pushdown). 인덱스 레벨에서 조건 필터링|

#### 주의 신호 ⚠️

|Extra|의미|대응|
|---|---|---|
|`Using filesort`|ORDER BY를 인덱스로 처리 못해 정렬 발생|ORDER BY 컬럼을 인덱스에 포함|
|`Using temporary`|임시 테이블 생성 (GROUP BY, DISTINCT 등)|인덱스 재설계, 쿼리 개선|
|`Using where`|인덱스 이후 추가 WHERE 필터링|단독으론 나쁘지 않지만 `rows`와 같이 봐야 함|

#### 심각 신호 🚨

|Extra|의미|
|---|---|
|`Using filesort` + `Using temporary` 동시|대용량 정렬+임시테이블로 매우 느릴 수 있음|

> **실무 팁**: `Using filesort`는 인덱스가 있어도 발생할 수 있다. `ORDER BY` 절의 컬럼이 인덱스 순서와 맞지 않거나, `WHERE` + `ORDER BY`가 서로 다른 인덱스를 쓸 때 발생.

---

### 3.6 `id` / `select_type` 컬럼

복잡한 쿼리(서브쿼리, UNION 등) 분석 시 필요.

#### `id`

- 같은 `id` = 같은 SELECT 단계 (조인)
- `id`가 다르면 서브쿼리 or UNION
- id가 **높을수록 먼저 실행**

#### `select_type`

|select_type|설명|
|---|---|
|`SIMPLE`|서브쿼리/UNION 없는 단순 SELECT|
|`PRIMARY`|가장 바깥쪽 SELECT|
|`SUBQUERY`|SELECT 절의 서브쿼리|
|`DERIVED`|FROM 절의 서브쿼리 (인라인 뷰)|
|`DEPENDENT SUBQUERY`|외부 쿼리에 의존하는 서브쿼리 ⚠️|
|`UNION`|UNION의 두 번째 이후 SELECT|

> **실무 팁**: `DEPENDENT SUBQUERY`는 외부 쿼리 행마다 서브쿼리가 실행되는 **상관 서브쿼리**. 대용량에서 치명적. JOIN이나 EXISTS로 변환 검토.

---

### 3.7 `key_len` 컬럼

실제 사용된 인덱스의 바이트 수. **복합 인덱스에서 얼마나 활용됐는지** 확인할 때 유용.

```sql
-- 인덱스: (user_id INT, status VARCHAR(10))
-- user_id만 사용: key_len = 4
-- user_id + status 모두 사용: key_len = 4 + (10 * 4 + 2) = 약 46
```

> **실무 팁**: 복합 인덱스를 설계했는데 `key_len`이 예상보다 작으면, 두 번째 이후 컬럼 조건이 인덱스에 사용되지 않고 있다는 신호.

## 4. 통계 정보와 옵티마이저 이해

### 왜 알아야 하나?

옵티마이저는 통계를 기반으로 실행 계획을 세운다. 통계가 오래됐으면 잘못된 계획을 선택할 수 있다.

```sql
-- 통계 정보 갱신
ANALYZE TABLE orders;

-- 테이블 통계 확인
SELECT * FROM information_schema.INNODB_TABLE_STATS
WHERE table_name = 'orders';
```

### 히스토그램 (MySQL 8.0+)

인덱스 없는 컬럼의 데이터 분포를 통계로 수집해 옵티마이저 정확도를 높임.

```sql
-- 히스토그램 생성
ANALYZE TABLE orders UPDATE HISTOGRAM ON status WITH 10 BUCKETS;

-- 히스토그램 확인
SELECT * FROM information_schema.COLUMN_STATISTICS
WHERE table_name = 'orders';
```

> **실무 팁**: 카디널리티가 낮은 컬럼(`status`, `is_deleted` 등)에 히스토그램을 설정하면 옵티마이저가 더 정확한 rows 추정 가능.

## 5. 실무 튜닝 체크리스트

### 실행 계획 확인 순서

```
1. type 확인 → ALL이나 index면 문제
2. key 확인 → NULL이면 인덱스 미사용
3. rows 확인 → 예상 스캔 행 수
4. filtered 확인 → 낮으면 인덱스 효율 나쁨
5. Extra 확인 → filesort, temporary 여부
```

### 자주 만나는 문제 패턴

#### 패턴 1: 인덱스가 있는데 `ALL`이 나오는 경우

```sql
-- 문제: 함수나 형변환으로 인덱스 무효화
SELECT * FROM orders WHERE YEAR(created_at) = 2024;  -- ❌
SELECT * FROM orders WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';  -- ✅

-- 문제: 묵시적 형변환
SELECT * FROM orders WHERE user_id = '123';  -- user_id가 INT인 경우 ❌
SELECT * FROM orders WHERE user_id = 123;    -- ✅
```

#### 패턴 2: `Using filesort` 제거

```sql
-- 인덱스: (user_id)
-- filesort 발생
SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC;

-- 인덱스를 (user_id, created_at)으로 변경하면 filesort 제거 가능
```

#### 패턴 3: 커버링 인덱스 활용

```sql
-- 인덱스: (user_id, status, created_at) 으로 설계 시
-- SELECT 절도 인덱스 컬럼만 사용하면 테이블 접근 없이 처리
SELECT user_id, status, created_at FROM orders WHERE user_id = 1;
-- Extra: Using index ✅
```

#### 패턴 4: `DEPENDENT SUBQUERY` 제거

```sql
-- ❌ 느린 상관 서브쿼리
SELECT * FROM users u
WHERE (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) > 0;

-- ✅ JOIN으로 변환
SELECT DISTINCT u.* FROM users u
INNER JOIN orders o ON o.user_id = u.id;

-- ✅ EXISTS로 변환 (더 명확)
SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

## 6. 요약 카드

```
┌─────────────────────────────────────────────────┐
│          실행 계획 분석 우선순위                    │
├──────────┬──────────────────────────────────────┤
│ 1순위    │ type = ALL 또는 index → 인덱스 문제    │
│ 2순위    │ key = NULL → 인덱스 미사용             │
│ 3순위    │ Extra에 filesort/temporary → 정렬 문제 │
│ 4순위    │ rows 크고 filtered 낮음 → 인덱스 비효율│
│ 5순위    │ select_type = DEPENDENT → 구조 개선   │
└──────────┴──────────────────────────────────────┘
```
