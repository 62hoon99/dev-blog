
B-Tree는 데이터베이스 인덱싱 알고리즘 가운데 가장 일반적으로 사용되고 가장 먼저 도입된 알고리즘이다. **칼럼의 원래 값을 변형하지 않고**, 인덱스 구조체 내에서 항상 **정렬된 상태**로 유지한다.

---

### 8.3.1 구조 및 특성

B-Tree는 루트 노드(Root Node), 브랜치 노드(Branch Node), 리프 노드(Leaf Node)의 3계층으로 구성된다.

```
         [루트 노드]
        /     |      \
 [브랜치] [브랜치] [브랜치]
   / \       / \      / \
 [리프] [리프] [리프] [리프] ...
```

- **루트/브랜치 노드** : 탐색 경로를 결정하는 키 값과 자식 노드 포인터를 가짐
- **리프 노드** : 실제 데이터 레코드를 찾아가기 위한 주소값을 가짐

**인덱스 키는 정렬되어 있지만, 데이터 파일의 레코드는 정렬되어 있지 않다.** INSERT 순서가 아니라 삭제된 공간을 재사용하는 방식으로 저장되기 때문이다.

#### MyISAM vs InnoDB 세컨더리 인덱스 구조 차이

|MyISAM|InnoDB|
|---|---|---|
|리프 노드가 가리키는 것|데이터 파일의 **물리적 주소**|**프라이머리 키 값** (논리적 주소)|
|레코드 접근 방식|주소로 데이터 파일 직접 접근|PK → 클러스터 인덱스 → 레코드 (2단계)|
|추가 I/O|없음|PK 인덱스를 한 번 더 탐색|

InnoDB에서 세컨더리 인덱스로 레코드를 읽는 흐름:

```
세컨더리 인덱스 탐색
    → 리프 노드에서 PK 값 획득
        → PK(클러스터) 인덱스 재탐색
            → 실제 레코드 반환
```

> InnoDB 세컨더리 인덱스는 항상 PK를 내포하고 있기 때문에, **PK 크기가 크면 세컨더리 인덱스도 덩달아 커진다**. PK를 작게 설계해야 하는 이유 중 하나다.

---

### 8.3.2 B-Tree 인덱스 키 추가 및 삭제

#### 인덱스 키 추가 (INSERT)

B-Tree에 새 키를 추가할 때는 적절한 리프 노드를 탐색한 후 저장한다. **리프 노드가 꽉 찬 경우 노드 분리(Split)** 가 발생하며, 이 작업이 상위 노드까지 전파될 수 있어 쓰기 비용이 높다.

- **MyISAM / MEMORY** : INSERT 즉시 B-Tree 인덱스에 반영
- **InnoDB** : 인덱스 키 추가 작업을 즉시 처리하지 않고 **체인지 버퍼(Change Buffer)에 임시 저장 후 지연 처리**. 단, 해당 페이지가 이미 버퍼 풀에 있으면 즉시 반영한다.

#### 인덱스 키 삭제

해당 리프 노드를 찾아 **삭제 마크(delete mark)** 만 표시하고 실제 공간 정리는 나중에 처리한다. 마찬가지로 InnoDB에서는 체인지 버퍼를 활용해 지연 처리가 가능하다.

#### 인덱스 키 변경

B-Tree는 키 값에 따라 저장 위치가 결정되기 때문에, 키 값 변경은 **기존 키 삭제 후 새 키 삽입**의 두 단계로 처리된다. InnoDB에서는 이 과정도 트랜잭션 내에서 처리된다.

#### 인덱스 키 검색

B-Tree 인덱스는 **100% 일치, 앞부분 일치, 범위 조건**에서 사용 가능하다. 단, 값을 변형해서 비교하는 경우(함수 적용 등)에는 인덱스를 사용할 수 없다.

**⚠️ InnoDB 인덱스와 잠금의 관계**

InnoDB의 레코드 잠금은 **테이블의 레코드가 아니라 인덱스를 잠그는 방식**으로 구현된다.

```sql
-- last_name에 인덱스가 있고, first_name에 인덱스가 없는 경우
UPDATE employees SET salary = 100000
WHERE last_name = 'Kim' AND first_name = 'Gihun';
```

위 쿼리에서 실제로 변경되는 레코드는 1건이지만, `last_name = 'Kim'` 조건에 해당하는 **인덱스 레코드 전체에 락이 걸린다.** `first_name`은 인덱스가 없어 필터링에 사용되지 않기 때문이다.

- 적절한 인덱스가 없으면 → 불필요하게 많은 레코드에 잠금 발생
- 극단적인 경우 → **테이블 전체 레코드가 잠길 수 있음**

이것이 **InnoDB에서 인덱스 설계가 단순한 성능 문제를 넘어 동시성(Concurrency)에 직접적인 영향을 주는 이유**다.

---

## 8.3.3 B-Tree 인덱스 사용에 영향을 미치는 요소

B-Tree 인덱스의 성능은 아래 요소들에 의해 결정된다.

- 인덱스를 구성하는 **칼럼의 크기**
- 테이블의 **레코드 건수**
- **유니크한 인덱스 키 값의 개수** (카디널리티)

---

### 8.3.3.1 인덱스 키 값의 크기

InnoDB 스토리지 엔진은 디스크에 데이터를 저장하는 가장 기본 단위를 **페이지(Page)** 또는 **블록(Block)** 이라고 한다.  
페이지는 디스크 읽기/쓰기 작업의 **최소 단위**이자, 버퍼 풀에서 데이터를 버퍼링하는 기본 단위이기도 하다.

> InnoDB 페이지 크기 기본값: **16KB** (`innodb_page_size` 시스템 변수로 조정 가능, 4KB ~ 64KB)

**B-Tree 인덱스 페이지 구조**

B-Tree의 각 노드는 하나의 페이지로 구성된다.  
하나의 페이지에 저장할 수 있는 키 엔트리 수는 아래 공식으로 계산한다.

```
저장 가능한 키 수 = 페이지 크기 / (키 값 크기 + 자식 노드 주소 크기)
```

자식 노드 주소 영역은 페이지 종류별로 6바이트 ~ 12바이트이며, 편의상 **12바이트**로 계산한다.

|인덱스 키 크기|키 + 주소 크기|페이지당 저장 가능한 키 수|
|:-:|:-:|:-:|
|16바이트|16 + 12 = 28바이트|16 * 1024 / 28 ≈ **585개**|
|32바이트|32 + 12 = 44바이트|16 * 1024 / 44 ≈ **372개**|

**실질적인 영향**

500개의 레코드를 읽어야 하는 상황을 가정하면:

```
[키 크기 16바이트]  → 페이지당 585개 저장
                   → 페이지 1개로 500개 커버 가능
                   → 디스크 I/O 1회

[키 크기 32바이트]  → 페이지당 372개 저장
                   → 페이지 1개로 500개 커버 불가
                   → 디스크 I/O 2회 필요
```

```
페이지 (16byte 키, 585개)
┌─────────────────────────────────────────────┐
│ K1│K2│K3│ ... │K372│K373│ ... │K500│...│K585│
└─────────────────────────────────────────────┘
  ↑ 500개 레코드 → 1페이지 안에 모두 포함 ✅

페이지 (32byte 키, 372개)
┌────────────────────────────┐  ┌─────────────────────┐
│ K1│K2│K3│ ... │K372        │  │K373│ ... │K500│ ... │
└────────────────────────────┘  └─────────────────────┘
  1페이지 (372개)                 2페이지 (나머지)
  ↑ 500개 레코드 → 2페이지 필요, 디스크 I/O 추가 발생 ❌
```

> **결론:** 인덱스 키 값이 커질수록 페이지당 저장 가능한 키 수가 줄어들고,  
> 같은 양의 데이터를 읽기 위해 더 많은 디스크 I/O가 발생한다.  
> **인덱스 키 값은 가능하면 작게 설계하는 것이 중요하다.**

---

### 8.3.3.2 B-Tree 깊이 (Depth)

B-Tree의 깊이는 루트 노드에서 리프 노드까지의 **레벨 수**를 의미한다.  
깊이가 깊어질수록 루트에서 리프까지 탐색하는 과정에서 더 많은 디스크 I/O가 발생한다.

> B-Tree의 깊이는 MySQL이 자동으로 관리하며, **사용자가 직접 제어할 수 없다.**

**키 크기와 깊이의 관계**

페이지당 저장 가능한 키 수가 많을수록, 동일한 레코드 수를 더 얕은 트리로 커버할 수 있다.

```
[키 크기 16바이트] → 페이지당 585개 키 저장 가능
  Depth 1 (루트만): 585개 커버
  Depth 2:         585 * 585 = 약 342,000개 커버
  Depth 3:         585^3    = 약 2억 개 커버

[키 크기 32바이트] → 페이지당 372개 키 저장 가능
  Depth 1 (루트만): 372개 커버
  Depth 2:         372 * 372 = 약 138,000개 커버
  Depth 3:         372^3    = 약 5,100만 개 커버
```

```
키 16바이트 (Depth 2, 페이지당 585개)          키 32바이트 (Depth 3 필요, 페이지당 372개)

        [Root]                                          [Root]
       /  |  \                                         /  |  \
   [L1] [L1] [L1]  ← 같은 레코드 수를          [L1] [L1] [L1]
   (리프)                커버 가능               /|\   /|\   /|\
                                              [L2][L2][L2]...  ← 깊이 1 증가
                                              (리프)
                                              → 탐색 시 I/O 1회 추가 발생
```

**실무 설계 포인트**

|상황|권장 사항|
|---|---|
|문자열 컬럼에 인덱스 생성|`VARCHAR(255)` 전체보다 앞 N글자만 인덱싱 (`prefix index`) 고려|
|복합 인덱스 설계|불필요하게 큰 컬럼을 앞에 두지 않기|
|정수 vs 문자열 PK|정수형 PK가 크기 면에서 유리 (`INT` 4바이트, `BIGINT` 8바이트)|

> **결론:** 인덱스 키 값이 작을수록 동일한 깊이에서 더 많은 레코드를 커버할 수 있고,  
> 대용량 테이블에서도 트리 깊이를 얕게 유지할 수 있어 탐색 성능이 향상된다.

## 8.3.3.3 선택도 (Cardinality / 기수성)

**선택도(Selectivity)** 란 인덱스의 전체 키 값 중 **유니크한 값의 수**를 의미한다.

```
선택도 = 유니크한 값의 수 / 전체 레코드 수
```

선택도가 높을수록 인덱스를 통해 걸러지는 레코드 수가 많아지므로 검색 성능이 향상된다.

**예시로 이해하기**

아래와 같은 `users` 테이블이 있다고 가정한다. (전체 레코드: 10,000건)

|컬럼|유니크한 값 수|선택도|비고|
|---|---|---|---|
|`user_id` (PK)|10,000|1.0 (100%)|완전 유니크|
|`email`|9,800|0.98 (98%)|거의 유니크|
|`gender`|2|0.0002 (0.02%)|매우 낮음|
|`age`|80|0.008 (0.8%)|낮음|

```sql
-- gender 컬럼에 인덱스가 있어도 선택도가 낮아 효율이 떨어짐
-- 'M' 조건 하나로 전체 레코드의 약 50%를 읽어야 함
SELECT * FROM users WHERE gender = 'M';

-- email 컬럼은 선택도가 높아 인덱스 효율이 좋음
-- 조건 하나로 1~2건으로 빠르게 좁혀짐
SELECT * FROM users WHERE email = 'test@example.com';
```

**인덱스가 아닌 컬럼의 기수성은 작업 범위에 영향 없음**

MySQL은 인덱스가 걸린 컬럼에 대해서만 통계 정보(유니크한 값의 개수)를 관리한다.  
따라서 **인덱스가 없는 컬럼**이 `WHERE` 조건에 포함되더라도, 해당 컬럼의 기수성은 옵티마이저의 **작업 범위 결정에 아무런 영향을 주지 못한다.**

```sql
-- country 컬럼에 인덱스 없음, age 컬럼에만 인덱스 있음
SELECT * FROM users WHERE age = 25 AND country = 'KR';

-- 옵티마이저 동작:
-- 1. age 인덱스로 age = 25에 해당하는 레코드를 먼저 추출 (작업 범위 결정)
-- 2. 추출된 레코드를 대상으로 country = 'KR' 필터링 (체크 조건, 범위 축소 불가)
-- country의 기수성이 아무리 높아도 인덱스 없이는 범위를 좁히는 데 기여하지 못함
```

> **결론:** 선택도가 높은 컬럼에 인덱스를 생성해야 효과적이다.  
> 선택도가 낮은 컬럼(예: `gender`, `boolean` 타입 등)은 인덱스를 생성해도 성능 향상이 미미하거나 오히려 오버헤드가 될 수 있다.

---

## 8.3.3.4 읽어야 하는 레코드의 건수

인덱스를 사용하는 것이 항상 빠른 것은 아니다. **읽어야 할 레코드 수에 따라 풀 테이블 스캔이 더 효율적인 경우가 있다.**

**인덱스 읽기 vs 직접 읽기 비용**

|읽기 방식|비용|이유|
|---|---|---|
|테이블 직접 읽기 (Full Table Scan)|1|순차 I/O, 페이지 단위 연속 읽기|
|인덱스를 통한 읽기|4 ~ 5배|랜덤 I/O 발생 (인덱스 탐색 → 레코드 페이지 이동)|

인덱스를 통해 레코드를 읽으면 **인덱스 페이지 탐색 + 레코드 페이지 랜덤 접근**이 발생하기 때문에 비용이 높다.

**손익 분기점**

```
인덱스 사용이 유리한 구간: 읽어야 할 레코드 수 < 전체 레코드의 20~25%
풀 테이블 스캔이 유리한 구간: 읽어야 할 레코드 수 >= 전체 레코드의 20~25%
```

```
전체 레코드 10,000건 기준

[인덱스 사용 유리]                    [풀 스캔 유리]
  0        2,000  2,500                          10,000
  |----------|------|---------------------------|
              ↑
           손익 분기점 (20~25%)

읽어야 할 레코드가 2,500건 이하 → 인덱스 사용
읽어야 할 레코드가 2,500건 초과 → 풀 테이블 스캔이 더 빠름
```

**옵티마이저의 판단**

MySQL 옵티마이저는 이 손익 분기점을 기준으로 실행 계획을 자동으로 선택한다.

```sql
-- 전체 10,000건 중 100건만 해당 → 인덱스 사용 (옵티마이저 선택)
SELECT * FROM users WHERE email = 'test@example.com';

-- 전체 10,000건 중 6,000건 해당 → 풀 테이블 스캔 선택
SELECT * FROM users WHERE age >= 10;
```

> 만약 옵티마이저가 잘못된 실행 계획을 선택한다면 `FORCE INDEX` 힌트로 강제할 수 있지만,  
> 대부분의 경우 옵티마이저의 판단을 따르는 것이 좋다.

---

## 8.3.4 B-Tree 인덱스를 통한 데이터 읽기

### 8.3.4.1 인덱스 레인지 스캔 (Index Range Scan)

인덱스 레인지 스캔은 B-Tree 인덱스에서 **특정 범위의 값을 순서대로 읽는** 방식이다.  
`=`, `BETWEEN`, `<`, `>`, `LIKE 'abc%'` 등의 조건에서 활용된다.

**동작 구조**

```
B-Tree 인덱스 구조

         [Root Node]
        /     |     \
   [Branch] [Branch] [Branch]
    /   \              /   \
[Leaf]  [Leaf] ← → [Leaf] [Leaf]   ← 리프 노드는 양방향 링크드 리스트로 연결
  |       |           |      |
(레코드 주소 포함)

WHERE age BETWEEN 25 AND 30 조건 시:

Step 1. [인덱스 탐색] 루트 → 브랜치 → 리프 순으로 age=25인 위치 탐색
Step 2. [인덱스 스캔] age=25 리프 노드부터 age=30까지 순차적으로 스캔
Step 3. [레코드 읽기] 각 인덱스 엔트리의 레코드 주소로 실제 데이터 페이지에 랜덤 접근
```

**3단계 처리 과정**

```
1단계: 인덱스 탐색 (Index Seek)
   - 조건을 만족하는 첫 번째 키 값의 위치를 B-Tree에서 탐색
   - 루트 노드 → 브랜치 노드 → 리프 노드 순으로 내려감

2단계: 인덱스 스캔 (Index Scan)
   - 탐색된 위치부터 조건 범위 끝까지 리프 노드를 순차적으로 읽음
   - 리프 노드는 링크드 리스트로 연결되어 있어 순차 스캔 가능

3단계: 레코드 읽기 (Random I/O)
   - 스캔된 각 인덱스 엔트리의 레코드 주소(rowid)로 데이터 페이지에 접근
   - 레코드마다 별도의 페이지에 접근할 수 있어 랜덤 I/O 발생
   - ※ 커버링 인덱스의 경우 이 단계 생략 가능
```

**커버링 인덱스와의 비교**

```
[일반 인덱스 레인지 스캔]
인덱스 리프 노드 → 레코드 주소 추출 → 데이터 페이지 랜덤 접근 (3단계 모두 수행)
                                        ↑ 레코드마다 랜덤 I/O 발생

[커버링 인덱스]
인덱스 리프 노드에서 필요한 모든 데이터 추출 → 끝 (3단계 생략)
                                               ↑ 랜덤 I/O 없음, 성능 대폭 향상
```

```sql
-- 일반 인덱스 레인지 스캔 (idx_age 인덱스 사용, 3단계 모두 수행)
SELECT * FROM users WHERE age BETWEEN 25 AND 30;

-- 커버링 인덱스 (SELECT 컬럼이 인덱스 안에 모두 포함, 3단계 생략)
-- idx_age_email (age, email) 복합 인덱스가 있다면:
SELECT age, email FROM users WHERE age BETWEEN 25 AND 30;
```

**작업 수행량 확인 상태 변수**

MySQL은 1단계(탐색)와 2단계(스캔)가 얼마나 수행됐는지 아래 상태 변수로 확인할 수 있다.

```sql
SHOW STATUS LIKE 'Handler_%';
```

|상태 변수|설명|
|---|---|
|`Handler_read_key`|인덱스 탐색(1단계) 횟수. 값이 높을수록 인덱스가 잘 활용되고 있음|
|`Handler_read_next`|인덱스 순방향 스캔(2단계) 횟수|
|`Handler_read_prev`|인덱스 역방향 스캔 횟수|
|`Handler_read_rnd_next`|데이터 파일에서 다음 레코드를 읽은 횟수. 값이 높으면 풀 테이블 스캔이 많이 발생함|

---
## 8.3.4.2 인덱스 풀 스캔 (Index Full Scan)

인덱스의 **처음부터 끝까지 모든 리프 노드를 순차적으로 읽는** 방식이다.

**발생 조건**

인덱스가 `(A, B, C)` 순서로 구성되어 있을 때, 쿼리 조건이 **선두 컬럼(A)을 포함하지 않는 경우** 발생한다.

```sql
-- 인덱스: (A, B, C)
SELECT * FROM t WHERE B = 'value';   -- A가 빠졌으므로 인덱스 풀 스캔
SELECT * FROM t WHERE C = 'value';   -- A, B가 빠졌으므로 인덱스 풀 스캔
```

**테이블 풀 스캔과의 비교**

```
[테이블 풀 스캔]
전체 데이터 페이지를 모두 읽음
→ 읽어야 할 페이지 수: 많음 (데이터 + 인덱스 페이지 모두 포함)

[인덱스 풀 스캔]
인덱스 리프 노드만 순차적으로 읽음
→ 읽어야 할 페이지 수: 적음 (인덱스 페이지만)
→ 단, SELECT * 처럼 인덱스에 없는 컬럼이 필요하면 결국 레코드도 읽어야 함
```

|스캔 방식|읽는 대상|속도|비고|
|---|---|---|---|
|인덱스 레인지 스캔|인덱스 일부 + 레코드|가장 빠름|정상적인 인덱스 활용|
|인덱스 풀 스캔|인덱스 전체 (+ 레코드)|중간|인덱스 비효율 사용|
|테이블 풀 스캔|데이터 페이지 전체|느림|인덱스 미사용|

**인덱스 사용 표현 정리**

```
"인덱스를 잘 사용한다"     → 인덱스 레인지 스캔 / 루스 인덱스 스캔
"인덱스를 사용하지 못한다" → 테이블 풀 스캔
"인덱스를 효율적으로       → 인덱스 풀 스캔
 사용하지 못한다"            (인덱스는 타지만 전부 읽음)
```

> **결론:** 인덱스 풀 스캔은 테이블 풀 스캔보다는 효율적이지만,  
> 인덱스를 제대로 활용하는 것은 아니다. 선두 컬럼을 조건에 포함하도록 쿼리나 인덱스를 재설계하는 것이 바람직하다.

---

## 8.3.4.3 루스 인덱스 스캔 (Loose Index Scan)

인덱스를 **듬성듬성 필요한 부분만 골라서 읽는** 방식이다.  
인덱스 레인지 스캔처럼 연속된 범위를 읽지 않고, **중간에 불필요한 키 값을 건너뛰면서** 스캔한다.

**주로 사용되는 경우**

- `GROUP BY` + 인덱스 컬럼
- `MAX()`, `MIN()` 집계 함수 최적화

**동작 예시**

```sql
-- 인덱스: (dept_no, emp_no)
SELECT dept_no, MIN(emp_no), MAX(emp_no)
FROM dept_emp
GROUP BY dept_no;
```

```
인덱스 리프 노드 (dept_no, emp_no 순 정렬)

d001 | 10001
d001 | 10002   ← 중간값 스킵
d001 | 10003
d001 | 99998
d001 | 99999   ← d001의 마지막 값 (MAX)
d002 | 10010   ← d002의 첫 번째 값 (MIN)
d002 | 10011   ← 중간값 스킵
d002 | 99990
d002 | 99991   ← d002의 마지막 값 (MAX)
...

루스 인덱스 스캔:
  - d001의 첫 번째(MIN)와 마지막(MAX) 값만 읽고 d002로 점프
  - 중간의 수많은 레코드를 스킵 → 읽는 양이 대폭 감소
```

**레인지 스캔과 비교**

```
[인덱스 레인지 스캔]               [루스 인덱스 스캔]
d001|10001 → 읽음                 d001|10001 → 읽음 (MIN)
d001|10002 → 읽음                 d001|10002 → 스킵 ↓
d001|10003 → 읽음                 d001|10003 → 스킵 ↓
   ...     → 읽음                    ...     → 스킵 ↓
d001|99999 → 읽음                 d001|99999 → 읽음 (MAX), 다음 그룹으로 점프
d002|10010 → 읽음                 d002|10010 → 읽음 (MIN)
   ...                               ...     → 스킵 ↓
```

> `EXPLAIN` 결과의 `Extra` 컬럼에 `Using index for group-by`가 표시되면 루스 인덱스 스캔이 사용된 것이다.

---

## 8.3.4.4 인덱스 스킵 스캔 (Index Skip Scan)

MySQL 8.0부터 도입된 최적화 기능으로, **선두 컬럼 조건 없이도** 인덱스를 활용할 수 있게 해준다.

**기존 문제 상황**

```sql
-- 인덱스: (gender, age)
-- gender 조건 없이 age만으로 검색하면 원래는 인덱스를 활용 못함
SELECT * FROM users WHERE age >= 25;
```

**인덱스 스킵 스캔 동작 원리**

옵티마이저가 내부적으로 선두 컬럼(`gender`)의 **유니크한 값을 모두 열거**한 뒤,  
각각의 값으로 쿼리를 분리해서 실행하는 방식으로 동작한다.

```
인덱스: (gender, age)
gender의 유니크한 값: 'M', 'F'

옵티마이저가 내부적으로 아래 두 쿼리로 분리하여 처리:
  ① SELECT * FROM users WHERE gender = 'M' AND age >= 25;
  ② SELECT * FROM users WHERE gender = 'F' AND age >= 25;

→ 각각 인덱스 레인지 스캔으로 처리 후 결과 합산
```

```
인덱스 리프 노드

F | 20  ← 스킵
F | 23  ← 스킵
F | 25  ← 읽음 ✅
F | 28  ← 읽음 ✅
F | 31  ← 읽음 ✅
M | 19  ← 스킵
M | 22  ← 스킵
M | 25  ← 읽음 ✅
M | 29  ← 읽음 ✅
M | 35  ← 읽음 ✅

→ gender 값이 바뀌는 지점에서 age 조건 범위로 점프
```

**적용 조건 및 단점**

|조건|설명|
|---|---|
|선두 컬럼의 유니크 값 수가 적어야 함|내부적으로 유니크 값 수만큼 쿼리가 생성되므로, 값이 많으면 오히려 비효율|
|커버링 인덱스여야 함|쿼리에서 사용하는 모든 컬럼이 인덱스에 포함되어 있어야 적용 가능|

```sql
-- 인덱스: (gender, age)

-- ✅ 스킵 스캔 적용 가능 (커버링 인덱스 + 선두 컬럼 유니크 값 적음)
SELECT gender, age FROM users WHERE age >= 25;

-- ❌ 스킵 스캔 적용 불가 (SELECT *는 커버링 인덱스 아님)
SELECT * FROM users WHERE age >= 25;
```

> `EXPLAIN` 결과의 `Extra` 컬럼에 `Using index for skip scan`이 표시되면 스킵 스캔이 사용된 것이다.

**스킵 스캔 vs 풀 스캔 비교**

```
[인덱스 풀 스캔]          [인덱스 스킵 스캔]
모든 리프 노드 읽음       선두 컬럼 값별로 필요한 범위만 읽음
                          → 읽는 양 감소, 성능 향상
```

> **결론:** 인덱스 스킵 스캔은 선두 컬럼이 조건에 없는 상황을 보완해주는 유용한 기능이지만,  
> **선두 컬럼의 카디널리티가 낮을 때만 효과적**이다.  
> 근본적으로는 쿼리 패턴에 맞게 인덱스를 재설계하는 것이 최선이다.

## 8.3.5 다중 컬럼 인덱스 (Composite Index)

두 개 이상의 컬럼으로 구성된 인덱스를 **다중 컬럼 인덱스** 또는 **복합 인덱스**라고 한다.

**핵심 원칙: 선두 컬럼 우선 정렬**

복합 인덱스는 **첫 번째 컬럼 기준으로 먼저 정렬**되고, 같은 값이 있을 때 **두 번째 컬럼 기준으로 정렬**된다.

```sql
-- 인덱스: (dept_no, emp_no)
-- 실제 인덱스 리프 노드 정렬 순서

dept_no | emp_no
--------|-------
d001    | 10001   ← dept_no 같으면 emp_no로 정렬
d001    | 10002
d001    | 10003
d002    | 10001   ← dept_no가 바뀌면 emp_no는 다시 처음부터
d002    | 10005
d003    | 10007
```

**컬럼 순서가 중요한 이유**

```sql
-- 인덱스: (A, B)

-- ✅ 인덱스 레인지 스캔 (A가 선두라 정상 활용)
SELECT * FROM t WHERE A = 1;
SELECT * FROM t WHERE A = 1 AND B = 2;
SELECT * FROM t WHERE A BETWEEN 1 AND 3;

-- ❌ 인덱스 풀 스캔 또는 미사용 (선두 컬럼 A 조건 없음)
SELECT * FROM t WHERE B = 2;
```

**컬럼 순서 결정 기준**

```
1. 선택도(카디널리티)가 높은 컬럼을 앞에
   → 검색 범위를 초반에 최대한 줄일 수 있음

2. 자주 쓰이는 조건의 컬럼을 앞에
   → WHERE 절에서 자주 등장하는 컬럼이 선두여야 인덱스 활용 가능

3. 범위 조건 컬럼은 가능하면 뒤에
   → 범위 조건 이후 컬럼은 인덱스 활용 불가
```

```sql
-- 인덱스: (gender, age)
-- gender는 'M'/'F' 2가지 → 카디널리티 낮음
-- age는 수십 가지 → 카디널리티 높음

-- ❌ 비효율적 설계: 카디널리티 낮은 컬럼이 선두
CREATE INDEX idx ON users (gender, age);

-- ✅ 효율적 설계: 카디널리티 높은 컬럼이 선두
CREATE INDEX idx ON users (age, gender);
```

**범위 조건이 있는 경우 주의점**

```sql
-- 인덱스: (age, gender, name)

SELECT * FROM users WHERE age BETWEEN 20 AND 30 AND gender = 'M' AND name = '홍길동';

-- age: 범위 조건 → 인덱스 활용 ✅
-- gender: age 범위 조건 이후 → 인덱스 활용 ❌ (필터링만 가능)
-- name: gender와 동일 → 인덱스 활용 ❌

-- 즉, 범위 조건 컬럼(age) 이후의 컬럼은 인덱스로 범위를 좁히지 못함
```

> **결론:** 복합 인덱스에서 컬럼 순서는 쿼리 성능에 직결된다.  
> 등치 조건(`=`) 컬럼 → 카디널리티 높은 컬럼 → 범위 조건 컬럼 순으로 설계하는 것이 일반적인 원칙이다.

## 8.3.6 B-Tree 인덱스의 정렬 및 스캔 방향

### 8.3.6.1 인덱스의 정렬

인덱스를 생성할 때 각 컬럼의 정렬 방향을 지정할 수 있다.

```sql
-- 오름차순 / 내림차순 혼합 인덱스 (MySQL 8.0+)
CREATE INDEX idx_mixed ON users (age ASC, score DESC);
```

MySQL 8.0 이전에는 `DESC` 키워드를 문법적으로는 허용했지만 **실제로는 무시**하고 항상 오름차순으로 저장했다. MySQL 8.0부터 진정한 내림차순 인덱스가 지원된다.

---

### 8.3.6.2 인덱스 스캔 방향

인덱스는 항상 정렬된 상태로 저장되어 있기 때문에, **옵티마이저가 쿼리에 따라 인덱스를 정방향 또는 역방향으로 읽는 방향을 실시간으로 결정**한다.

```sql
-- 인덱스: (age ASC)

-- 정방향 스캔 (Forward Scan)
SELECT * FROM users ORDER BY age ASC;
→ 인덱스 리프 노드를 왼쪽 → 오른쪽으로 읽음

-- 역방향 스캔 (Backward Scan)
SELECT * FROM users ORDER BY age DESC;
→ 인덱스 리프 노드를 오른쪽 → 왼쪽으로 읽음
```

```
[오름차순 인덱스 리프 노드]

← Backward Scan        Forward Scan →
[20] ↔ [23] ↔ [25] ↔ [28] ↔ [31] ↔ [35]

ORDER BY age ASC  → 왼쪽부터 순방향으로 읽음
ORDER BY age DESC → 오른쪽부터 역방향으로 읽음
```

**정방향 vs 역방향 스캔 성능 차이**

역방향 스캔이 정방향 스캔보다 **약간 느리다.** 이유는 InnoDB의 내부 구조 때문이다.

```
InnoDB 리프 노드 구조 (단방향 최적화)

[페이지 A] → [페이지 B] → [페이지 C]   ← 정방향 링크 (최적화됨)
[페이지 A] ← [페이지 B] ← [페이지 C]   ← 역방향 링크 (페이지 잠금 경합 발생 가능)

이유:
- InnoDB 페이지는 정방향 탐색에 최적화된 구조
- 역방향 스캔 시 페이지 잠금(Latch) 획득 순서가 반대로 되어 경합 발생 가능
- 대용량 정렬에서 역방향 스캔은 정방향 대비 약 28% 느릴 수 있음 (벤치마크 기준)
```

---

### 8.3.6.3 내림차순 인덱스 (Descending Index)

**내림차순 인덱스가 필요한 상황**

단일 컬럼이라면 오름차순 인덱스를 역방향 스캔해도 되지만,  
**복합 인덱스에서 각 컬럼의 정렬 방향이 혼합된 경우**에는 역방향 스캔만으로 해결이 불가능하다.

```sql
-- 인덱스: (age ASC, score ASC)

-- ✅ 해결 가능: 두 컬럼 모두 같은 방향
SELECT * FROM users ORDER BY age ASC, score ASC;   -- 정방향 스캔
SELECT * FROM users ORDER BY age DESC, score DESC;  -- 역방향 스캔

-- ❌ 해결 불가: 방향이 혼합됨 → filesort 발생
SELECT * FROM users ORDER BY age ASC, score DESC;
SELECT * FROM users ORDER BY age DESC, score ASC;
```

**왜 혼합 방향은 단순 역방향 스캔으로 안 될까?**

```
[인덱스: (age ASC, score ASC) 리프 노드]

age | score
----|------
 20 |  90
 20 |  85    ← age가 같을 때 score는 오름차순
 20 |  70
 25 |  95
 25 |  80
 30 |  75

ORDER BY age ASC, score DESC 요청 시:
  - age는 20 → 25 → 30 순 (ASC)
  - score는 70 → 85 → 90 순이 아니라 90 → 85 → 70 순 (DESC)이어야 함
  - 인덱스는 오름차순으로만 저장되어 있으므로 단순 스캔으로는 불가능
  → filesort(별도 정렬 작업) 발생
```

**내림차순 인덱스로 해결**

```sql
-- ✅ 혼합 정렬 인덱스 생성 (MySQL 8.0+)
CREATE INDEX idx_age_score ON users (age ASC, score DESC);

-- 이제 아래 쿼리가 filesort 없이 인덱스만으로 처리 가능
SELECT * FROM users ORDER BY age ASC, score DESC;
```

```
[인덱스: (age ASC, score DESC) 리프 노드]

age | score
----|------
 20 |  90    ← age가 같을 때 score는 내림차순으로 저장
 20 |  85
 20 |  70
 25 |  95
 25 |  80
 30 |  75

ORDER BY age ASC, score DESC → 정방향 스캔만으로 바로 처리 가능 ✅
```

**정리**

|상황|해결 방법|
|---|---|
|단일 컬럼 `ORDER BY col DESC`|오름차순 인덱스 역방향 스캔으로 처리 가능|
|복합 인덱스 모든 컬럼 같은 방향|정방향 또는 역방향 스캔으로 처리 가능|
|복합 인덱스 컬럼 방향 혼합|**반드시 혼합 정렬 인덱스 생성 필요** (MySQL 8.0+)|

> **결론:** 대부분의 경우 오름차순 인덱스의 역방향 스캔으로 `DESC` 정렬을 처리할 수 있다.  
> 단, 복합 인덱스에서 컬럼별 정렬 방향이 혼합된 쿼리가 빈번하다면,  
> MySQL 8.0의 내림차순 인덱스를 적극 활용해 `filesort`를 제거하는 것이 성능 최적화에 효과적이다.

## 8.3.7 B-Tree 인덱스의 가용성과 효율성

### 8.3.7.1 비교 조건의 종류와 효율성

다중 컬럼 인덱스에서 각 컬럼에 사용된 조건이 **동등 비교(`=`)** 인지 **범위 조건(`>`, `<`, `BETWEEN`)** 인지에 따라 인덱스 활용 범위가 달라진다.

**핵심 원칙: 범위 조건 이후 컬럼은 인덱스 활용 불가**

```sql
-- 인덱스: (dept_no, salary, age)
```

```
케이스 A: dept_no = 'dev' AND salary > 300 AND age = 30

인덱스 활용 여부:
  dept_no = 'dev'   → ✅ 작업 범위 결정 (동등 비교)
  salary > 300      → ✅ 작업 범위 결정 (범위 조건, 여기서 범위 확정)
  age = 30          → ❌ 작업 범위 결정 불가 (범위 조건 이후 컬럼)
                         필터링(체크 조건)으로만 사용

케이스 B: dept_no = 'dev' AND salary = 300 AND age > 25

인덱스 활용 여부:
  dept_no = 'dev'   → ✅ 작업 범위 결정
  salary = 300      → ✅ 작업 범위 결정
  age > 25          → ✅ 작업 범위 결정 (범위 조건이지만 마지막 컬럼)
```

```
[인덱스 리프 노드: (dept_no, salary, age)]

dept_no | salary | age
--------|--------|----
dev     |    200 |  25
dev     |    200 |  30
dev     |    300 |  28
dev     |    350 |  22   ← salary > 300 이후부터 스캔 시작
dev     |    350 |  35   ← age = 30 아니므로 필터링에서 제거
dev     |    400 |  30   ← age = 30 이므로 최종 결과에 포함
dev     |    400 |  45   ← age = 30 아니므로 필터링에서 제거
mkt     |    ...

케이스 A에서 salary > 300 이후 age는 정렬 기준이 아니므로
인덱스 내에서 age = 30인 값이 연속해 있다는 보장이 없음
→ 스캔한 레코드를 하나씩 age 조건으로 필터링해야 함 (비효율)
```

**컬럼 순서 변경으로 효율 개선**

```sql
-- ❌ 비효율적 인덱스 순서
CREATE INDEX idx ON employees (dept_no, salary, age);
SELECT * FROM employees WHERE dept_no = 'dev' AND salary > 300 AND age = 30;
-- salary 범위 조건 이후 age는 필터링만 가능

-- ✅ 효율적 인덱스 순서 (범위 조건 컬럼을 뒤로)
CREATE INDEX idx ON employees (dept_no, age, salary);
SELECT * FROM employees WHERE dept_no = 'dev' AND age = 30 AND salary > 300;
-- dept_no, age 모두 동등 비교로 범위 확정 후 salary 범위 조건 적용
-- 3개 컬럼 모두 인덱스 활용 가능 ✅
```

> **결론:** 복합 인덱스 설계 시 **동등 조건(`=`) 컬럼을 앞에, 범위 조건 컬럼을 뒤에** 배치해야  
> 더 많은 컬럼이 작업 범위 결정에 기여할 수 있다.

### 8.3.7.2 인덱스의 가용성

B-Tree 인덱스의 핵심 특성은 **"왼쪽 기준 정렬"** 이다.  
이는 단일 컬럼뿐 아니라 다중 컬럼 인덱스에도 동일하게 적용된다.

**단일 컬럼에서의 왼쪽 기준 정렬**

```
인덱스: (last_name)

정렬된 인덱스 값:
  'Apple'
  'Banana'
  'Candy'
  'Dog'
  'Elephant'

-- ✅ 왼쪽부터 비교 가능 → 인덱스 사용 가능
WHERE last_name = 'Banana'
WHERE last_name LIKE 'Ban%'      ← 왼쪽 고정, 오른쪽이 와일드카드

-- ❌ 왼쪽 기준이 없음 → 인덱스 사용 불가
WHERE last_name LIKE '%anana'    ← 왼쪽이 와일드카드
WHERE last_name LIKE '%ana%'     ← 양쪽 와일드카드
```

```
LIKE 'Ban%' → B → a → n 순으로 왼쪽부터 비교 가능
              인덱스에서 'Ban'으로 시작하는 위치를 탐색 후 스캔 ✅

LIKE '%ana' → 시작 위치를 특정할 수 없음
              인덱스 전체를 풀 스캔해야 함 ❌
```

**다중 컬럼 인덱스에서의 왼쪽 기준 정렬**

```sql
-- 인덱스: (A, B, C)
```

```
다중 컬럼 인덱스도 왼쪽(선두) 컬럼부터 순서대로 정렬됨

A | B | C
--|---|--
1 | 1 | 1
1 | 1 | 3
1 | 2 | 1   ← A가 같으면 B로 정렬
1 | 2 | 4
2 | 1 | 1   ← A가 바뀌면 B는 다시 처음부터
2 | 3 | 2
3 | 1 | 5

-- ✅ 선두 컬럼(A)부터 순서대로 조건 제공 → 인덱스 활용 가능
WHERE A = 1                          → A 활용
WHERE A = 1 AND B = 2                → A, B 활용
WHERE A = 1 AND B = 2 AND C = 4     → A, B, C 모두 활용

-- ❌ 선두 컬럼(A) 없이 중간/후미 컬럼만 조건 제공 → 인덱스 풀 스캔 또는 미사용
WHERE B = 2                          → A 없음, 인덱스 활용 불가
WHERE B = 2 AND C = 4                → A 없음, 인덱스 활용 불가
WHERE A = 1 AND C = 4                → B 건너뜀, C는 인덱스 활용 불가
```

### 8.3.7.3 가용성과 효율성 판단

**B-Tree 인덱스를 사용할 수 없는 조건들**

#### 1. `NOT`, `<>` (부정 조건)

```sql
-- ❌ 인덱스 사용 불가 (어디서부터 읽어야 할지 시작점을 특정할 수 없음)
WHERE age != 30
WHERE age NOT IN (25, 30)
WHERE dept_no <> 'dev'
```

#### 2. `LIKE '%검색어'` (왼쪽 와일드카드)

```sql
-- ❌ 인덱스 사용 불가
WHERE name LIKE '%길동'
WHERE name LIKE '%길%'

-- ✅ 인덱스 사용 가능 (오른쪽 와일드카드)
WHERE name LIKE '홍%'
WHERE name LIKE '홍길%'
```

#### 3. 인덱스 컬럼에 함수 또는 연산 적용

```sql
-- ❌ 인덱스 사용 불가 (컬럼 가공 시 인덱스 정렬 기준과 달라짐)
WHERE YEAR(created_at) = 2024
WHERE UPPER(name) = 'HONG'
WHERE age + 1 = 31
WHERE salary * 1.1 > 5000

-- ✅ 인덱스 사용 가능 (컬럼을 가공하지 않고 비교값을 가공)
WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'
WHERE age = 30
WHERE salary > 4545
```

#### 4. 데이터 타입 불일치

```sql
-- phone 컬럼이 VARCHAR 타입인데 숫자로 비교
-- ❌ 인덱스 사용 불가 (묵시적 형변환 발생)
WHERE phone = 01012345678

-- ✅ 인덱스 사용 가능 (타입 일치)
WHERE phone = '01012345678'
```

```
묵시적 형변환 발생 시:
  VARCHAR 컬럼 → 내부적으로 CAST(phone AS SIGNED) 처리와 동일
  → 인덱스 컬럼에 함수 적용한 것과 같은 효과
  → 인덱스 사용 불가
```

#### 5. 다중 컬럼 인덱스에서 선두 컬럼 누락

```sql
-- 인덱스: (dept_no, salary, age)

-- ❌ 선두 컬럼 없음 → 인덱스 사용 불가
WHERE salary = 300 AND age = 30

-- ✅ 선두 컬럼 포함 → 인덱스 사용 가능
WHERE dept_no = 'dev' AND salary = 300
```

**가용성과 효율성 종합 판단표**

```sql
-- 인덱스: (A, B, C) 기준
```

|조건|A 활용|B 활용|C 활용|비고|
|---|:-:|:-:|:-:|---|
|`A = 1`|✅|-|-||
|`A = 1 AND B = 2`|✅|✅|-||
|`A = 1 AND B = 2 AND C = 3`|✅|✅|✅|최적|
|`A = 1 AND B > 2 AND C = 3`|✅|✅|❌|B 범위 조건 이후 C 미활용|
|`A = 1 AND C = 3`|✅|❌|❌|B 누락으로 C 미활용|
|`B = 2`|❌|❌|❌|선두 컬럼 A 누락|
|`A LIKE '%val'`|❌|❌|❌|왼쪽 와일드카드|
|`A LIKE 'val%'`|✅|❌|❌|오른쪽 와일드카드, A만 활용|
|`A = 1 AND B LIKE 'val%'`|✅|✅|❌|B 범위성 조건 이후 C 미활용|

> **최종 정리**
> 
> - 인덱스는 **왼쪽(선두) 컬럼부터 순서대로** 활용된다
> - **동등 조건(`=`)** 은 다음 컬럼까지 인덱스 활용을 이어주지만, **범위 조건**은 해당 컬럼에서 인덱스 활용이 끊긴다
> - **컬럼 가공, 부정 조건, 왼쪽 와일드카드, 타입 불일치**는 인덱스를 무력화한다
