## 8.4 R-Tree 인덱스

MySQL이 지원하는 **공간 인덱스(Spatial Index)** 로, 2차원 공간 데이터를 인덱싱하고 검색하는 목적의 인덱스다.

|구분|B-Tree|R-Tree|
|---|---|---|
|데이터 차원|1차원 (숫자, 문자열 등 단일 값)|2차원 (좌표, 도형 등 공간 데이터)|
|정렬 기준|값의 크기|공간적 포함 관계 (MBR)|
|주요 용도|일반 컬럼 검색|위치 기반 검색|

---

### 8.4.1 구조 및 특성

**지원 데이터 타입**

|타입|설명|예시|
|---|---|---|
|`POINT`|단일 좌표점|특정 가게의 위치|
|`LINESTRING`|선 (점들의 연결)|도로, 경로|
|`POLYGON`|닫힌 다각형|행정구역 경계, 건물 외곽|
|`GEOMETRY`|위 모든 타입의 상위 타입|모든 공간 데이터|

**MBR (Minimum Bounding Rectangle)**

MBR이란 특정 도형을 완전히 감싸는 **최소 크기의 직사각형**을 의미한다.

```
실제 도형 (삼각형)         MBR (감싸는 최소 사각형)

      *                  ┌──────┐
     / \                 │  *   │
    /   \       →        │ / \  │
   /     \               │/   \ │
  *───────*              *─────-*
                         └──────┘
```

**R-Tree 인덱스 구조**

MBR들의 **포함 관계**를 계층적으로 표현한 것이 R-Tree 인덱스다.

```
[루트 노드] 가장 큰 MBR (전체 공간을 감싸는 사각형)
     │
     ├── [브랜치 노드] 중간 크기 MBR들
     │        ├── [리프 노드] 실제 도형의 MBR + 데이터 주소
     │        └── [리프 노드] 실제 도형의 MBR + 데이터 주소
     │
     └── [브랜치 노드] 중간 크기 MBR들
              ├── [리프 노드] 실제 도형의 MBR + 데이터 주소
              └── [리프 노드] 실제 도형의 MBR + 데이터 주소

→ B-Tree처럼 계층 구조이지만
  정렬 기준이 "값의 크기"가 아닌 "공간적 포함 관계"
```

```
실제 공간에서의 MBR 포함 관계 예시

┌─────────────────────────────┐  ← 루트 MBR (전체)
│  ┌──────────┐  ┌─────────┐  │
│  │ MBR-A   │  │  MBR-B  │  │  ← 브랜치 MBR
│  │  ┌───┐  │  │  ┌───┐  │  │
│  │  │ a │  │  │  │ b │  │  │  ← 리프 MBR (실제 도형)
│  │  └───┘  │  │  └───┘  │  │
│  └──────────┘  └─────────┘  │
└─────────────────────────────┘
```

---

### 8.4.2 R-Tree 인덱스의 용도

주로 **GPS 기반 위도/경도 좌표 저장 및 검색**에 사용되며, 좌표 시스템 기반의 모든 공간 정보에 적용할 수 있다.

**실무 활용 예시**

```sql
-- 테이블 생성
CREATE TABLE stores (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    location POINT NOT NULL SRID 4326,  -- SRID 4326 = GPS 좌표계 (위도/경도)
    SPATIAL INDEX idx_location (location)
);

-- 데이터 삽입 (경도, 위도 순서)
INSERT INTO stores VALUES (1, '스타벅스 강남점',
    ST_GeomFromText('POINT(127.0276 37.4979)', 4326));
```

**거리 기반 검색 방법**

`ST_Distance()` 단독으로는 인덱스를 활용하지 못한다.  
반드시 **`ST_Contains()` 또는 `ST_Within()`으로 범위를 먼저 좁힌 후** 거리 필터링을 해야 인덱스가 활용된다.

```sql
-- ❌ 인덱스 활용 불가 (ST_Distance만 사용)
SELECT * FROM stores
WHERE ST_Distance(location, ST_GeomFromText('POINT(127.0276 37.4979)', 4326)) <= 1000;

-- ✅ 인덱스 활용 가능 (ST_Contains로 범위 먼저 좁힘)
SET @center = ST_GeomFromText('POINT(127.0276 37.4979)', 4326);
SET @search_area = ST_Buffer(@center, 0.009);  -- 약 1km 반경의 사각형 생성

SELECT *, ST_Distance(location, @center) AS distance
FROM stores
WHERE ST_Contains(@search_area, location)      -- 인덱스 활용 (범위 필터)
  AND ST_Distance(location, @center) <= 1000   -- 정확한 거리 필터링 (원형)
ORDER BY distance;
```

```
ST_Contains + ST_Distance 조합의 동작 방식

① ST_Contains로 사각형 범위 내 후보 추출 (R-Tree 인덱스 활용)
┌─────────────────┐
│  ·    *    ·    │  * = 검색 반경 내 포함
│    ┌──────┐     │  · = 사각형엔 포함되나 반경 밖
│  · │  **  │ ·   │
│    │  **  │     │
│  · └──────┘ ·   │
└─────────────────┘
② ST_Distance로 원형 반경 밖 제거 (정확한 거리 계산)
```

**`ST_Contains` vs `ST_Within` 차이**

|함수|의미|사용 예|
|---|---|---|
|`ST_Contains(A, B)`|A가 B를 포함하는가|검색 영역이 해당 지점을 포함하는가|
|`ST_Within(A, B)`|A가 B 안에 있는가|해당 지점이 검색 영역 안에 있는가|

```sql
-- 아래 두 쿼리는 동일한 결과
WHERE ST_Contains(@search_area, location)
WHERE ST_Within(location, @search_area)
```

> **결론:** R-Tree 인덱스는 위치 기반 서비스(배달앱 근처 가게 검색, 지도 앱 주변 시설 검색 등)에서 핵심적으로 사용된다.  
> 단, 인덱스를 제대로 활용하려면 `ST_Contains()` 또는 `ST_Within()`으로 **사각형 범위를 먼저 좁힌 후** 정확한 거리 계산을 적용하는 2단계 방식을 사용해야 한다.

# 추가 학습 내용
## 위치 기반 서비스의 데이터 저장 및 검색 방식

### 1. MySQL R-Tree의 한계

MySQL R-Tree 인덱스는 소규모 서비스에는 적합하지만, 아래와 같은 한계가 있다.

```
데이터 수백만 건 이상 → 성능 급격히 저하
전 세계 단위 서비스  → R-Tree 인덱스 구조 한계
실시간 위치 추적     → MySQL로는 무리
```

---

### 2. 서비스 규모별 기술 스택

|서비스 규모|기술 스택|이유|
|---|---|---|
|소규모|MySQL R-Tree|간단, 별도 인프라 불필요|
|중규모|Redis GEOSEARCH + MySQL|실시간 응답 + 상세 정보 분리|
|대규모|PostGIS / 자체 공간 DB|복잡한 공간 연산, 대용량|
|구글맵급|S2 Geometry + 자체 분산 DB|전 세계 단위, 실시간 처리|

---

### 3. 소규모 서비스 — MySQL R-Tree

배달앱 초기 버전, 동네 맛집 앱 수준이라면 MySQL R-Tree로 충분하다.

```sql
CREATE TABLE restaurants (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    location POINT NOT NULL SRID 4326,
    SPATIAL INDEX idx_location (location)
);

-- 내 위치(127.0276, 37.4979) 기준 1km 반경 음식점 검색
SET @my_location = ST_GeomFromText('POINT(127.0276 37.4979)', 4326);
SET @search_area = ST_Buffer(@my_location, 0.009); -- 위도/경도 단위 약 1km

SELECT
    name,
    ST_Distance_Sphere(location, @my_location) AS distance_meter
FROM restaurants
WHERE ST_Contains(@search_area, location)
ORDER BY distance_meter
LIMIT 20;
```

---

### 4. 중규모 서비스 — Redis GEOSEARCH

Redis는 내부적으로 **Geohash** 방식으로 좌표를 저장한다.

**Geohash란?**

2차원 좌표를 1차원 문자열로 변환하는 인코딩 방식이다.

```
위도 37.4979, 경도 127.0276
         ↓ Geohash 인코딩
     "wydm6q..." (문자열)

지리적으로 가까운 위치일수록 Geohash 앞부분이 동일
  강남역:  wydm6qxx...
  역삼역:  wydm6rxx...  ← 앞부분 동일 = 같은 구역
  뉴욕:    dr5ru7xx...  ← 앞부분 다름 = 먼 구역

→ 이 문자열을 Sorted Set으로 저장
→ 근접 검색 = 앞부분이 같은 Geohash 찾기
```

**Redis GEOSEARCH 사용 예시**

```
# 데이터 저장
GEOADD restaurants 127.0276 37.4979 "스타벅스강남"
GEOADD restaurants 127.0281 37.4985 "맥도날드강남"

# 내 위치 기준 1km 이내 음식점 검색
GEOSEARCH restaurants
  FROMLONLAT 127.0276 37.4979
  BYRADIUS 1 km
  ASC
  COUNT 20
  WITHCOORD WITHDIST
```

**Redis GEOSEARCH의 장점**

- 인메모리 기반으로 응답 속도가 매우 빠름
- "내 주변 N km 이내" 같은 단순 근접 검색에 특화
- 실시간 위치 업데이트에 강함 (배달원 위치 추적 등)

---

### 5. 대규모 서비스 — PostGIS

PostgreSQL의 확장 모듈로, 가장 강력한 오픈소스 공간 DB다.

- 복잡한 공간 연산 및 대용량 처리에 강함
- 우버, 에어비앤비 초기에 사용
- MySQL R-Tree 대비 훨씬 다양한 공간 함수 지원

---

### 6. 구글맵급 서비스 — S2 Geometry + QuadTree

**QuadTree**

전 세계 지도를 재귀적으로 4등분하는 트리 구조다.

```
┌────┬────┐
│ NW │ NE │      각 셀을 재귀적으로 4등분
├────┼────┤  →   데이터 밀도가 높은 지역은 더 세밀하게 분할
│ SW │ SE │      (서울 > 강남구 > 역삼동 > 블록 단위)
└────┴────┘

장점:
  - 데이터 밀도에 따라 동적으로 분할 가능
  - 전 세계 좌표를 균일하게 처리 가능
  - 분산 시스템에 적합
```

**S2 Geometry (구글 오픈소스)**

지구를 정육면체로 감싼 후 각 면을 격자로 분할하는 방식이다.

```
구 → 정육면체 투영 → 각 면을 격자로 분할
                      ↓
              각 셀에 고유한 64비트 정수 ID 부여
              (Hilbert Curve 기반)

장점:
  - 극지방 왜곡 없이 균일한 셀 크기
  - 정수 ID로 범위 검색 가능 (B-Tree 인덱스 활용 가능)
  - 셀 계층 구조로 줌 레벨별 검색 가능
```

---

### 7. 실무 아키텍처 패턴 (배달앱 수준)

실무에서는 Redis와 MySQL의 역할을 분리하는 것이 일반적이다.

```
[앱] 내 위치(위도/경도) 전송
        ↓
[API 서버]
        ↓
[Redis GEOSEARCH]  ← 빠른 근접 검색 (실시간)
  "반경 3km 음식점 ID 목록" 반환
        ↓
[MySQL]  ← 음식점 상세 정보 조회
  음식점 메뉴, 평점, 영업시간 등 반환
        ↓
[앱] 결과 표시
```

|저장소|역할|이유|
|---|---|---|
|Redis|"어디 근처에 뭐가 있는가"|공간 검색, 빠른 응답|
|MySQL|"그게 뭔가"|상세 정보, 데이터 정합성|

> **결론:** MySQL R-Tree는 공간 인덱스 개념을 이해하는 데 좋지만,  
> 실무 위치 기반 서비스에서는 **Redis GEOSEARCH가 가장 현실적인 첫 번째 선택지**다.  
> 백엔드 개발자라면 Redis Geo 명령어를 익혀두는 것이 실용적이다.

## 8.5 전문 검색 인덱스 (Full-Text Search Index)

### B-Tree 인덱스의 한계

```
B-Tree 인덱스로 긴 문서를 검색하려 하면:

1. 키 길이 제한
   - MyISAM:  최대 1,000바이트까지만 인덱스 키로 사용
   - InnoDB:  최대 3,072바이트까지만 인덱스 키로 사용
   - 1MB짜리 문서 컬럼 → 앞부분만 잘려서 인덱싱됨

2. 검색 방식 제한
   - 전체 일치: WHERE content = '정확한 문장 전체'
   - 좌측 일치: WHERE content LIKE '시작단어%'
   - ❌ 불가: WHERE content LIKE '%중간단어%' → 인덱스 미사용, 풀 스캔
```

이러한 한계 때문에 **문서 내 특정 키워드 포함 여부**를 검색하는 데는 B-Tree 인덱스를 사용할 수 없다.  
이를 위해 **전문 검색 인덱스(Full-Text Index)** 가 필요하다.

---

### 8.5.1 인덱스 알고리즘

전문 검색 인덱스는 문서의 키워드를 추출하는 방식에 따라 두 가지로 구분된다.

---

#### 8.5.1.1 어근 분석 알고리즘 (Stemming)

문서에서 의미 있는 단어만 골라내는 **언어학적 접근** 방식이다.  
아래 두 단계를 거쳐 색인 작업이 수행된다.

**1단계: 불용어 처리 (Stop Word)**

검색 가치가 없는 단어를 필터링해서 제거한다.

```
원문: "This is a great product and I love it"

불용어 목록: this, is, a, and, i, it (조사, 접속사, 관사 등)

불용어 제거 후: "great product love"
→ 의미 있는 단어만 남김
```

**2단계: 어근 분석 (Stemming / Morphological Analysis)**

단어의 변형을 원형으로 되돌려 색인한다.

```
영어 예시:
  running → run
  loves   → love
  better  → good

한국어 예시 (형태소 분석):
  "데이터베이스를 공부하고 있습니다"
   → 데이터베이스 / 공부 / 하다  (형태소 단위로 분리)
```

MySQL에서는 **MeCab** 플러그인을 통해 한국어/일본어 형태소 분석을 지원한다.

```sql
-- MeCab 플러그인 설치 후 전문 검색 인덱스 생성
CREATE TABLE articles (
    id INT PRIMARY KEY,
    content TEXT,
    FULLTEXT INDEX idx_ft (content) WITH PARSER mecab
);
```

> **단점:** 언어별로 별도의 형태소 분석기가 필요하고, 한국어처럼 교착어는 분석 품질을 높이기 위한 추가 튜닝이 필요하다. 도입 및 유지 비용이 높다.

---

#### 8.5.1.2 n-gram 알고리즘

형태소 분석의 복잡함을 피하기 위해 도입된 방식으로,  
**언어에 무관하게 본문을 n글자씩 슬라이딩하며 잘라서 인덱싱**한다.

```
n=2 (bigram) 예시:
원문: "데이터베이스"

분리 결과:
  데이 / 이터 / 터베 / 베이 / 이스

→ 이 토큰들이 모두 인덱스 키로 등록됨
```

```
n=2 기준 검색 예시:
검색어: "베이스"

검색어도 동일하게 분리:
  베이 / 이스

→ 인덱스에서 "베이", "이스" 토큰을 포함하는 문서를 찾음
→ "데이터베이스" 포함 문서 검색됨 ✅
```

**n 값에 따른 특성**

|n 값|토큰 예시 ("MySQL")|특성|
|---|---|---|
|1 (unigram)|M, y, S, Q, L|너무 짧아 검색 정확도 낮음|
|2 (bigram)|My, yS, SQ, QL|MySQL 기본값, 균형적|
|3 (trigram)|MyS, ySQ, SQL|정확도 높지만 인덱스 크기 증가|

```sql
-- MySQL 기본 n-gram 파서 사용 (기본값 n=2)
CREATE TABLE articles (
    id INT PRIMARY KEY,
    title VARCHAR(500),
    content TEXT,
    FULLTEXT INDEX idx_ft (title, content) WITH PARSER ngram
);

-- n 값 변경 (my.cnf)
-- ngram_token_size = 2  (기본값)
```

> **장점:** 언어에 무관하게 동작, 별도 형태소 분석기 불필요  
> **단점:** 형태소 분석 대비 인덱스 크기가 크고, 불필요한 토큰도 인덱싱됨

---

#### 8.5.1.3 불용어 변경 및 삭제

**기본 불용어 무시**

```sql
-- 전역 설정 (my.cnf)
ft_stopword_file = ''           -- MyISAM: 빈 문자열로 불용어 비활성화
innodb_ft_enable_stopword = OFF -- InnoDB: 불용어 처리 비활성화
```

**사용자 정의 불용어**

```sql
-- 사용자 정의 불용어 테이블 생성
CREATE TABLE my_stopwords (value VARCHAR(30));
INSERT INTO my_stopwords VALUES ('그리고'), ('그러나'), ('하지만');

-- 전역 설정으로 적용
SET GLOBAL innodb_ft_server_stopword_table = 'mydb/my_stopwords';
```

> 서비스 도메인에 맞게 불용어를 커스터마이징하면 검색 품질을 높일 수 있다.  
> 예: 쇼핑몰이라면 "상품", "제품" 같은 단어는 불용어로 처리

### 8.5.2 전문 검색 인덱스의 가용성

전문 검색 인덱스를 활용하려면 반드시 아래 두 가지 조건을 모두 충족해야 한다.

```
조건 1. 테이블에 FULLTEXT 인덱스가 생성되어 있어야 함
조건 2. 쿼리가 MATCH ... AGAINST 문법을 사용해야 함
```

**잘못된 사용 vs 올바른 사용**

```sql
-- ❌ 전문 검색 인덱스 미활용 (풀 테이블 스캔 발생)
SELECT * FROM articles WHERE content LIKE '%데이터베이스%';

-- ✅ 전문 검색 인덱스 활용
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('데이터베이스' IN BOOLEAN MODE);
```

**MATCH ... AGAINST 검색 모드**

```sql
-- 1. 자연어 검색 (Natural Language Mode, 기본값)
--    관련도 점수 기반으로 결과 반환
SELECT *, MATCH(content) AGAINST('데이터베이스') AS score
FROM articles
WHERE MATCH(content) AGAINST('데이터베이스')
ORDER BY score DESC;

-- 2. 불리언 검색 (Boolean Mode)
--    연산자를 이용한 정교한 검색 가능
SELECT * FROM articles
WHERE MATCH(content) AGAINST('+데이터베이스 -Oracle' IN BOOLEAN MODE);
-- + : 반드시 포함
-- - : 반드시 제외
```

**MATCH 절 컬럼 주의사항**

```sql
-- 인덱스: FULLTEXT INDEX idx_ft (title, content)

-- ✅ 인덱스 생성 시 컬럼과 MATCH 절 컬럼이 정확히 일치
WHERE MATCH(title, content) AGAINST('검색어')

-- ❌ 컬럼 순서나 구성이 다르면 인덱스 미사용
WHERE MATCH(content) AGAINST('검색어')        -- title 누락
WHERE MATCH(content, title) AGAINST('검색어') -- 순서 다름
```

**B-Tree vs 전문 검색 인덱스 비교**

|구분|B-Tree 인덱스|전문 검색 인덱스|
|---|---|---|
|적합한 데이터|짧은 값, 정형 데이터|긴 문서, 비정형 텍스트|
|검색 방식|등치, 범위, 좌측 일치|키워드 포함 여부|
|문법|`WHERE col = ?` / `LIKE`|`MATCH ... AGAINST`|
|정렬 기준|값의 크기|관련도 점수(score)|
|인덱스 크기|작음|큼 (모든 토큰 저장)|

> **결론:** 전문 검색 인덱스는 블로그 본문, 상품 설명, 게시글처럼 **긴 텍스트에서 키워드 검색**이 필요한 경우에 사용한다.  
> 단, 인덱스 크기가 크고 실시간 업데이트 성능이 B-Tree보다 낮으므로, **검색 품질이 중요한 서비스라면 Elasticsearch 같은 전문 검색 엔진을 별도로 사용하는 것이 일반적**이다.

## 8.6 함수 기반 인덱스 (Function-Based Index)

일반적인 인덱스는 컬럼의 값 그대로만 인덱싱할 수 있다.  
하지만 **컬럼 값을 가공한 결과**에 대해 인덱스가 필요한 경우, 함수 기반 인덱스를 활용한다.

**함수 기반 인덱스가 필요한 상황**

```sql
-- 이메일에서 도메인만 추출해서 검색하는 경우
SELECT * FROM users WHERE SUBSTRING_INDEX(email, '@', -1) = 'gmail.com';

-- 날짜에서 연도만 추출해서 검색하는 경우
SELECT * FROM orders WHERE YEAR(created_at) = 2024;

-- 위 두 경우 모두 컬럼에 함수를 적용했으므로 일반 인덱스 사용 불가
-- → 함수 기반 인덱스 필요
```

구현 방법은 두 가지다.

```
1. 가상 컬럼(Virtual Column)을 만들고 그 위에 인덱스 생성
2. 함수 표현식을 직접 인덱스로 생성 (MySQL 8.0+)

내부 구조와 유지관리 방식은 B-Tree 인덱스와 동일하다.
인덱싱할 값을 계산하는 과정만 다를 뿐이다.
```

---

### 8.6.1 가상 컬럼을 이용한 인덱스

테이블에 **가상 컬럼(Generated Column)** 을 추가하고, 그 컬럼에 인덱스를 생성하는 방식이다.

```sql
-- 기존 테이블
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(100),
    created_at DATETIME
);

-- 가상 컬럼 + 인덱스 추가
ALTER TABLE users
    ADD COLUMN email_domain VARCHAR(50)
        AS (SUBSTRING_INDEX(email, '@', -1)) VIRTUAL,  -- 가상 컬럼 정의
    ADD INDEX idx_email_domain (email_domain);          -- 가상 컬럼에 인덱스 생성
```

```
VIRTUAL vs STORED 차이

VIRTUAL (기본값)
  - 디스크에 저장되지 않음
  - 레코드를 읽을 때마다 계산
  - 저장 공간 절약

STORED
  - 디스크에 실제로 저장됨
  - INSERT/UPDATE 시 계산 후 저장
  - 저장 공간 사용하지만 읽기 빠름
  - 인덱스 생성 가능 (VIRTUAL도 가능)
```

**활용 예시**

```sql
-- 이메일 도메인으로 검색 → 인덱스 활용 ✅
SELECT * FROM users WHERE email_domain = 'gmail.com';

-- 연도 기반 가상 컬럼
ALTER TABLE orders
    ADD COLUMN order_year SMALLINT
        AS (YEAR(created_at)) VIRTUAL,
    ADD INDEX idx_order_year (order_year);

-- 연도로 검색 → 인덱스 활용 ✅
SELECT * FROM orders WHERE order_year = 2024;
```

**장점과 단점**

|구분|내용|
|---|---|
|장점|가상 컬럼명으로 직관적인 쿼리 작성 가능|
|장점|기존 쿼리 수정 없이 컬럼명으로 검색 가능|
|단점|테이블 스키마가 변경됨|
|단점|컬럼이 늘어나 스키마 복잡도 증가|

---

### 8.6.2 함수를 이용한 인덱스

MySQL 8.0부터 **테이블 구조 변경 없이** 함수 표현식을 직접 인덱스로 생성할 수 있다.

```sql
-- 가상 컬럼 없이 함수 표현식으로 바로 인덱스 생성
CREATE INDEX idx_email_domain
    ON users ((SUBSTRING_INDEX(email, '@', -1)));
--           ↑ 표현식은 반드시 괄호로 감싸야 함

-- 날짜 함수 인덱스
CREATE INDEX idx_order_year
    ON orders ((YEAR(created_at)));

-- 문자열 소문자 변환 인덱스 (대소문자 구분 없는 검색)
CREATE INDEX idx_lower_name
    ON users ((LOWER(name)));
```

**인덱스 활용 조건 — 표현식이 정확히 일치해야 함**

```sql
-- ✅ 인덱스 활용 (표현식이 인덱스 정의와 정확히 동일)
SELECT * FROM users
WHERE SUBSTRING_INDEX(email, '@', -1) = 'gmail.com';

-- ❌ 인덱스 미활용 (표현식이 다름)
SELECT * FROM users
WHERE SUBSTRING_INDEX(email, '@', 1) = 'gmail.com';  -- 인자 다름

-- ❌ 인덱스 미활용 (컬럼 직접 검색)
SELECT * FROM users WHERE email = 'test@gmail.com';
```

```
함수 기반 인덱스가 활용되는 원리

인덱스 생성 시:
  SUBSTRING_INDEX(email, '@', -1) 계산 결과를 B-Tree에 저장
  'test@gmail.com'    → 'gmail.com'  저장
  'hello@naver.com'   → 'naver.com'  저장
  'world@kakao.com'   → 'kakao.com'  저장

검색 시:
  WHERE SUBSTRING_INDEX(email, '@', -1) = 'gmail.com'
  → 'gmail.com'으로 B-Tree 탐색 → 인덱스 활용 ✅

  WHERE email = 'test@gmail.com'
  → 표현식이 다르므로 인덱스 탐색 불가 ❌
```

**가상 컬럼 방식 vs 함수 인덱스 방식 비교**

|구분|가상 컬럼 + 인덱스|함수 기반 인덱스|
|---|---|---|
|스키마 변경|필요 (컬럼 추가)|불필요|
|쿼리 작성|컬럼명으로 검색 가능|반드시 동일 표현식 사용|
|가독성|높음|낮음 (표현식이 길 경우)|
|MySQL 버전|5.7+|8.0+|

> **결론:** 스키마 변경이 부담스럽고 MySQL 8.0 이상이라면 함수 기반 인덱스가 편리하다.  
> 단, **조건절에 인덱스 생성 시 사용한 표현식을 정확히 동일하게 작성**해야 인덱스가 활용된다.

## 8.7 멀티 밸류 인덱스 (Multi-Value Index)

### 기존 인덱스와의 차이

기존 인덱스는 레코드 1건 : 인덱스 키 1개의 **1:1 관계**였다.

```
[일반 인덱스]
레코드 1 (id=1, age=25) → 인덱스 키: 25
레코드 2 (id=2, age=30) → 인덱스 키: 30
레코드 3 (id=3, age=28) → 인덱스 키: 28
```

멀티 밸류 인덱스는 레코드 1건이 **여러 개의 인덱스 키**를 가질 수 있는 **1:N 관계**다.

```
[멀티 밸류 인덱스]
레코드 1 (id=1, credit_scores=[700, 750, 800])
  → 인덱스 키: 700, 750, 800  (3개의 키가 모두 같은 레코드를 가리킴)
```

### 도입 배경

```
RDBMS의 정규화 원칙상 하나의 컬럼에 여러 값을 저장하는 것은 위반이다.
그러나 MySQL 5.7부터 JSON 타입을 지원하면서
JSON 배열 필드에 저장된 원소들에 대한 인덱스 요건이 생겼다.
→ MySQL 8.0에서 멀티 밸류 인덱스로 해결
```

### 생성 및 사용 예시

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    credit_info JSON,  -- JSON 배열 컬럼
    INDEX idx_credit ((CAST(credit_info->'$.credit_scores' AS UNSIGNED ARRAY)))
    --                 ↑ JSON 배열을 ARRAY 타입으로 캐스팅
);

-- 데이터 삽입
INSERT INTO users VALUES
(1, '홍길동', '{"credit_scores": [700, 750, 800]}'),
(2, '김철수', '{"credit_scores": [600, 650]}'),
(3, '이영희', '{"credit_scores": [800, 850, 900]}');
```

**멀티 밸류 인덱스 내부 구조**

```
인덱스 키  │  레코드 주소
-----------│-------------
600        │  → id=2 (김철수)
650        │  → id=2 (김철수)
700        │  → id=1 (홍길동)
750        │  → id=1 (홍길동)
800        │  → id=1 (홍길동), id=3 (이영희)  ← 같은 키에 여러 레코드
850        │  → id=3 (이영희)
900        │  → id=3 (이영희)
```

**검색 쿼리 — 반드시 전용 함수 사용**

멀티 밸류 인덱스를 활용하려면 `MEMBER OF()`, `JSON_CONTAINS()`, `JSON_OVERLAPS()` 함수를 사용해야 한다.

```sql
-- MEMBER OF(): 특정 값이 배열에 포함되는지 검색
SELECT * FROM users
WHERE 750 MEMBER OF (credit_info->'$.credit_scores');
-- → 홍길동 반환 (credit_scores에 750 포함)

-- JSON_CONTAINS(): 배열이 특정 값들을 모두 포함하는지 검색
SELECT * FROM users
WHERE JSON_CONTAINS(credit_info->'$.credit_scores', '[700, 750]');
-- → 홍길동 반환 (700, 750 모두 포함)

-- JSON_OVERLAPS(): 두 배열 중 겹치는 원소가 하나라도 있는지 검색
SELECT * FROM users
WHERE JSON_OVERLAPS(credit_info->'$.credit_scores', '[750, 800]');
-- → 홍길동, 이영희 반환 (750 또는 800 포함)
```

**주의사항**

```
일반 JSON 조건으로는 멀티 밸류 인덱스 활용 불가

-- ❌ 인덱스 미활용
SELECT * FROM users
WHERE JSON_EXTRACT(credit_info, '$.credit_scores') LIKE '%750%';

-- ✅ 인덱스 활용
SELECT * FROM users
WHERE 750 MEMBER OF (credit_info->'$.credit_scores');
```

> **결론:** 멀티 밸류 인덱스는 JSON 배열 데이터를 효율적으로 검색할 수 있게 해주지만,  
> 정규화 원칙에 위배되는 구조인 만큼 **JSON 배열이 꼭 필요한 경우에만 사용**하는 것이 바람직하다.  
> 반드시 `MEMBER OF()`, `JSON_CONTAINS()`, `JSON_OVERLAPS()` 전용 함수를 사용해야 인덱스가 활용된다.

## 8.8 클러스터링 인덱스 (Clustering Index)

클러스터링이란 **여러 개를 하나로 묶는다**는 의미로, MySQL에서는 **프라이머리 키 값이 비슷한 레코드끼리 묶어서 물리적으로 인접한 위치에 저장**하는 방식을 의미한다.

```
InnoDB  → 클러스터링 인덱스 지원 ✅
MyISAM  → 클러스터링 인덱스 미지원 ❌ (힙 구조로 저장)
```

---

### 8.8.1 클러스터링 인덱스

**핵심 개념: 인덱스 알고리즘이 아닌 테이블 저장 방식**

클러스터링 인덱스는 프라이머리 키 값에 의해 **레코드의 물리적 저장 위치가 결정**되는 구조다.  
따라서 인덱스 알고리즘이라기보다 **테이블 레코드의 저장 방식**으로 이해하는 것이 정확하다.

```
[일반 인덱스 (MyISAM 힙 구조)]
레코드가 INSERT 순서대로 저장됨

id=5 저장 위치: 0x001
id=2 저장 위치: 0x002   ← PK와 무관하게 삽입 순서대로
id=8 저장 위치: 0x003
id=1 저장 위치: 0x004

[클러스터링 인덱스 (InnoDB)]
레코드가 PK 순서대로 정렬되어 저장됨

id=1 저장 위치: 0x001
id=2 저장 위치: 0x002   ← PK 순서대로 물리적으로 정렬
id=5 저장 위치: 0x003
id=8 저장 위치: 0x004
```

**클러스터링 인덱스 구조**

일반 B-Tree 인덱스와 달리, 리프 노드에 **레코드의 모든 컬럼**이 저장된다.  
즉, 클러스터링 테이블 자체가 하나의 거대한 B-Tree 인덱스 구조다.

```
[일반 세컨더리 인덱스 리프 노드]
┌──────────┬──────────────┐
│  키 값   │ 레코드 주소  │  ← 주소만 저장
└──────────┴──────────────┘

[클러스터링 인덱스 리프 노드]
┌──────────┬─────────────────────────────────────┐
│  PK 값   │ col1 │ col2 │ col3 │ ... (모든 컬럼)│  ← 실제 데이터 전체 저장
└──────────┴─────────────────────────────────────┘
```

**PK 변경 시 물리적 위치도 변경**

```
UPDATE users SET id = 10 WHERE id = 1;

Before: [id=1 | 홍길동 | 25] → 0x001 위치
After:  [id=10 | 홍길동 | 25] → 0x005 위치로 이동

→ PK가 변경되면 레코드가 새 위치로 이동해야 함 (비용 큼)
→ PK는 변경되지 않는 값으로 설계해야 함
```

**PK가 없는 경우 클러스터링 키 선택 순서**

```
1순위: 프라이머리 키
2순위: NOT NULL + UNIQUE 인덱스 중 첫 번째
3순위: 위 둘 다 없으면 InnoDB가 내부적으로 48비트 숨겨진 키를 자동 생성
        → 사용자가 접근 불가, 아무런 이점 없음
        → 반드시 PK를 명시하는 것이 좋다
```

---

### 8.8.2 프라이머리 키가 세컨더리 인덱스에 미치는 영향

**세컨더리 인덱스가 레코드 주소를 저장하면 생기는 문제**

```
PK가 변경되면 레코드의 물리적 위치가 바뀜
→ 해당 레코드를 가리키는 모든 세컨더리 인덱스의 주소를 일일이 업데이트해야 함
→ 세컨더리 인덱스가 많을수록 업데이트 비용 폭증
```

**InnoDB의 해결책: 세컨더리 인덱스에 PK 값 저장**

```
[세컨더리 인덱스 리프 노드]
┌──────────┬──────────────┐
│  키 값   │   PK 값      │  ← 주소 대신 PK 값 저장
└──────────┴──────────────┘
```

**세컨더리 인덱스를 통한 검색 과정**

```
SELECT * FROM users WHERE name = '홍길동';
-- name 컬럼에 세컨더리 인덱스 존재

Step 1. name 세컨더리 인덱스에서 '홍길동' 탐색
         → PK 값 = 1 획득

Step 2. PK 값(1)으로 클러스터링 인덱스 재탐색
         → 실제 레코드 데이터 획득

→ 세컨더리 인덱스 검색은 항상 2번의 인덱스 탐색이 발생
```

```
[클러스터링 인덱스]                [세컨더리 인덱스 (name)]
루트                               루트
 │                                  │
리프: id=1 │ 홍길동 │ 25 │ ...      리프: 홍길동 │ PK=1
리프: id=2 │ 김철수 │ 30 │ ...      리프: 김철수 │ PK=2
           ↑                                      │
           └──────────────────────────────────────┘
                    PK로 재탐색
```

---

### 8.8.3 클러스터링 인덱스의 장점과 단점

**장점**

```
1. PK 검색 성능이 매우 빠름
   - 리프 노드에 실제 데이터가 있어 바로 반환 가능
   - 범위 검색(BETWEEN, >, <)에서 특히 효과적
     → PK 순으로 물리적으로 정렬되어 있어 순차 I/O 발생

2. 커버링 인덱스 활용 가능성 높음
   - 세컨더리 인덱스가 PK를 포함하고 있어
     PK 컬럼이 SELECT에 있어도 추가 조회 없이 처리 가능
```

**단점**

```
1. 세컨더리 인덱스 크기 증가
   - 모든 세컨더리 인덱스가 PK 값을 포함
   - PK 크기가 크면 전체 세컨더리 인덱스 크기가 비례해서 증가

   예시: PK가 INT(4바이트) vs VARCHAR(32바이트)
   세컨더리 인덱스 10개 존재 시
   → INT:     10 * 4바이트  = 40바이트 추가
   → VARCHAR: 10 * 32바이트 = 320바이트 추가 (8배)

2. 세컨더리 인덱스 검색 시 2번의 인덱스 탐색 필요
   - 세컨더리 인덱스 → PK 획득 → 클러스터링 인덱스 재탐색

3. INSERT 성능 저하
   - PK 순서에 맞는 위치를 찾아 삽입해야 함
   - 페이지가 꽉 찬 경우 페이지 분할(Page Split) 발생
   
   [페이지 분할 예시]
   PK: 1, 3, 5, 7, 9 가 꽉 찬 페이지에 PK=4 삽입 시
   → 페이지를 두 개로 분할하고 재정렬
   → I/O 비용 증가

4. PK 변경 시 비용 큼
   - 기존 레코드 DELETE + 새 위치에 INSERT 수행
   - 연쇄적으로 세컨더리 인덱스도 업데이트 필요
```

---

### 8.8.4 클러스터링 테이블 사용 시 주의사항

#### 8.8.4.1 클러스터링 인덱스 키의 크기

```
PK 크기와 세컨더리 인덱스 크기는 비례 관계

[PK: INT 4바이트, 세컨더리 인덱스 5개, 레코드 1억 건]
세컨더리 인덱스 추가 저장 공간: 4 * 5 * 1억 = 약 2GB

[PK: VARCHAR(50) 50바이트, 동일 조건]
세컨더리 인덱스 추가 저장 공간: 50 * 5 * 1억 = 약 25GB (12배 이상)
```

> PK 크기는 가능하면 작게 설계하는 것이 전체 인덱스 크기에 큰 영향을 미친다.

---

#### 8.8.4.2 PK는 AUTO_INCREMENT보다 업무적인 컬럼으로 생성

PK는 검색에서 빈번하게 사용되므로, **업무적으로 레코드를 대표할 수 있는 컬럼**이 있다면 크기가 다소 크더라도 PK로 설정하는 것이 좋다.

```sql
-- 주문 테이블 예시
-- order_no가 업무적으로 레코드를 대표하고 자주 검색에 사용된다면
CREATE TABLE orders (
    order_no VARCHAR(20) PRIMARY KEY,  -- 업무 식별자를 PK로
    user_id INT,
    amount DECIMAL(10,2),
    ...
);

-- 단순 AUTO_INCREMENT보다 order_no로 직접 검색 시 훨씬 빠름
SELECT * FROM orders WHERE order_no = 'ORD-2024-001234';
```

---

#### 8.8.4.3 PK는 반드시 명시할 것

```sql
-- ❌ PK 없는 테이블
CREATE TABLE logs (
    user_id INT,
    action VARCHAR(100),
    created_at DATETIME
);
-- → InnoDB가 내부적으로 숨겨진 48비트 키 자동 생성
-- → 사용자가 제어 불가, PK 검색 이점 없음, 세컨더리 인덱스도 이 숨겨진 키 참조

-- ✅ PK 명시
CREATE TABLE logs (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id INT,
    action VARCHAR(100),
    created_at DATETIME
);
```

---

#### 8.8.4.4 AUTO_INCREMENT를 인조 식별자로 사용할 경우

복합 PK로 키 크기가 길어지는 경우의 판단 기준은 다음과 같다.

```
세컨더리 인덱스가 없다면?
  → 복합 PK 그대로 사용 (크기가 커도 무방)

세컨더리 인덱스가 필요하고 PK 크기도 크다면?
  → AUTO_INCREMENT 인조 식별자를 PK로 추가
  → 기존 복합 컬럼은 UNIQUE INDEX로 대체
```

```sql
-- ❌ 복합 PK + 세컨더리 인덱스가 많은 경우
CREATE TABLE order_items (
    order_no VARCHAR(20),
    product_no VARCHAR(20),
    user_id INT,
    ...
    PRIMARY KEY (order_no, product_no),  -- PK 크기 40바이트
    INDEX idx_user (user_id)             -- user_id + 40바이트 PK 저장
);

-- ✅ 인조 식별자 도입
CREATE TABLE order_items (
    id BIGINT AUTO_INCREMENT PRIMARY KEY, -- 인조 식별자 (8바이트)
    order_no VARCHAR(20),
    product_no VARCHAR(20),
    user_id INT,
    ...
    UNIQUE KEY uq_order_product (order_no, product_no), -- 업무 유일성 보장
    INDEX idx_user (user_id)              -- user_id + 8바이트 PK만 저장
);
```

**INSERT 위주 테이블에서 AUTO_INCREMENT가 유리한 이유**

```
AUTO_INCREMENT PK는 항상 증가하는 값
→ 새 레코드는 항상 마지막 페이지에 추가됨
→ 페이지 분할 발생 없음 → INSERT 성능 최적

업무 식별자 PK (예: 주문번호, UUID)는 값이 랜덤
→ 새 레코드가 중간 페이지에 삽입될 수 있음
→ 페이지 분할 빈번하게 발생 → INSERT 성능 저하

따라서 로그 테이블처럼 INSERT가 압도적으로 많은 테이블은
AUTO_INCREMENT 인조 식별자가 성능에 유리
```

**PK 선택 가이드**

|상황|권장 PK|
|---|---|
|업무 식별자가 명확하고 크기가 작음|업무 식별자를 PK로|
|업무 식별자가 있지만 크기가 크고 세컨더리 인덱스 많음|AUTO_INCREMENT 인조 식별자|
|INSERT 위주 테이블 (로그, 이벤트 등)|AUTO_INCREMENT 인조 식별자|
|PK가 될 만한 업무 컬럼이 없음|AUTO_INCREMENT 인조 식별자|

> **결론:** InnoDB에서 PK는 단순한 식별자가 아니라 **데이터 저장 구조 자체를 결정**한다.  
> PK 설계는 검색 패턴, 세컨더리 인덱스 수, INSERT 빈도를 종합적으로 고려해서 결정해야 한다.

## 8.9 유니크 인덱스 (Unique Index)

유니크 인덱스는 **인덱스라기보다 제약 조건에 가깝다.**  
MySQL에서는 유니크 제약을 설정하면 자동으로 인덱스가 함께 생성되며, 인덱스 없이 유니크 제약만 설정하는 방법은 없다.

**PK vs 유니크 인덱스 비교**

|구분|PK|유니크 인덱스|
|---|---|---|
|NULL 허용|❌|✅ (여러 개 가능)|
|중복 허용|❌|❌ (NULL 제외)|
|테이블당 개수|1개|여러 개 가능|
|클러스터링 키|✅|❌|

```sql
-- NULL은 특정 값이 아니므로 여러 개 저장 가능
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(100),
    nickname VARCHAR(50),
    UNIQUE KEY uq_email (email),
    UNIQUE KEY uq_nickname (nickname)
);

INSERT INTO users VALUES (1, NULL, 'user1');
INSERT INTO users VALUES (2, NULL, 'user2');  -- ✅ NULL 중복 허용
INSERT INTO users VALUES (3, 'test@test.com', 'user3');
INSERT INTO users VALUES (4, 'test@test.com', 'user4');  -- ❌ 중복 값 오류
```

---

### 8.9.1 유니크 인덱스와 일반 세컨더리 인덱스 비교

#### 8.9.1.1 인덱스 읽기

**유니크 인덱스가 일반 인덱스보다 빠르다는 것은 오해다.**

```
[유니크 인덱스 읽기]
인덱스에서 값 탐색 → 1건 찾으면 바로 중단
(유니크하므로 더 이상 같은 값 없음)

[일반 세컨더리 인덱스 읽기]
인덱스에서 값 탐색 → 1건 찾은 후 다음 레코드도 확인
(중복 값이 있을 수 있으므로)

추가 작업: 다음 레코드의 키 값을 CPU에서 비교
→ 디스크 I/O가 아닌 CPU 연산
→ 성능 차이 거의 없음
```

결국 일반 세컨더리 인덱스가 느린 이유는 **인덱스 자체의 특성 때문이 아니라 중복 값이 많아 읽어야 할 레코드 수가 많기 때문**이다.

```sql
-- 두 쿼리의 성능 차이는 인덱스 타입이 아닌 결과 건수에 의해 결정됨

-- 유니크 인덱스 (결과 1건)
SELECT * FROM users WHERE email = 'test@test.com';

-- 일반 인덱스 (결과 1건인 경우 → 성능 차이 없음)
SELECT * FROM orders WHERE status = 'PENDING' LIMIT 1;

-- 일반 인덱스 (결과 수천 건 → 느림, 인덱스 특성 때문이 아님)
SELECT * FROM orders WHERE status = 'PENDING';
```

---

#### 8.9.1.2 인덱스 쓰기

쓰기 성능은 유니크 인덱스가 **일반 세컨더리 인덱스보다 느리다.**

```
[일반 세컨더리 인덱스 쓰기]
1. 인덱스 키 값 계산
2. B-Tree에 키 삽입
   → 즉시 처리 or 체인지 버퍼에 지연 처리 가능

[유니크 인덱스 쓰기]
1. 인덱스 키 값 계산
2. 중복 값 존재 여부 확인  ← 추가 단계
   → 반드시 즉시 디스크에서 확인 (버퍼링 불가)
3. B-Tree에 키 삽입
```

**체인지 버퍼(Change Buffer)를 사용할 수 없는 이유**

```
일반 인덱스:
  INSERT/UPDATE 시 인덱스 변경을 체인지 버퍼에 모아뒀다가
  나중에 디스크에 일괄 반영 가능 (지연 처리)
  → I/O 효율적

유니크 인덱스:
  중복 체크를 위해 현재 인덱스 페이지를 즉시 디스크에서 읽어야 함
  → 체인지 버퍼 사용 불가
  → 즉시 디스크 I/O 발생 → 쓰기 성능 저하
```

**데드락 발생 가능성**

```
유니크 인덱스 쓰기 시 중복 체크 과정에서 쓰기 잠금 필요

트랜잭션 A: users 테이블 email 유니크 인덱스에 쓰기 잠금
트랜잭션 B: 동일 인덱스 페이지에 다른 email 값 삽입 시도
            → 트랜잭션 A의 잠금 해제 대기

여러 트랜잭션이 동시에 유니크 인덱스에 쓰기 시도 시
→ 잠금 경합 빈번 발생
→ 데드락으로 이어질 수 있음
```

---

### 8.9.2 유니크 인덱스 사용 시 주의사항

**같은 컬럼에 유니크 인덱스 + 일반 인덱스 중복 생성 금지**

```sql
-- ❌ 불필요한 중복 인덱스
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(100),
    UNIQUE KEY uq_email (email),   -- 유니크 인덱스
    INDEX idx_email (email)        -- 일반 인덱스 (중복!)
);
-- 유니크 인덱스가 일반 인덱스 역할도 하므로
-- 일반 인덱스는 완전히 불필요, 공간 낭비 + 쓰기 성능 저하

-- ✅ 유니크 인덱스만 생성
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(100),
    UNIQUE KEY uq_email (email)
);
```

**유니크 인덱스 사용 판단 기준**

```
유니크 인덱스를 써야 하는 경우:
  → 데이터 무결성 보장이 반드시 필요한 경우
     (이메일, 주민번호, 사번 등 업무상 중복 불가 컬럼)

유니크 인덱스를 쓰지 않아도 되는 경우:
  → 애플리케이션 레벨에서 중복 체크를 이미 하고 있는 경우
  → INSERT가 매우 빈번한 테이블에서 쓰기 성능이 중요한 경우
  → 성능 향상 목적으로 유니크 인덱스를 추가하려는 경우
     (읽기 성능 차이가 거의 없으므로 의미 없음)
```

> **결론:** 유니크 인덱스는 **데이터 무결성 보장이 목적**이지 성능 향상이 목적이 아니다.  
> 유일성 보장이 꼭 필요한 컬럼에만 사용하고, 성능을 위해 불필요하게 추가하지 않도록 한다.

## 8.10 외래키 (Foreign Key)

```
InnoDB  → 외래키 지원 ✅
MyISAM  → 외래키 미지원 ❌
```

외래키 제약을 설정하면 **연관 테이블의 컬럼에 인덱스가 자동 생성**된다.  
외래키가 존재하는 한 자동 생성된 인덱스는 삭제할 수 없다.

**InnoDB 외래키 관리의 두 가지 핵심 원칙**

```
1. 테이블의 변경(쓰기 잠금)이 발생하는 경우에만 잠금 경합 발생
2. 외래키와 연관되지 않은 컬럼의 변경은 잠금 경합을 발생시키지 않음
```

---

### 8.10.1 자식 테이블의 변경이 대기하는 경우

자식 테이블에서 외래키 값을 변경할 때, **부모 테이블의 해당 레코드에 쓰기 잠금**이 걸려 있으면 대기한다.

```sql
-- 테이블 구조
CREATE TABLE departments (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);

CREATE TABLE employees (
    id INT PRIMARY KEY,
    dept_id INT,
    name VARCHAR(100),
    salary INT,
    FOREIGN KEY (dept_id) REFERENCES departments(id)
);
```

```
[시나리오: 자식 테이블 변경 대기]

트랜잭션 A (먼저 시작):
  UPDATE departments SET name = '개발팀' WHERE id = 1;
  → departments.id=1 레코드에 쓰기 잠금 획득
  (아직 커밋 안 함)

트랜잭션 B:
  UPDATE employees SET dept_id = 1 WHERE id = 100;
  → dept_id=1이 유효한지 확인하기 위해 departments.id=1 읽기 필요
  → 트랜잭션 A가 쓰기 잠금 보유 중
  → 트랜잭션 A 커밋/롤백까지 대기 ⏳

단, 외래키와 무관한 컬럼 변경은 영향 없음:
  UPDATE employees SET salary = 5000 WHERE id = 100;
  → dept_id 변경 없음 → 잠금 경합 없음 ✅
```

### 8.10.2 부모 테이블의 변경 작업이 대기하는 경우

부모 테이블의 레코드를 **삭제**할 때, 해당 FK를 참조하는 자식 레코드에 쓰기 잠금이 걸려 있으면 대기한다.

```
[시나리오: 부모 테이블 삭제 대기]

트랜잭션 A (먼저 시작):
  UPDATE employees SET salary = 6000 WHERE dept_id = 1;
  → employees 레코드들에 쓰기 잠금 획득
  (아직 커밋 안 함)

트랜잭션 B:
  DELETE FROM departments WHERE id = 1;
  → ON DELETE CASCADE로 인해 자식(employees) 레코드도 삭제 필요
  → 트랜잭션 A가 employees 레코드 쓰기 잠금 보유 중
  → 트랜잭션 A 커밋/롤백까지 대기 ⏳
```

**ON DELETE 옵션별 동작**

|옵션|부모 레코드 삭제 시 자식 레코드 처리|
|---|---|
|`RESTRICT` (기본값)|자식 레코드 존재 시 삭제 거부|
|`CASCADE`|자식 레코드도 함께 삭제|
|`SET NULL`|자식 FK 컬럼을 NULL로 변경|
|`NO ACTION`|RESTRICT와 동일|

```sql
-- CASCADE 예시
CREATE TABLE employees (
    id INT PRIMARY KEY,
    dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES departments(id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

-- departments.id=1 삭제 시 dept_id=1인 employees 레코드도 자동 삭제
DELETE FROM departments WHERE id = 1;
```

**잠금 확장으로 인한 동시성 문제**

```
외래키로 인한 잠금은 다른 테이블로 확장됨

부모 테이블 변경
  → 자식 테이블 잠금 확인 필요
  → 자식 테이블 잠금 대기 가능

자식 테이블 변경
  → 부모 테이블 잠금 확인 필요
  → 부모 테이블 잠금 대기 가능

→ 테이블 간 잠금 의존성이 생겨 전체 동시 처리량 감소
→ 최악의 경우 데드락 발생 가능
```

**실무에서의 외래키 사용 전략**

```
물리적 외래키 사용 (DB 레벨 강제)
  장점: 데이터 정합성 DB가 보장
  단점: 잠금 경합, 성능 저하, 스키마 변경 어려움
  적합: 데이터 정합성이 최우선인 소규모 서비스

외래키 없이 애플리케이션 레벨에서 관리
  장점: 잠금 경합 없음, 높은 동시성, 유연한 스키마 변경
  단점: 애플리케이션 버그 시 데이터 정합성 깨질 수 있음
  적합: 대용량 트래픽 서비스, MSA 환경
```

> **결론:** 외래키는 데이터 정합성을 DB 레벨에서 보장해주지만,  
> **잠금이 테이블 간에 확장되어 동시 처리량을 저하**시킬 수 있다.  
> 대용량 트래픽 환경에서는 물리적 외래키 대신 **애플리케이션 레벨에서 정합성을 관리**하는 방식을 많이 선택한다.
