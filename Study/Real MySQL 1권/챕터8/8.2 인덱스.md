### 기본 개념

인덱스는 **읽기 속도를 높이는 대신 쓰기 성능을 희생**하는 자료구조다. 책의 색인(찾아보기)과 같은 원리로, 원하는 데이터의 위치를 빠르게 찾을 수 있게 해준다.

- **인덱스 없음** → 풀 테이블 스캔 (처음부터 끝까지 전부 읽기)
- **인덱스 있음** → 인덱스를 통해 해당 위치로 바로 접근

INSERT/UPDATE/DELETE 시에는 데이터 변경뿐 아니라 인덱스도 함께 갱신해야 하므로, **인덱스가 많을수록 쓰기 비용이 증가**한다.

> 따라서 인덱스 추가 여부는 "쓰기 성능을 어디까지 희생할 수 있는가" vs "읽기 속도를 얼마나 높여야 하는가"를 고려해 결정해야 한다.

### 유니크 인덱스 vs 논-유니크 인덱스

단순히 중복 허용 여부의 차이처럼 보이지만, **옵티마이저 동작 방식에 큰 영향**을 준다.

|유니크 인덱스|논-유니크 인덱스|
|---|---|---|
|중복|불가|허용|
|옵티마이저 동작|1건 찾으면 탐색 즉시 중단|조건에 맞는 모든 레코드 탐색|
|대표 사용 예|PK, UNIQUE 제약 컬럼|일반 검색 조건 컬럼|

유니크 인덱스는 "이 조건엔 결과가 최대 1건"임을 옵티마이저가 알기 때문에, 첫 번째 일치 레코드를 찾는 순간 추가 탐색을 중단한다. 이것이 **유니크 인덱스가 동등 조건(=) 조회에서 더 효율적인 이유**다.

### 인덱스 종류

**역할(용도)별 분류**

|종류|설명|
|---|---|
|B-Tree 인덱스|가장 일반적. 범위 검색, 정렬, 동등 비교 모두 지원|
|전문 검색 인덱스 (Full-Text)|문장/문서 내 키워드 검색에 특화 (`MATCH ... AGAINST`)|
|공간 검색 인덱스 (Spatial)|좌표, 지도 등 공간 데이터 검색에 특화 (`ST_` 함수군)|
|해시 인덱스|동등 비교(=)에 특화, 범위 검색 불가. Memory 엔진에서 사용|

MySQL을 일반적으로 사용하는 수준에서는 **B-Tree 인덱스**를 깊이 이해하는 것이 핵심이고, 전문/공간 인덱스는 필요할 때 찾아보는 수준으로 충분하다.
