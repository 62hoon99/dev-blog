## 인덱스 있을 때

### where 조건에 포함되는 두 컬럼을 기준으로 복합 인덱스

```
-- 복합 인덱스 (추천)
CREATE INDEX idx_department_status ON employees (department, status);
```

#### 실행계획
- index는 탔지만 filesort를 하는 걸 확인할 수 있다.
- type이 ref로 바뀌었다.

**항목별 분석**

| 항목         | 값                       | 해석                       |
| ---------- | ----------------------- | ------------------------ |
| `type`     | `ref`                   | 인덱스 정상적으로 탐 ✅            |
| `key`      | `idx_department_status` | 예상대로 인덱스 사용 ✅            |
| `rows`     | 155,290                 | 인덱스 타고도 **15만 행** 읽음 ⚠️  |
| `filtered` | 100%                    | WHERE 조건은 완벽히 필터링 ✅      |
| `Extra`    | `Using filesort`        | **메모리/디스크에서 별도 정렬 발생** ❌ |


# 실습 2

## 커버링 인덱스

```
mysql> EXPLAIN SELECT department, status, salary FROM employees  WHERE department = '개발팀' AND status = 'ACTIVE'  ORDER BY salary DESC LIMIT 50 \G;

*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ref
possible_keys: idx_department_status,idx_department_status_salary
          key: idx_department_status_salary
      key_len: 164
          ref: const,const
         rows: 158192
     filtered: 100.00
        Extra: Using index
1 row in set, 1 warning (0.003 sec)
```

idx_department_status_salary 인덱스에 포함된 컬럼에 대해서만 조회를 하니 Extra 에 Using index 가 나오는 것을 볼 수 있다.

### **자주 보이는 Extra 값들**

**✅ 좋은 것들**

| 값                       | 의미                                               |
| ----------------------- | ------------------------------------------------ |
| `NULL`                  | 특이사항 없음, 정상                                      |
| `Using index`           | 커버링 인덱스 → 테이블 안 읽고 인덱스만으로 해결                     |
| `Using index condition` | ICP(Index Condition Pushdown) → 스토리지 엔진 레벨에서 필터링 |

**⚠️ 주의해야 할 것들**

| 값                 | 의미                               |
| ----------------- | -------------------------------- |
| `Using filesort`  | 인덱스로 정렬 못해서 별도 정렬 발생             |
| `Using temporary` | 임시 테이블 생성 (GROUP BY, DISTINCT 등) |
| `Using where`     | 인덱스 후 MySQL 서버 레벨에서 추가 필터링       |

**❌ 나쁜 것들**

| 값                                        | 의미                                    |
| ---------------------------------------- | ------------------------------------- |
| `Using filesort` + `Using temporary`     | 동시에 뜨면 심각, GROUP BY + ORDER BY 최적화 필요 |
| `Using join buffer (Block Nested Loop)`  | 조인 시 인덱스 없음, 버퍼로 처리                   |
| `Using join buffer (Batched Key Access)` | BKA 사용 중, MRR 활성화 여부 확인               |

**자주 보이는 조합 패턴**

```
Using where; Using filesort          -- WHERE 후 정렬 못함
Using index; Using filesort          -- 커버링 인덱스 탔지만 정렬은 별도
Using temporary; Using filesort      -- GROUP BY 최적화 필요
Using index condition; Using where   -- ICP 적용됐지만 추가 필터 있음
```


## 실습3

### 문제1 (인덱스 컬럼에 함수 적용)

```ALTER TABLE employees ADD INDEX idx_join_date (join_date);``` 인덱스가 걸려있음에도 첫번째 쿼리는 Using where 즉 인덱스 후 MySQL 서버 레벨에서 추가 필터링 되는 것을 볼 수 있다.

```
mysql> EXPLAIN SELECT * FROM employees WHERE YEAR(join_date) = 2023 \G;
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ALL
possible_keys: NULL
          key: NULL
      key_len: NULL
          ref: NULL
         rows: 994462
     filtered: 100.00
        Extra: Using where
1 row in set, 1 warning (0.002 sec)


mysql> EXPLAIN SELECT * FROM employees WHERE join_date >= '2023-01-01' AND join_date < '2024-01-01' \G;
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: range
possible_keys: idx_join_date
          key: idx_join_date
      key_len: 3
          ref: NULL
         rows: 80176
     filtered: 100.00
        Extra: Using index condition
1 row in set, 1 warning (0.003 sec)
```

### 인덱스를 못 타는 이유

**인덱스 컬럼에 함수를 씌우면 인덱스를 못 탄다.**

**YEAR(join_date) = 2023 → 풀스캔**

```sql
WHERE YEAR(join_date) = 2023
```

인덱스는 `join_date` 값 자체로 정렬되어 있는데, `YEAR(join_date)`는 **가공된 값**이다.

MySQL 입장에서는:

```
YEAR('2023-01-01') = 2023  ✅
YEAR('2023-06-15') = 2023  ✅
YEAR('2022-12-31') = 2023  ❌
```

어떤 `join_date`가 `YEAR() = 2023`을 만족하는지 **인덱스만 보고 알 수 없어요.**  
→ 결국 전체 행을 꺼내서 하나하나 `YEAR()` 계산 → **풀스캔 (type: ALL)**

**join_date >= '2023-01-01' AND join_date < '2024-01-01' → 인덱스**

```sql
WHERE join_date >= '2023-01-01' AND join_date < '2024-01-01'
```

`join_date` 원본값 그대로 비교하니까 인덱스 B-Tree에서 **범위 탐색** 가능하다.

```
... 2022-12-31 | 2023-01-01 ~ 2023-12-31 | 2024-01-01 ...
                 ↑ 여기서 ←————————————→ 여기까지 스캔
```

→ **range 스캔 (type: range)**

**일반 원칙**

인덱스 컬럼에 **함수, 연산, 형변환** 씌우면 전부 인덱스 무력화된다.

```sql
WHERE YEAR(join_date) = 2023        -- ❌ 함수
WHERE join_date + 1 > '2023-01-01' -- ❌ 연산
WHERE join_date = 20230101          -- ❌ 암묵적 형변환 (문자열 vs 숫자)
WHERE DATE(join_date) = '2023-01-01'-- ❌ 함수

WHERE join_date >= '2023-01-01'     -- ✅
WHERE join_date BETWEEN '2023-01-01' AND '2023-12-31' -- ✅
```

### 문제2

```ALTER TABLE employees ADD INDEX idx_emp_no (emp_no);``` 인덱스가 걸려있음에도 첫번째 쿼리는 Using where 즉 인덱스 후 MySQL 서버 레벨에서 추가 필터링 되는 것을 볼 수 있다.

```
mysql> EXPLAIN SELECT * FROM employees WHERE emp_no = 1234567 \G;
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ALL
possible_keys: idx_emp_no
          key: NULL
      key_len: NULL
          ref: NULL
         rows: 994462
     filtered: 10.00
        Extra: Using where
1 row in set, 3 warnings (0.003 sec)

ERROR:
No query specified

mysql> EXPLAIN SELECT * FROM employees WHERE emp_no = 'EMP-1234567' \G;
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ref
possible_keys: idx_emp_no
          key: idx_emp_no
      key_len: 82
          ref: const
         rows: 1
     filtered: 100.00
        Extra: NULL
```


### 인덱스를 못 타는 이유

**암묵적 형변환** 때문이다.

**emp_no 컬럼이 VARCHAR인데 숫자로 비교했다.**

```sql
WHERE emp_no = 1234567       -- 숫자 (INT)
WHERE emp_no = 'EMP-1234567' -- 문자열 (VARCHAR) ✅
```

MySQL이 타입을 맞추려고 내부적으로 이렇게 변환해요:

```sql
-- 실제로 이렇게 동작
WHERE CAST(emp_no AS SIGNED) = 1234567
```

컬럼에 함수/변환이 씌워지는 순간 → **인덱스 무력화** (이전에 `YEAR()` 예시랑 같은 원리)

**흥미로운 점**
`possible_keys`에는 `idx_emp_no`가 있어요. 인덱스 존재는 알지만, 형변환 때문에 **쓸 수 없다고 판단**해서 `key = NULL`이다.

**반대 방향은 괜찮다.**

```sql
-- INT 컬럼에 문자열 비교 → MySQL이 문자열을 숫자로 변환 (컬럼은 그대로)
WHERE age = '30'   -- age가 INT면 인덱스 탐 ✅

-- VARCHAR 컬럼에 숫자 비교 → 컬럼 전체를 숫자로 변환
WHERE emp_no = 30  -- emp_no가 VARCHAR면 인덱스 못 탐 ❌
```

**컬럼이 변환되면 인덱스 죽고, 값이 변환되면 괜찮다.**

> VARCHAR 컬럼에 숫자 비교하기 전에 VARCHAR 컬럼이면 30을 문자로 바꾸고 비교하면 될 것 같은데 그건 안된다고 한다. 잘 이해가 가지는 않는다.
