## 실습 1 — 복합 인덱스 설계와 filesort 제거

**시나리오:** 현재 재직 중인 개발팀 직원을 연봉 높은 순으로 조회

```sql
SELECT id, emp_no, name, position, salary
FROM employees
WHERE department = '개발팀'
  AND status = 'ACTIVE'
ORDER BY salary DESC
LIMIT 50;
```

---

### 인덱스 없을 때

**실행 계획**

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ALL
possible_keys: NULL
          key: NULL
      key_len: NULL
          ref: NULL
         rows: 994462
     filtered: 1.00
        Extra: Using where; Using filesort
```

**소요 시간:** 272ms

`type: ALL` — 풀 테이블 스캔이 발생하고 있다. `Using filesort`까지 함께 뜨는 것을 볼 수 있다.

---

### 인덱스 추가 (1단계) — WHERE 조건 컬럼 기준 복합 인덱스

```sql
CREATE INDEX idx_department_status ON employees (department, status);
```

**실행 계획**

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ref
possible_keys: idx_department_status
          key: idx_department_status
      key_len: 164
          ref: const,const
         rows: 155290
     filtered: 100.00
        Extra: Using filesort
```

**소요 시간:** 210ms

`type: ref`로 바뀌며 인덱스를 타기 시작했다. 하지만 `Using filesort`가 여전히 남아 있다.

**원인:** 인덱스가 `(department, status)`까지만 커버하고 `salary`는 포함하지 않기 때문에, `ORDER BY salary DESC`를 처리할 때 MySQL이 155,290건을 읽어온 뒤 메모리/디스크에서 별도로 정렬한다.

---

### 인덱스 추가 (2단계) — 정렬 컬럼까지 포함한 복합 인덱스

```sql
CREATE INDEX idx_department_status_salary ON employees (department, status, salary DESC);
```

**실행 계획**

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ref
possible_keys: idx_department_status,idx_department_status_salary
          key: idx_department_status_salary
      key_len: 164
          ref: const,const
         rows: 155290
     filtered: 100.00
        Extra: NULL
```

**소요 시간:** 3ms

`Using filesort`가 사라졌다. `salary DESC`까지 인덱스 안에서 처리되면서 별도 정렬 단계가 제거됐다. 210ms → 3ms로 엄청나게 줄었다.

---

### 항목별 비교 정리

|항목|인덱스 없음|`(dept, status)`|`(dept, status, salary)`|
|---|---|---|---|
|type|ALL|ref|ref|
|key|NULL|idx_department_status|idx_department_status_salary|
|Extra|Using where; Using filesort|Using filesort|NULL|
|소요 시간|272ms|210ms|3ms|

## 실습 2 — 커버링 인덱스

실습 1에서 만든 `idx_department_status_salary` 인덱스를 그대로 두고 SELECT 절을 바꿔가며 실행 계획을 비교한다.

```sql
-- 인덱스 컬럼만 SELECT
EXPLAIN SELECT department, status, salary
FROM employees
WHERE department = '개발팀'
  AND status = 'ACTIVE'
ORDER BY salary DESC
LIMIT 50\G;
```

**실행 계획**

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ref
possible_keys: idx_department_status,idx_department_status_salary
          key: idx_department_status_salary
      key_len: 164
          ref: const,const
         rows: 158192
     filtered: 100.00
        Extra: Using index
```

`idx_department_status_salary` 인덱스에 포함된 컬럼(`department`, `status`, `salary`)에 대해서만 조회하니 `Extra: Using index`가 나오는 것을 볼 수 있다.

**커버링 인덱스란?** SELECT 절에서 요청한 컬럼이 모두 인덱스 안에 포함되어 있을 때, 테이블 본체(Clustered Index)를 전혀 읽지 않고 인덱스만으로 결과를 반환하는 것이다. 불필요한 I/O가 사라지기 때문에 성능이 크게 향상된다.

반면 `SELECT *`처럼 인덱스에 없는 컬럼이 포함되면 테이블을 다시 읽어야 하므로 `Using index`가 사라진다.

---

### 자주 보이는 Extra 값 정리

**✅ 좋은 것들**

|값|의미|
|---|---|
|`NULL`|특이사항 없음, 정상|
|`Using index`|커버링 인덱스 → 테이블 안 읽고 인덱스만으로 해결|
|`Using index condition`|ICP(Index Condition Pushdown) → 스토리지 엔진 레벨에서 필터링|

**⚠️ 주의해야 할 것들**

|값|의미|
|---|---|
|`Using filesort`|인덱스로 정렬 못해서 별도 정렬 발생|
|`Using temporary`|임시 테이블 생성 (GROUP BY, DISTINCT 등)|
|`Using where`|인덱스 후 MySQL 서버 레벨에서 추가 필터링|

**❌ 나쁜 것들**

|값|의미|
|---|---|
|`Using filesort` + `Using temporary`|동시에 뜨면 심각, GROUP BY + ORDER BY 최적화 필요|
|`Using join buffer (Block Nested Loop)`|조인 시 인덱스 없음, 버퍼로 처리|
|`Using join buffer (Batched Key Access)`|BKA 사용 중, MRR 활성화 여부 확인|

**자주 보이는 조합 패턴**

```
Using where; Using filesort          -- WHERE 후 정렬 못함
Using index; Using filesort          -- 커버링 인덱스 탔지만 정렬은 별도
Using temporary; Using filesort      -- GROUP BY 최적화 필요
Using index condition; Using where   -- ICP 적용됐지만 추가 필터 있음
```

## 실습 3 — 인덱스를 무력화하는 쿼리 패턴

### 문제 1 — 인덱스 컬럼에 함수 적용

```sql
ALTER TABLE employees ADD INDEX idx_join_date (join_date);

-- 비교 대상 ①
SELECT * FROM employees WHERE YEAR(join_date) = 2023;

-- 비교 대상 ②
SELECT * FROM employees WHERE join_date >= '2023-01-01' AND join_date < '2024-01-01';
```

**실행 계획 비교**

```
-- ① YEAR(join_date) = 2023
type: ALL / key: NULL / Extra: Using where

-- ② join_date >= '2023-01-01' AND join_date < '2024-01-01'
type: range / key: idx_join_date / Extra: Using index condition
```

**인덱스를 못 타는 이유**

인덱스는 `join_date` 원본값을 기준으로 정렬되어 있다. 그런데 `YEAR(join_date)`는 가공된 값이다. MySQL 입장에서는 어떤 `join_date`가 `YEAR() = 2023`을 만족하는지 인덱스만 보고 알 수 없기 때문에, 전체 행을 꺼내서 하나하나 `YEAR()`를 계산하는 풀스캔이 발생한다.

반면 `join_date >= '2023-01-01'`은 원본값 그대로 비교하므로 B-Tree에서 범위 탐색이 가능하다.

**일반 원칙: 인덱스 컬럼에 함수, 연산, 형변환을 씌우면 인덱스가 무력화된다.**

```sql
WHERE YEAR(join_date) = 2023           -- ❌ 함수
WHERE join_date + 1 > '2023-01-01'     -- ❌ 연산
WHERE join_date = 20230101             -- ❌ 암묵적 형변환
WHERE DATE(join_date) = '2023-01-01'   -- ❌ 함수

WHERE join_date >= '2023-01-01'        -- ✅
WHERE join_date BETWEEN '2023-01-01' AND '2023-12-31'  -- ✅
```

### 문제 2 — 암묵적 형변환

```sql
ALTER TABLE employees ADD INDEX idx_emp_no (emp_no);

-- 비교 대상 ①
SELECT * FROM employees WHERE emp_no = 1234567;

-- 비교 대상 ②
SELECT * FROM employees WHERE emp_no = 'EMP-1234567';
```

**실행 계획 비교**

```
-- ① emp_no = 1234567
type: ALL / possible_keys: idx_emp_no / key: NULL / Extra: Using where

-- ② emp_no = 'EMP-1234567'
type: ref / key: idx_emp_no / rows: 1 / Extra: NULL
```

**인덱스를 못 타는 이유**

`emp_no`는 VARCHAR 컬럼인데 숫자로 비교했기 때문에 암묵적 형변환이 발생한다. MySQL이 타입을 맞추려고 내부적으로 아래처럼 동작한다.

```sql
WHERE CAST(emp_no AS SIGNED) = 1234567
```

컬럼 자체에 변환이 씌워지는 순간 인덱스가 무력화된다. `YEAR()` 예시와 같은 원리다.

흥미로운 점은 `possible_keys`에 `idx_emp_no`가 있다는 것이다. 인덱스의 존재는 알지만, 형변환 때문에 쓸 수 없다고 판단해서 `key: NULL`이 된다.

**반대 방향은 괜찮은 이유**

```sql
WHERE age = '30'   -- age가 INT → '30'을 30으로 변환, 변환 결과가 유일 → 인덱스 탐 ✅
WHERE emp_no = 30  -- emp_no가 VARCHAR → 30을 문자열로 변환해야 하는데, '30'인지 'EMP-30'인지 결정 불가 → 인덱스 못 탐 ❌
```

핵심은 **변환 후 값이 유일하게 결정되느냐**이다. 숫자 → 문자열 변환은 어떤 포맷으로 저장되어 있는지 MySQL이 알 수 없어서 인덱스 탐색 위치를 특정할 수 없다. 반대 방향인 문자열 → 숫자는 변환 결과가 하나로 결정되므로 인덱스를 탈 수 있다.

**결론: 컬럼이 변환되면 인덱스가 죽고, 값이 변환되면 괜찮다.**

## 실습 4 — DEPENDENT SUBQUERY 탐지와 개선

**시나리오:** 자기 부서 평균 연봉보다 높은 직원 조회

두 쿼리의 결과는 동일하지만 실행 시간 차이가 어마어마하다.

```sql
-- 쿼리 A
SELECT id, name, department, salary
FROM employees e1
WHERE salary > (
    SELECT AVG(salary)
    FROM employees e2
    WHERE e2.department = e1.department
);

-- 쿼리 B
SELECT e.id, e.name, e.department, e.salary
FROM employees e
INNER JOIN (
    SELECT department, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department
) dept_avg ON e.department = dept_avg.department
WHERE e.salary > dept_avg.avg_salary;
```

---

**핵심: 서브쿼리 실행 횟수가 다르다**

**쿼리 A — DEPENDENT SUBQUERY**

`e1.department`를 참조하기 때문에 바깥 쿼리 행마다 서브쿼리가 실행된다. 서브쿼리가 자기 혼자 실행될 수 없고 바깥 쿼리의 현재 행 값에 의존해야 실행 가능한 구조이기 때문이다.

```
e1 행 1번 → AVG(salary) 계산 (department = '개발팀')
e1 행 2번 → AVG(salary) 계산 (department = '개발팀')  ← 같은 계산 반복
e1 행 3번 → AVG(salary) 계산 (department = '마케팅팀')
...
총 994,462번 실행
```

**쿼리 B — DERIVED (파생 테이블)**

서브쿼리를 먼저 한 번만 실행해서 결과를 임시 테이블로 만든다.

```
dept_avg 한 번 계산:
  개발팀    → AVG = 650만
  마케팅팀  → AVG = 580만
  ...
그 다음 e 테이블이랑 JOIN
총 1번 실행
```

**실행 횟수 비교**

||쿼리 A|쿼리 B|
|---|---|---|
|서브쿼리 실행 횟수|994,462번|1번|
|select_type|`DEPENDENT SUBQUERY`|`DERIVED`|
|구조|행마다 의존|먼저 계산 후 JOIN|

**DEPENDENT SUBQUERY가 되는 조건**

WHERE 절에 서브쿼리를 쓴다고 무조건 DEPENDENT SUBQUERY가 되는 건 아니다. **바깥 쿼리의 컬럼을 참조하느냐**가 기준이다.

|조건|select_type|
|---|---|
|서브쿼리가 바깥 컬럼 참조 O|`DEPENDENT SUBQUERY` (N번 실행)|
|서브쿼리가 바깥 컬럼 참조 X|`SUBQUERY` (1번 실행)|
|FROM 절 서브쿼리|`DERIVED` (1번 실행)|

EXPLAIN에서 `DEPENDENT SUBQUERY`가 뜨는 순간 "이거 N번 실행되겠다"를 바로 알아챌 수 있다. 실행 계획 볼 때 가장 먼저 체크해야 할 위험 신호다.

## 실습 5 — 실행 계획의 rows와 filtered 해석

```sql
EXPLAIN SELECT * FROM employees
WHERE department = '개발팀'
  AND status = 'ACTIVE'
  AND salary > 5000\G;
```

**실행 계획**

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: employees
   partitions: NULL
         type: ref
possible_keys: idx_department_status,idx_department_status_salary,idx_department,idx_dept_status
          key: idx_department_status
      key_len: 164
          ref: const,const
         rows: 155290
     filtered: 33.33
        Extra: Using where
```

**실제 결과 확인**

```sql
SELECT COUNT(*) FROM employees WHERE department = '개발팀' AND status = 'ACTIVE' AND salary > 5000;
-- COUNT(*): 44057
```

---

### rows와 filtered의 의미

**rows: 155,290**

MySQL이 인덱스로 읽을 것으로 예상하는 행 수다. 실제 값이 아닌 통계 기반 추정치다. 이 쿼리에서는 `idx_department_status`로 `department = '개발팀' AND status = 'ACTIVE'` 조건을 처리해서 155,290건을 읽는다고 예상한 것이다.

**filtered: 33.33**

rows에서 읽은 행 중 나머지 WHERE 조건을 통과할 비율(%)이다. 인덱스가 `department + status`까지만 커버하고, `salary > 5000`은 인덱스 밖 조건이라 MySQL 서버 레벨에서 추가 필터링한다 (`Extra: Using where`).

```
155,290 (rows) × 33.33% (filtered) = 약 51,762건 (추정)
실제 결과: 44,057건
```

추정치라 실제랑 완전히 일치하지는 않는다. 옵티마이저는 이 값을 기반으로 조인 순서, 인덱스 선택 등을 결정한다.

**filtered가 낮을수록 비효율**

|filtered|의미|
|---|---|
|100%|읽은 행 전부 결과에 포함|
|33.33%|읽은 행의 2/3는 버림 ⚠️|
|10% 이하|인덱스 개선 필요 ❌|

---

### salary 조건은 어느 단계에서 처리되는가?

MySQL은 스토리지 엔진과 서버 레이어 두 단계로 나뉜다.

```
[스토리지 엔진 레이어]
idx_department_status로 department = '개발팀' AND status = 'ACTIVE' 필터링
→ 155,290건 읽어서 서버로 넘김

[MySQL 서버 레이어]
salary > 5000 조건으로 추가 필터링  ← Using where가 이걸 의미
→ 44,057건만 최종 반환
```

`salary`는 인덱스에 없으니까 테이블에서 실제 행을 읽어온 뒤 서버 레이어에서 처리된다.

---

### 인덱스를 `(department, status, salary)`로 바꾸면?

```sql
CREATE INDEX idx_department_status_salary ON employees (department, status, salary DESC);
```

`salary > 5000`까지 인덱스 안에서 처리 가능해진다.

```
[스토리지 엔진 레이어]
세 조건 모두 인덱스로 필터링
→ 처음부터 44,057건만 읽음

[MySQL 서버 레이어]
추가 필터링 없음
```

||`(department, status)`|`(department, status, salary)`|
|---|---|---|
|rows|155,290|약 44,057|
|filtered|33.33%|100%에 가까워짐|
|Extra|`Using where`|`Using index condition`|

읽는 시점에 이미 세 조건을 모두 만족한 행만 가져오니까 서버 레이어에서 버려지는 행이 없어진다. **filtered가 100%에 가까울수록 읽은 행을 버리지 않는 효율적인 인덱스**다.
