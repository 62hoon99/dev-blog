## 4.2.1 프라이머리 키에 의한 클러스터링

InnoDB의 모든 테이블은 기본적으로 **프라이머리 키(Primary Key)를 기준으로 클러스터링**되어 저장된다. 즉, 프라이머리 키 값의 순서대로 데이터가 물리적으로 정렬되어 디스크에 저장된다.

> **클러스터링 인덱스(Clustered Index)** 란, 테이블 자체가 인덱스 구조로 저장되는 방식이다. InnoDB에서는 프라이머리 키가 곧 클러스터링 인덱스이다.

이로 인해 프라이머리 키를 이용한 **범위 스캔(Range Scan)** 은 다른 인덱스 방식보다 훨씬 빠르게 처리될 수 있다. 데이터가 이미 물리적으로 정렬되어 있으므로, 연속된 범위를 읽을 때 I/O 비용이 크게 줄어든다.

### 세컨더리 인덱스와의 관계

- 세컨더리 인덱스의 리프 노드에는 실제 레코드 주소가 아닌 **프라이머리 키 값**이 저장된다.
- 따라서 세컨더리 인덱스를 통해 레코드를 조회하면, 최종적으로 클러스터링 인덱스(프라이머리 키)를 **한 번 더 탐색**해야 한다.
- 이를 **이중 탐색(Double Lookup)** 이라고도 하며, 세컨더리 인덱스가 여러 개 존재하더라도 결국 클러스터링 인덱스를 경유하게 된다.

>  **팁**: 단조 증가(AUTO_INCREMENT)하는 숫자형 컬럼을 프라이머리 키로 사용하면 클러스터링 인덱스의 페이지 분할을 최소화할 수 있어 성능에 유리하다.

## 4.2.2 외래 키(Foreign Key) 지원

InnoDB는 **외래 키(Foreign Key)** 제약을 지원한다. 외래 키는 테이블 간의 참조 무결성을 데이터베이스 수준에서 보장해주는 기능이다.

### 실무에서의 외래 키 사용 현황

- **서비스 운영 환경(Production)** 에서는 운영 편의성 문제로 외래 키를 사용하지 않는 경우도 많다.
- **개발 환경** 에서는 테이블 간 관계의 가이드라인 역할을 하므로 유용하게 활용할 수 있다.

### 잠금(Lock) 전파 및 데드락 주의

외래 키가 설정된 테이블에서 데이터를 변경(INSERT, UPDATE, DELETE)하면, 부모 테이블과 자식 테이블 모두에 데이터가 있는지 확인하는 체크 작업이 수행된다. 이 과정에서 **잠금이 관련 테이블로 전파**될 수 있다.

> **주의**: 잠금 전파로 인해 여러 트랜잭션이 서로의 잠금을 대기하게 되면 **데드락(Deadlock)** 이 발생할 수 있다. 외래 키가 많은 구조에서는 특히 주의가 필요하다.

### foreign_key_checks 시스템 변수

수동으로 대량 데이터 작업을 수행해야 하는 경우, 외래 키 검사를 임시로 비활성화할 수 있다.

```sql
SET foreign_key_checks = OFF;
-- 데이터 작업 수행
SET foreign_key_checks = ON;
```

>  **주의**: OFF 상태에서 작업할 때는 반드시 **외래 키 제약 조건을 직접 준수**해야 한다. 외래 키 무결성이 깨진 상태로 다시 ON으로 전환하면, 이후 데이터 정합성 문제가 발생할 수 있다.

## 4.2.3 MVCC (Multi-Version Concurrency Control)

MVCC는 레코드 레벨의 트랜잭션을 지원하는 DBMS에서 제공하는 기능으로, 가장 큰 목적은 **잠금 없이 일관된 읽기(Non-locking Consistent Read)** 를 제공하는 것이다.

> **멀티 버전(Multi-Version)** 이란, 하나의 레코드에 대해 여러 버전이 동시에 존재하며 트랜잭션의 격리 수준과 상황에 따라 어떤 버전이 읽힐지 결정되는 방식이다.

InnoDB는 **언두 로그(Undo Log)** 를 이용해 MVCC를 구현한다. 동작 방식은 다음과 같다.

- 트랜잭션이 레코드를 변경하면, 변경 전 데이터를 언두 로그에 백업한다.
- 다른 트랜잭션이 해당 레코드를 읽을 때, **격리 수준에 따라** 실제 데이터 또는 언두 로그의 이전 버전 중 하나를 반환한다.
- 이를 통해 읽기 작업이 쓰기 작업의 잠금 해제를 기다리지 않아도 된다.

### 언두 로그 데이터의 삭제

언두 영역의 백업 데이터는 즉시 삭제되지 않는다. **해당 데이터를 필요로 하는 트랜잭션이 더 이상 없을 때** 비로소 삭제된다.

> ⚠️ **주의**: 장시간 실행되는 트랜잭션이 있으면 언두 로그가 계속 쌓여 스토리지를 과도하게 사용하게 될 수 있다.

---

## 4.2.4 잠금 없는 일관된 읽기 (Non-Locking Consistent Read)

트랜잭션 격리 수준이 **SERIALIZABLE이 아닌 READ COMMITTED 또는 REPEATABLE READ** 인 경우, INSERT와 연결되지 않은 단순 읽기(SELECT) 작업은 다른 트랜잭션의 변경 작업과 관계없이 **잠금을 기다리지 않고 즉시 실행**된다.

어떤 트랜잭션이 데이터를 변경 중이더라도(아직 커밋하지 않았더라도) 다른 사용자의 SELECT 작업을 방해하지 않는다. 이를 **'잠금 없는 일관된 읽기'** 라고 한다.

> InnoDB는 변경되기 전의 데이터를 읽기 위해 **언두 로그(Undo Log)** 를 사용한다. 이것이 MVCC와 잠금 없는 일관된 읽기의 핵심 메커니즘이다.

### 격리 수준별 동작

|격리 수준|읽기 동작|
|---|---|
|READ COMMITTED|커밋된 가장 최신 버전의 데이터를 읽는다|
|REPEATABLE READ|트랜잭션이 시작된 시점의 스냅샷을 기준으로 데이터를 읽는다|
|SERIALIZABLE|읽기 작업도 공유 잠금을 획득하므로, 잠금 없는 일관된 읽기가 적용되지 않는다|

---

## 4.2.5 자동 데드락 감지 (Automatic Deadlock Detection)

InnoDB 스토리지 엔진은 내부적으로 잠금의 교착 상태(Deadlock)를 주기적으로 감지하는 **데드락 감지 스레드**를 별도로 운영한다.

### 데드락 감지 및 처리 방식

- 교착 상태에 빠진 트랜잭션들 중, **언두 로그의 양이 더 적은(롤백 비용이 적은) 트랜잭션**을 강제 종료(롤백)한다.
- 언두 로그의 양이 많은 트랜잭션은 롤백 비용이 크므로, 반대 트랜잭션을 종료시켜 데드락을 해소한다.

### innodb_table_locks 설정

InnoDB는 기본적으로 상위 레이어인 MySQL 엔진에서 관리하는 **테이블 수준의 잠금을 인식하지 못한다**. `innodb_table_locks` 시스템 변수를 활성화(ON)하면 InnoDB가 테이블 잠금도 인식할 수 있게 된다.

> `innodb_table_locks`는 기본적으로 활성화(ON)되어 있으며, `LOCK TABLES` 명령 등을 사용할 때 데드락 감지가 정확하게 동작하도록 활성화 상태를 유지하는 것이 권장된다.

### 데드락 감지 스레드 비활성화 시 주의사항

동시 처리 스레드가 매우 많은 고부하 환경에서는 데드락 감지 스레드가 성능에 영향을 줄 수 있어 비활성화하는 경우도 있다.

> **주의**: 데드락 감지 스레드를 비활성화하면, 데드락 상황에서 어떤 트랜잭션도 자동으로 종료되지 않아 **무한 대기 상태**에 빠질 수 있다.

이 경우 반드시 `innodb_lock_wait_timeout` 시스템 변수를 함께 설정해야 한다. 일정 시간이 지나면 자동으로 요청이 실패하고 에러를 반환하게 된다.

```ini
# 데드락 감지 비활성화 시 권장 설정
innodb_deadlock_detect = OFF
innodb_lock_wait_timeout = 50  # 기본값(50초) 이하로 설정 권장
```

> **권장사항**: 자동 데드락 감지 스레드를 비활성화한 경우, `innodb_lock_wait_timeout` 값을 기본값인 **50초 이하**로 줄여서 설정하는 것이 권장된다.


# 4.2.6 InnoDB의 자동화된 장애 복구

> InnoDB는 MySQL이 비정상적으로 종료되더라도 재시작 시 데이터 일관성을 자동으로 복구하도록 설계되어 있다. 이것이 InnoDB의 **자동화된 장애 복구(Automatic Crash Recovery)** 기능이다.

## 자동 복구의 원리

MySQL(InnoDB)은 모든 데이터 변경 사항을 즉시 디스크의 데이터 파일에 쓰지 않는다. 변경 내용을 먼저 메모리(Buffer Pool)에 기록하고, 이후 백그라운드로 디스크에 반영하는 구조를 가진다. 따라서 **MySQL이 갑자기 종료**되면, 메모리에만 있던 변경 내용이 디스크에 반영되지 않은 채로 유실될 수 있다.

InnoDB는 이 문제를 해결하기 위해 두 가지 로그를 활용한다.

### Redo Log (리두 로그)

- 데이터 변경이 발생하면, 실제 데이터 파일에 쓰기 전에 **Redo Log에 먼저 기록**한다. (Write-Ahead Logging, WAL)
- MySQL 재시작 시, Redo Log를 읽어 **디스크에 반영되지 못한 커밋된 트랜잭션을 다시 적용**한다. 이 과정을 **Roll Forward**라고 한다.
- 즉, "커밋은 됐지만 아직 디스크에 안 쓴 것"을 복구하는 역할이다.

### Undo Log (언두 로그)

- Roll Forward 이후, **커밋되지 않은 채로 종료된 트랜잭션**이 있다면 Undo Log를 이용해 해당 변경을 **롤백**한다.
- "작업 중이었지만 완료되지 못한 것"을 되돌리는 역할이다.

### 복구 흐름 요약

```
MySQL 재시작
    │
    ▼
① Redo Log 확인
    → 커밋됐지만 디스크에 미반영된 트랜잭션 → Roll Forward (재적용)
    │
    ▼
② Undo Log 확인
    → 커밋되지 않은 미완료 트랜잭션 → Rollback (되돌리기)
    │
    ▼
③ 정상 서비스 재개
```

---
### 복구 레벨별 상세 설명

| 레벨  | 이름                           | 동작                                                                    | 위험도   |
| --- | ---------------------------- | --------------------------------------------------------------------- | ----- |
| `0` | 기본값                          | 정상 시작                                                                 | —     |
| `1` | `SRV_FORCE_IGNORE_CORRUPT`   | 손상된 페이지를 감지해도 서버를 계속 실행. 손상된 인덱스/페이지를 건너뛰며 SELECT 시도                  | 낮음    |
| `2` | `SRV_FORCE_NO_BACKGROUND`    | 마스터 스레드 및 Purge 스레드 실행 중단                                             | 낮음    |
| `3` | `SRV_FORCE_NO_TRX_UNDO`      | 미완료 트랜잭션에 대한 롤백(Undo) 수행 안 함                                          | 보통    |
| `4` | `SRV_FORCE_NO_IBUF_MERGE`    | Insert Buffer 병합 작업 수행 안 함. 테이블 통계 계산 안 함. **데이터 파일 영구 손상 가능**        | 높음    |
| `5` | `SRV_FORCE_NO_UNDO_LOG_SCAN` | Undo Log를 검사하지 않음. 미완료 트랜잭션도 커밋된 것으로 처리. **데이터 파일 영구 손상 가능**          | 높음    |
| `6` | `SRV_FORCE_NO_LOG_REDO`      | Redo Log의 Roll Forward를 수행하지 않음. B-tree 등 데이터 구조 추가 손상 가능. **최후의 수단** | 매우 높음 |

> **레벨 4 이상은 데이터 파일을 영구적으로 손상시킬 수 있다.** 프로덕션 서버에 레벨 4 이상을 적용하기 전에, 반드시 별도의 복사본에서 먼저 테스트해야 한다.

### 레벨별 가능한 작업

|레벨|SELECT|DROP/CREATE|INSERT/UPDATE/DELETE|
|---|---|---|---|
|1 ~ 3|✅|✅|❌ (강제 차단)|
|4 ~ 6|✅|❌|❌ (읽기 전용 모드)|

## 정리: 자동 복구 vs 강제 복구

| 구분      | 자동 복구 (Crash Recovery) | 강제 복구 (innodb_force_recovery)          |
| ------- | ---------------------- | -------------------------------------- |
| 발동 시점   | MySQL 재시작 시 항상 자동 실행   | 자동 복구 실패로 MySQL이 뜨지 않을 때 수동 설정         |
| 목적      | 커밋/미완료 트랜잭션 정리         | 손상된 상태에서 강제 기동 후 데이터 덤프                |
| 사용 방식   | 별도 설정 불필요              | `my.cnf`에 `innodb_force_recovery` 값 지정 |
| 데이터 안전성 | 높음                     | 레벨이 높을수록 손상 위험 증가                      |

# 4.2.7 InnoDB 버퍼 풀 & 4.2.8 DoubleWrite Buffer

---

## 4.2.7 InnoDB 버퍼 풀

> InnoDB의 가장 핵심 컴포넌트. 디스크의 데이터/인덱스 페이지를 메모리에 캐시하고, 쓰기 작업을 지연시켜 일괄 처리하는 버퍼 역할을 동시에 수행한다.

---

### 4.2.7.1 버퍼 풀 크기 설정

- 전용 DB 서버라면 **물리 메모리의 50~80%** 를 버퍼 풀에 할당하는 것이 일반적이다.
- MySQL 5.7부터 **동적으로 크기 조절** 이 가능하다. (서버 재시작 불필요)
- 버퍼 풀이 클수록 디스크 I/O가 줄어들어 인메모리 DB처럼 동작한다.
- 멀티코어 환경에서는 `innodb_buffer_pool_instances` 로 버퍼 풀을 여러 인스턴스로 분할해 **잠금 경합을 줄일 수 있다.**

```ini
innodb_buffer_pool_size = 4G
innodb_buffer_pool_instances = 4  # 보통 1GB당 1개 권장
```

---

### 4.2.7.2 버퍼 풀의 구조

버퍼 풀은 페이지(기본 16KB) 단위로 관리되며, **3가지 리스트** 로 구성된다.

|리스트|역할|
|---|---|
|**Free List**|아직 사용되지 않은 빈 페이지 목록. 새 페이지 적재 시 여기서 꺼낸다.|
|**LRU List**|디스크에서 읽어온 페이지를 관리. 자주 쓰이면 New(MRU) 쪽으로, 안 쓰이면 Old(LRU) 쪽으로 밀린다.|
|**Flush List**|변경됐지만 아직 디스크에 기록되지 않은 **더티 페이지(Dirty Page)** 목록. 디스크 동기화 대상.|

#### LRU 리스트 동작 방식

- 리스트는 **New 영역(5/8)** 과 **Old 영역(3/8)** 으로 나뉜다.
- 새로 읽힌 페이지는 **Old 영역의 Head(Midpoint)** 에 삽입된다.
- Old 영역에서 다시 접근되면 **New 영역으로 승급** 한다.
- 오래 안 쓰이면 Old 영역 Tail에서 제거된다.

> 💡 **Midpoint 삽입 전략의 이유**: `mysqldump`나 풀 스캔처럼 일회성으로 대량 데이터를 읽는 작업이 자주 쓰이는 Hot 데이터를 밀어내지 못하도록 보호하기 위함이다.

---

### 4.2.7.3 버퍼 풀과 리두 로그

버퍼 풀의 더티 페이지는 리두 로그와 **밀접하게 연관**되어 있다.

- 데이터 변경 시 → 버퍼 풀의 페이지가 더티 페이지가 됨 + 리두 로그에 변경 내용 기록
- 리두 로그 공간을 재사용하려면 → 해당 더티 페이지가 먼저 디스크에 플러시돼야 함
- 리두 로그가 너무 작으면 → 자주 플러시가 일어나 버퍼 풀의 쓰기 지연 효과가 줄어듦
- 리두 로그가 너무 크면 → 장애 시 복구 시간이 길어짐

> 💡 버퍼 풀 100GB 기준, 리두 로그는 **5~10GB** 정도가 적절하다고 알려져 있다.

```ini
# MySQL 8.0.30+
innodb_redo_log_capacity = 8G
```

---

### 4.2.7.4 버퍼 풀 플러시

더티 페이지를 디스크에 기록하는 작업. **Page Cleaner 스레드** 가 백그라운드에서 수행한다.

플러시 방식은 두 가지다.

- **Flush List Flush**: 오래된 더티 페이지 순으로 주기적으로 플러시 (Redo 로그 공간 확보 목적)
- **LRU List Flush**: LRU 끝에서 더티 페이지를 플러시 후 Free List로 이동 (빈 페이지 확보 목적)

#### 관련 설정

|변수|설명|
|---|---|
|`innodb_max_dirty_pages_pct`|더티 페이지 비율 상한선 (기본 90%). 초과 시 강제 플러시|
|`innodb_max_dirty_pages_pct_lwm`|비율이 이 값(기본 10%) 이상이면 플러시 시작|
|`innodb_io_capacity`|백그라운드 I/O 처리량 (IOPS). 스토리지 성능에 맞게 설정|
|`innodb_lru_scan_depth`|LRU 리스트에서 스캔할 깊이. 너무 크면 오히려 I/O 낭비|

> ⚠️ 더티 페이지가 갑자기 대량 플러시되면 **쓰기 폭발(Write Burst)** 이 발생해 응답 속도가 급락할 수 있다. InnoDB는 이를 방지하기 위해 적응형 플러시(Adaptive Flushing) 알고리즘으로 플러시 속도를 자동 조절한다.

---

### 4.2.7.5 버퍼 풀 상태 백업 및 복구

MySQL 재시작 직후에는 버퍼 풀이 비어있어 **워밍업(Warm-up)** 시간 동안 성능이 저하될 수 있다. 이를 방지하기 위해 종료 전 버퍼 풀 상태를 저장하고 재시작 시 복구하는 기능이 있다.

```ini
innodb_buffer_pool_dump_at_shutdown = ON   # 종료 시 자동 저장
innodb_buffer_pool_load_at_startup  = ON   # 시작 시 자동 복구
```

- 백업 파일(`ib_buffer_pool`)에는 실제 데이터가 아닌 **페이지의 메타 정보(테이블스페이스 ID + 페이지 번호)만** 저장된다.
- 그래서 백업 파일 크기는 수십 MB 이하로 매우 작지만, 복구 시에는 실제 페이지를 디스크에서 다시 읽어야 하므로 버퍼 풀 크기에 따라 복구 시간이 걸릴 수 있다.

```sql
-- 수동으로 덤프/복구
SET GLOBAL innodb_buffer_pool_dump_now = ON;
SET GLOBAL innodb_buffer_pool_load_now = ON;

-- 복구 진행률 확인
SHOW STATUS LIKE 'Innodb_buffer_pool_load_status';
```

---

### 4.2.7.6 버퍼 풀 적재 내용 확인

현재 버퍼 풀에 어떤 데이터가 올라와 있는지 확인할 수 있다.

```sql
-- 테이블별 버퍼 풀 점유 페이지 수 확인
SELECT table_name,
       count(*) AS pages,
       sum(data_size) / 1024 / 1024 AS size_mb
FROM information_schema.innodb_buffer_page
GROUP BY table_name
ORDER BY pages DESC
LIMIT 20;
```

> ⚠️ `information_schema.innodb_buffer_page` 조회는 버퍼 풀 전체를 스캔하므로, **운영 중인 서버에서는 주의해서 실행**해야 한다. 부하가 있는 서버에서 성능 영향을 줄 수 있다.

## 4.2.8 DoubleWrite Buffer (이중 쓰기 버퍼)

### 왜 필요한가? — Partial Write 문제

InnoDB의 페이지 크기는 기본 **16KB** 다. 그런데 OS는 보통 **4KB 단위**로 I/O를 처리한다. 따라서 16KB 페이지를 디스크에 쓰는 도중 서버가 죽으면 **4KB만 쓰여진 손상된 페이지(Partial Write / Torn Page)** 가 생길 수 있다.

리두 로그는 "변경된 내용"을 기록하는 것이지, 페이지 전체의 복사본이 아니기 때문에 손상된 페이지를 리두 로그만으로는 복구할 수 없다.

### 동작 방식

```
더티 페이지 플러시 시:

① 버퍼 풀의 더티 페이지를 DoubleWrite Buffer에 순차적으로 기록 (Sequential I/O)
② DoubleWrite Buffer → 실제 데이터 파일 위치에 기록
③ 장애 발생 시, DoubleWrite Buffer의 복사본으로 데이터 파일 복구
```

- 데이터가 두 번 기록되지만 I/O 오버헤드는 두 배가 되지 않는다. DoubleWrite Buffer에 쓸 때는 큰 덩어리로 순차(Sequential) I/O를 수행하고 단 하나의 `fsync()` 호출로 처리되기 때문이다.
- 실제 성능 차이는 일반적으로 **5~10% 이내**로 알려져 있다.

### 관련 설정

```ini
innodb_doublewrite = ON   # 기본값, 비활성화 비권장
```

> ⚠️ 성능 벤치마크 등 데이터 유실이 허용되는 환경에서만 OFF를 고려한다. 운영 서버에서는 반드시 ON 상태를 유지해야 한다.

#### MySQL 8.0.30+ 추가 옵션

|값|설명|
|---|---|
|`ON` / `DETECT_AND_RECOVER`|기본값. 완전한 보호 및 복구|
|`DETECT_ONLY`|손상 감지만 하고 복구에는 사용 안 함. 가벼운 설정|
|`OFF`|비활성화. 데이터 안전성 포기|

> 📌 **MySQL 8.0.20부터** DoubleWrite Buffer의 저장 위치가 System Tablespace(`ibdata`)에서 별도의 `.dblwr` 파일로 분리되었다. 빠른 스토리지에 배치하면 성능 향상에 도움이 된다.
