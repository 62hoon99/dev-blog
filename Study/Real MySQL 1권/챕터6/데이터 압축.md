# 데이터 압축

MySQL 서버에서 디스크에 저장된 데이터 파일의 크기는 쿼리 처리 성능과 직결될 뿐만 아니라, 백업 및 복구 시간과도 밀접하게 연결된다.

데이터 파일이 클수록 쿼리 처리를 위해 더 많은 데이터 페이지를 버퍼 풀에 읽어야 하고, 새로운 페이지가 버퍼 풀로 적재되는 만큼 **더티 페이지(Dirty Page)** 가 더 자주 디스크에 기록되어야 한다.

> **더티 페이지(Dirty Page)** 버퍼 풀에 올라온 데이터 페이지가 수정되었지만, 아직 디스크에 반영되지 않은 상태의 페이지. 체크포인트 또는 버퍼 풀 공간 부족 시 디스크로 flush된다.

이러한 문제를 완화하기 위해 MySQL은 두 가지 압축 방식을 제공한다.

---

## 페이지 압축 (Page Compression)

버퍼 풀에 한 번 적재된 데이터 페이지는 InnoDB가 **항상 압축 해제된 상태로만 관리**한다. 여기서 근본적인 문제가 생긴다.

- 16KB 페이지를 압축하면 결과 크기를 예측할 수 없다.
- 그러나 하나의 테이블 내 모든 페이지는 **동일한 크기**여야 한다는 제약이 있다.

이 문제를 해결하기 위해 페이지 압축은 **펀치 홀(Punch Hole)** 기능을 활용한다.

### 펀치 홀 (Punch Hole)

파일 시스템 수준에서 특정 블록을 "구멍(hole)"으로 표시해 실제 디스크 공간을 반환하는 기능이다.

- 예: 16KB 페이지를 압축해 7KB가 됐다면, 나머지 9KB를 펀치 홀로 처리해 디스크 공간 반환
- OS 입장에서는 여전히 16KB 페이지처럼 읽힌다 (압축 데이터 + 빈 홀을 합산)

> **주의** 펀치 홀은 OS뿐만 아니라 **하드웨어(스토리지 장치)** 도 지원해야 동작한다. 하드웨어 호환성 문제로 인해 실무에서는 거의 사용되지 않는다.

---

## 테이블 압축 (Table Compression)

OS나 하드웨어에 대한 제약 없이 사용할 수 있어 **실무에서 더 많이 활용**된다. 단, 다음 단점을 반드시 고려해야 한다.

|단점|설명|
|---|---|
|버퍼 풀 효율 저하|압축/비압축 두 버전을 동시에 관리해 메모리를 이중 소비|
|쿼리 처리 성능 저하|페이지 접근 시마다 압축/해제 오버헤드 발생|
|빈번한 변경 시 압축률 하락|페이지 스플릿·재압축이 반복되어 CPU 자원 소모 증가|

### 압축 테이블 생성 전제 조건

테이블 압축을 사용하려면 해당 테이블이 **별도의 테이블스페이스(file-per-table)** 를 사용해야 한다.

- `innodb_file_per_table = ON` 설정 필요
- `ROW_FORMAT=COMPRESSED` + `KEY_BLOCK_SIZE` 옵션으로 테이블 생성

### 압축 실패율과 사용 판단 기준

압축 실패율이 높다고 해서 반드시 압축을 포기해야 하는 것은 아니다. **워크로드 특성**에 따라 판단해야 한다.

|워크로드 패턴|권장 여부|이유|
|---|---|---|
|로그성 테이블 (INSERT 후 불변)|권장|페이지 스플릿·재압축이 일어나더라도 전체 파일 크기가 대폭 줄어 이득|
|빈번한 조회·변경 테이블|비권장|압축/해제 반복으로 CPU 자원 소모가 크고 성능 저하가 두드러짐|

> 압축은 많은 CPU 자원을 소모한다. 변경이 잦은 테이블에는 적용하지 않는 것이 좋다.

### 압축된 페이지의 버퍼 풀 적재 및 사용

InnoDB는 압축 테이블의 데이터 페이지를 버퍼 풀에 적재할 때 **두 가지 버전을 동시에 유지**한다.

- **압축된 페이지**: 디스크에서 읽어 온 원본
- **압축 해제된 페이지**: 실제 쿼리 처리에 사용

결과적으로 버퍼 풀 공간을 **이중으로 소비**하여 메모리 효율이 떨어진다.

이를 보완하기 위해 InnoDB는 **LRU 리스트를 압축/비압축 페이지별로 분리 관리**하는 로직을 내부적으로 갖추고 있다. 비압축 페이지가 한동안 사용되지 않으면 우선적으로 evict하여 메모리를 확보한다.

---

## 요약 비교

|페이지 압축|테이블 압축|
|---|---|---|
|하드웨어 제약|있음 (펀치 홀 지원 필요)|없음|
|실무 활용도|낮음|높음|
|버퍼 풀 관리|해제된 상태만 관리|압축 + 비압축 이중 관리|
|적합 워크로드|제한적|읽기 중심, 변경이 적은 테이블|

# DBMS 압축 vs 애플리케이션 압축

실무에서 데이터 압축이 필요한 상황이라면 크게 두 가지 선택지가 있다.

- **DBMS 압축**: MySQL 테이블 압축처럼 DB 엔진이 내부적으로 압축을 처리
- **애플리케이션 압축**: 애플리케이션 레이어에서 데이터를 압축한 뒤 BLOB 등의 컬럼에 저장

---

## 방식별 개요

### DBMS 압축 (MySQL 테이블 압축)

DB 엔진이 페이지 단위로 데이터를 압축/해제한다. 애플리케이션 코드는 변경 없이 그대로 사용할 수 있다.

```sql
CREATE TABLE logs (
    id BIGINT NOT NULL AUTO_INCREMENT,
    content TEXT NOT NULL,
    PRIMARY KEY (id)
) ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8;
```

### 애플리케이션 압축

애플리케이션에서 직접 데이터를 압축(gzip, zstd, snappy 등)한 뒤 BLOB 컬럼에 저장한다.

```java
// 저장 시
byte[] compressed = compress(jsonString); // gzip, zstd 등
entity.setData(compressed); // BLOB 컬럼에 저장

// 조회 시
String original = decompress(entity.getData());
```

---

## 핵심 트레이드오프 비교

|항목|DBMS 압축|애플리케이션 압축|
|---|---|---|
|압축 단위|페이지 단위 (16KB)|컬럼 단위 (레코드 수준)|
|압축 알고리즘|zlib 고정|gzip / zstd / snappy 등 자유 선택|
|압축률|보통|높음 (알고리즘 선택 가능)|
|인덱스 사용|가능|불가 (압축된 BLOB은 검색 불가)|
|SQL 쿼리 투명성|완전 투명 (`WHERE`, `ORDER BY` 등 그대로)|불가 (압축 컬럼은 쿼리 조건으로 사용 불가)|
|버퍼 풀 효율|낮음 (압축/비압축 이중 관리)|높음 (압축된 상태로만 저장·관리)|
|CPU 오버헤드 위치|DB 서버|애플리케이션 서버|
|운영 복잡도|낮음 (코드 변경 없음)|높음 (압축/해제 로직, 버전 관리 필요)|
|실시간 데이터 확인|용이 (SQL로 직접 조회)|불편 (직접 조회 불가, 별도 도구 필요)|

---

## 언제 어떤 방식을 선택할까?

### DBMS 압축이 적합한 경우

- 기존 테이블에 **코드 변경 없이** 저장 공간을 줄이고 싶을 때
- 압축 대상 데이터에 **인덱스나 쿼리 조건**이 필요한 경우
- INSERT 후 거의 변경되지 않는 **로그성·이력성 데이터**가 많은 경우
- DBA 중심으로 운영되는 환경에서 **운영 편의성**을 우선할 때

### 애플리케이션 압축이 적합한 경우

- JSON, XML, 바이너리 파일 등 **대용량 비정형 데이터**를 통째로 저장하는 경우
- 해당 컬럼을 **쿼리 조건으로 사용하지 않는** 경우 (단순 저장·조회만 할 때)
- **압축률을 최대화**해야 하거나, zstd처럼 **성능이 좋은 알고리즘**을 선택하고 싶을 때
- DB 서버가 아닌 **애플리케이션 서버에 CPU 부하를 분산**시키고 싶을 때
- 멀티 DB 환경이나 NoSQL과 함께 쓰는 경우처럼 **DB에 종속되지 않는 설계**가 필요할 때

## 실무 관점에서의 현실

MySQL 테이블 압축은 생각보다 실무에서 자주 쓰이지 않는다. 이유는 다음과 같다.

- **버퍼 풀 이중 소비**: 압축/비압축 페이지를 동시에 관리하므로 메모리 효율이 나빠진다. 트래픽이 많은 서비스에서는 오히려 역효과가 날 수 있다.
- **쓰기 성능 저하**: 빈번하게 INSERT/UPDATE가 발생하는 테이블에 적용하면 페이지 스플릿과 재압축이 반복되어 CPU를 많이 소모한다.
- **알고리즘 고정**: MySQL 테이블 압축은 내부적으로 zlib만 사용한다. zstd 같은 더 빠르고 효율적인 알고리즘을 선택할 수 없다.

반면 애플리케이션 압축은 **"어차피 애플리케이션에서만 읽고 쓰는 대용량 컬럼"** 에 대해서는 훨씬 유리하다. 특히 아래 패턴이 실무에서 자주 쓰인다.

- API 응답 캐싱: 직렬화한 JSON을 gzip으로 압축 후 BLOB에 저장
- 파일 첨부: 문서·이미지 바이너리를 압축해 DB에 저장 (S3 등 외부 스토리지 미사용 시)
- 감사 로그: 대용량 데이터를 압축해 보관

> **결론** 쿼리로 검색하거나 인덱스가 필요한 컬럼 → DBMS 압축 단순 저장·조회만 하는 대용량 비정형 컬럼 → 애플리케이션 압축 실무에서는 두 방식을 혼용하는 경우도 많다. 예를 들어 메타데이터 컬럼은 인덱스를 걸고, 본문 데이터 컬럼만 애플리케이션에서 압축해 BLOB으로 저장하는 식이다.
