# 9.3 옵티마이저 고급 최적화

## 9.3.1 옵티마이저 스위치 옵션

옵티마이저 스위치(`optimizer_switch`)는 MySQL 옵티마이저의 최적화 기능을 **개별적으로 ON/OFF** 할 수 있는 시스템 변수다.

```sql
-- 글로벌/세션 단위로 설정 가능
SET GLOBAL optimizer_switch = 'mrr=on,mrr_cost_based=on';
SET SESSION optimizer_switch = 'index_condition_pushdown=on';

-- 특정 쿼리에만 적용 (힌트)
SELECT /*+ SET_VAR(optimizer_switch='mrr=off') */ ...
FROM ...;
```

---

## 9.3.1.1 MRR과 배치 키 액세스 (mrr, batched_key_access)

### 기존 방식의 문제: 네스티드 루프 조인

기존 조인 방식은 드라이빙 테이블에서 레코드를 **한 건씩** 읽고, 즉시 드리븐 테이블을 조회한다.

```
드라이빙 테이블 레코드 1 → 드리븐 테이블 랜덤 I/O
드라이빙 테이블 레코드 2 → 드리븐 테이블 랜덤 I/O
드라이빙 테이블 레코드 3 → 드리븐 테이블 랜덤 I/O
...
```

→ 드리븐 테이블에 대한 **랜덤 I/O가 반복**되어 성능 저하

### MRR (Multi-Range Read)

드리븐 테이블 조회 전, **조인 키를 버퍼(join_buffer)에 모아두고 정렬한 뒤** 한 번에 조회하는 방식이다.

```
드라이빙 테이블 레코드 1, 2, 3 ... → join_buffer에 키 누적
→ 키를 정렬
→ 드리븐 테이블을 순차적으로 읽음 (랜덤 I/O → 순차 I/O에 가깝게)
```

> 핵심: 디스크 I/O 패턴을 **랜덤 → 순차**에 가깝게 바꿔 성능 향상

### BKA (Batched Key Access)

MRR을 조인에 적용한 것이 **BKA**다.

```sql
-- BKA 활성화 (MRR도 함께 켜야 함)
SET optimizer_switch = 'mrr=on,mrr_cost_based=off,batched_key_access=on';
```

> ⚠️ BKA는 join_buffer를 사용하므로 **부가적인 메모리 사용** 발생. 무조건 좋은 건 아니며, 실행 계획 확인 후 판단 필요.

---

## 9.3.1.2 블록 네스티드 루프 조인 (block_nested_loop)

### 기존 네스티드 루프 조인

```
for each row in 드라이빙 테이블:
    for each row in 드리븐 테이블:
        if 조인 조건 일치: 결과에 추가
```

드리븐 테이블에 **인덱스가 없으면** 매번 풀 스캔 → 심각한 성능 저하

### 블록 네스티드 루프 (BNL)

드라이빙 테이블 레코드를 **join_buffer에 버퍼링**하고, 드리븐 테이블을 한 번 스캔하면서 버퍼 전체와 비교한다.

```
드라이빙 테이블 레코드들 → join_buffer에 적재
드리븐 테이블 풀 스캔 1회 → join_buffer 전체와 비교
```

- 드리븐 테이블 스캔 횟수를 줄여 **I/O 감소**
- join_buffer 크기(`join_buffer_size`)에 따라 성능 차이 발생

> ⚠️ MySQL 8.0.20부터 BNL은 **해시 조인(Hash Join)으로 대체**됨. `block_nested_loop=off`가 기본값.

### 해시 조인 (MySQL 8.0+)

```
드라이빙 테이블 → 해시 테이블 빌드
드리븐 테이블 → 해시 테이블 프로브
```

BNL보다 효율적이므로, **인덱스 없는 조인**에서 MySQL 8.0 이상은 해시 조인을 사용한다.

## 9.3.1.3 인덱스 컨디션 시다운 (index_condition_pushdown)

### 핵심 개념

ICP는 인덱스를 이용해서 스토리지 엔진이 **레코드를 읽기 전에** 조건을 먼저 필터링하는 최적화다.

### ICP 없는 경우 (기존)

```
스토리지 엔진: 인덱스 범위 스캔 → 레코드 읽어서 MySQL 엔진에 전달
MySQL 엔진:   나머지 조건 필터링 (WHERE 조건)
```

불필요한 레코드까지 읽어서 올려보낸 후 버림 → **불필요한 I/O 발생**

### ICP 있는 경우

```
스토리지 엔진: 인덱스에서 조건 체크 → 조건 통과한 레코드만 읽어서 전달
MySQL 엔진:   최종 처리
```

```sql
-- 예시
-- 인덱스: (last_name, first_name)
SELECT * FROM employees
WHERE last_name = 'Action' AND first_name LIKE '%sal';
```

- `last_name = 'Action'` → 인덱스 범위 스캔
- `first_name LIKE '%sal'` → ICP 없으면 MySQL 엔진에서 필터, **ICP 있으면 스토리지 엔진에서 인덱스로 먼저 필터**

실행 계획에서 `Extra: Using index condition`으로 확인 가능

> ✅ 기본값 ON. 일반적으로 켜두는 것이 유리하다.

## 9.3.1.4 인덱스 확장 (use_index_extensions)

### 핵심 개념

InnoDB의 **세컨더리 인덱스에는 PK 컬럼이 자동으로 포함**된다.

```
-- 테이블 구조
CREATE TABLE employees (
  emp_no INT PRIMARY KEY,
  dept_no CHAR(4),
  from_date DATE,
  INDEX ix_dept_from (dept_no, from_date)
);

-- 실제 세컨더리 인덱스 구성
-- ix_dept_from: (dept_no, from_date, emp_no)  ← emp_no 자동 포함
```

### 활용 포인트

옵티마이저가 이 사실을 인지하고 **PK 컬럼을 추가 조건/정렬에 활용**할 수 있다.

```sql
-- dept_no 조건 + emp_no 정렬 → 인덱스만으로 정렬 처리 가능 (filesort 없음)
SELECT * FROM dept_emp
WHERE dept_no = 'd001'
ORDER BY emp_no;
```

실행 계획에서 `key_len`이 늘어난 것으로 PK 컬럼까지 활용 여부를 확인할 수 있다.

> ✅ 기본값 ON. 불필요한 filesort를 줄이고 인덱스 활용도를 높여준다.

---

## 9.3.1.5 인덱스 머지 (index_merge)

### 핵심 개념

일반적으로 옵티마이저는 테이블당 **하나의 인덱스만** 사용한다. 인덱스 머지는 **2개 이상의 인덱스를 동시에 사용**해 결과를 병합하는 방식이다.

인덱스 머지는 세 가지 방식으로 나뉜다.

---

### (1) index_merge_intersection

두 인덱스의 결과를 **AND(교집합)**로 병합

```sql
-- ix_firstname, ix_empno_lastname 두 인덱스 동시 사용
SELECT * FROM employees
WHERE first_name = 'Georgi' AND emp_no BETWEEN 10000 AND 20000;
```

```
실행 계획 Extra: Using intersect(ix_firstname, PRIMARY)
```

각 인덱스로 rowid 집합을 구하고 **교집합**만 레코드 읽기 → 읽는 레코드 수 감소

---

### (2) index_merge_union

두 인덱스의 결과를 **OR(합집합)**로 병합

```sql
SELECT * FROM employees
WHERE first_name = 'Matt' OR hire_date = '1987-03-31';
```

```
실행 계획 Extra: Using union(ix_firstname, ix_hiredate)
```

각 인덱스 결과를 합치되, **중복 제거(Priority Queue 사용)**하여 반환

> OR 조건에서 각 컬럼에 인덱스가 있을 때 활용됨

---

### (3) index_merge_sort_union

Union과 유사하나, 인덱스 결과가 **정렬되지 않은 경우** 먼저 정렬 후 합집합 처리

```sql
SELECT * FROM employees
WHERE first_name = 'Matt'
   OR hire_date BETWEEN '1987-03-01' AND '1987-03-31';
```

```
실행 계획 Extra: Using sort_union(ix_firstname, ix_hiredate)
```

범위 조건(`BETWEEN`, `>`, `<`)의 결과는 PK 순 정렬이 보장되지 않으므로, **정렬 후 병합**한다.

---

### 인덱스 머지 제어

```sql
-- 개별 제어
SET optimizer_switch = 'index_merge_intersection=off';
SET optimizer_switch = 'index_merge_union=off';
SET optimizer_switch = 'index_merge_sort_union=off';

-- 전체 끄기
SET optimizer_switch = 'index_merge=off';
```

> ⚠️ 인덱스 머지가 항상 최선은 아니다. 복합 인덱스 설계로 해결 가능한 경우, 인덱스 머지보다 **복합 인덱스가 더 효율적**일 수 있다.

---
## 9.3.1.6 인덱스 머지 - 교집합 (index_merge_intersection)

### 언제 사용되나?

WHERE 조건이 **AND로 연결**되어 있고, 각 조건에 **별도의 인덱스**가 존재할 때 옵티마이저가 선택할 수 있다.

```sql
-- 인덱스: ix_firstname(first_name), PRIMARY(emp_no)
SELECT *
FROM employees
WHERE first_name = 'Georgi'        -- ix_firstname 사용
  AND emp_no BETWEEN 10000 AND 20000;  -- PRIMARY 사용
```

### 동작 원리

```
ix_firstname  → first_name = 'Georgi'       → rowid 집합 A
PRIMARY       → emp_no BETWEEN 10000~20000  → rowid 집합 B

교집합(A ∩ B) → 실제 레코드 읽기
```

각 인덱스가 반환하는 결과는 **PK(rowid) 기준으로 정렬된 상태**이므로, 별도 정렬 없이 **순차 비교로 교집합** 처리가 가능하다.

### 핵심 포인트

단일 인덱스만 사용할 경우와 비교:

- `ix_firstname`만 사용 → `first_name = 'Georgi'` 결과 전체 읽은 뒤 `emp_no` 필터
- 교집합 사용 → 양쪽 조건을 먼저 교집합으로 좁힌 뒤 최소한의 레코드만 읽음

```sql
-- 실행 계획 확인
EXPLAIN SELECT * FROM employees
WHERE first_name = 'Georgi' AND emp_no BETWEEN 10000 AND 20000;
```

```
Extra: Using intersect(ix_firstname, PRIMARY); Using where
```

### 주의 사항

> ⚠️ 교집합이 오히려 비효율적인 경우도 있다.  
> `first_name = 'Georgi'` 결과가 적으면, 단순히 `ix_firstname`만 쓰고 `emp_no` 조건을 WHERE 필터로 처리하는 게 더 빠를 수 있다.  
> → **복합 인덱스 `(first_name, emp_no)`** 설계가 근본적인 해결책이다.

---

## 9.3.1.7 인덱스 머지 - 합집합 (index_merge_union)

### 언제 사용되나?

WHERE 조건이 **OR로 연결**되어 있고, 각 조건에 **별도의 인덱스**가 존재할 때 사용된다.

```sql
-- 인덱스: ix_firstname(first_name), ix_hiredate(hire_date)
SELECT *
FROM employees
WHERE first_name = 'Matt'
   OR hire_date = '1987-03-31';
```

### 동작 원리

```
ix_firstname → first_name = 'Matt'         → rowid 집합 A (PK 순 정렬됨)
ix_hiredate  → hire_date = '1987-03-31'    → rowid 집합 B (PK 순 정렬됨)

합집합(A ∪ B), 중복 제거 → 실제 레코드 읽기
```

두 인덱스의 결과가 이미 **PK 기준으로 정렬된 상태**이므로, **Priority Queue**를 사용해 중복 없이 병합한다.

### 핵심 포인트

OR 조건을 인덱스 없이 처리하면 → **풀 테이블 스캔 불가피**  
인덱스 머지 합집합 사용 시 → **두 인덱스로 각각 좁혀서 병합** → 훨씬 효율적

```sql
EXPLAIN SELECT * FROM employees
WHERE first_name = 'Matt' OR hire_date = '1987-03-31';
```

```
Extra: Using union(ix_firstname, ix_hiredate); Using where
```

### 합집합 vs 교집합 비교

|구분|조건 연산자|병합 방식|정렬 필요 여부|
|---|---|---|---|
|**교집합**|AND|교집합(∩)|불필요 (이미 PK 정렬)|
|**합집합**|OR|합집합(∪) + 중복 제거|불필요 (이미 PK 정렬)|
|**정렬 후 합집합**|OR (범위 조건 포함)|정렬 후 합집합(∪)|**필요**|

---

## 9.3.1.8 인덱스 머지 - 정렬 후 합집합 (index_merge_sort_union)

### 언제 사용되나?

OR 조건 중 **범위 조건(`BETWEEN`, `>`, `<`, `LIKE` 등)** 이 포함될 때 사용된다.

```sql
SELECT *
FROM employees
WHERE first_name = 'Matt'
   OR hire_date BETWEEN '1987-03-01' AND '1987-03-31';
```

### 합집합과 다른 이유

```
ix_firstname → first_name = 'Matt'                        → PK 순 정렬 보장 ✅
ix_hiredate  → hire_date BETWEEN '1987-03-01~03-31'       → hire_date 순 정렬 ❌ (PK 순 아님)
```

범위 조건으로 검색한 결과는 **해당 인덱스 컬럼 기준으로 정렬**되어 있어, **PK 기준 정렬이 보장되지 않는다.**  
→ 중복 제거를 위해 **PK 기준 정렬을 먼저 수행**해야 한다.

### 동작 원리

```
ix_firstname → first_name = 'Matt'             → rowid 집합 A (PK 정렬됨)
ix_hiredate  → hire_date BETWEEN ...           → rowid 집합 B (PK 기준 재정렬 필요)
                                                     ↓
                                               B를 PK 기준으로 정렬 (Sort)
                                                     ↓
                              합집합(A ∪ B), 중복 제거 → 실제 레코드 읽기
```

```sql
EXPLAIN SELECT * FROM employees
WHERE first_name = 'Matt'
   OR hire_date BETWEEN '1987-03-01' AND '1987-03-31';
```

```
Extra: Using sort_union(ix_firstname, ix_hiredate); Using where
```

### 핵심 포인트

> `Using union` → 추가 정렬 없이 병합 가능 (등치 조건)  
> `Using sort_union` → **정렬 부하 발생** (범위 조건 포함 시)  
> sort_union이 자주 보인다면 → **인덱스 설계 재검토** 또는 **쿼리 분리(UNION ALL)** 고려

## 9.3.1.9 세미 조인 (semijoin)

### 개념

세미 조인은 **다른 테이블과 조인하되, 조인 테이블의 실제 컬럼은 반환하지 않고 레코드 존재 여부만 확인**하는 형태의 조인이다.

주로 `IN (subquery)`, `EXISTS (subquery)` 형태의 쿼리에서 발생한다.

```sql
-- 세미 조인 형태의 쿼리
SELECT *
FROM employees e
WHERE e.emp_no IN (
    SELECT de.emp_no
    FROM dept_emp de
    WHERE de.dept_no = 'd001'
);
```

### MySQL의 세미 조인 최적화 전략

MySQL 옵티마이저는 세미 조인을 아래 5가지 방식으로 최적화한다.

```
1. Table Pull-out       (테이블 풀-아웃)
2. Duplicate Weed-out   (중복 제거)
3. First Match          (퍼스트 매치)
4. Loose Scan           (루스 스캔)
5. Materialization      (구체화)
```

각 전략은 **쿼리 구조, 인덱스 유무, 서브쿼리 특성**에 따라 옵티마이저가 자동으로 선택한다.

### 세미 조인 최적화 활성화 제어

```sql
-- 전체 세미 조인 OFF
SET optimizer_switch = 'semijoin=off';

-- 개별 전략 제어
SET optimizer_switch = 'firstmatch=off';
SET optimizer_switch = 'loosescan=off';
SET optimizer_switch = 'materialization=off';
```

> ✅ 기본값 ON. 서브쿼리 성능에 큰 영향을 주는 핵심 최적화다.

---

## 9.3.1.10 테이블 풀-아웃 (Table Pull-out)

### 개념

세미 조인 최적화 중 **가장 간단하고 효과적인 방식**이다.  
서브쿼리의 테이블을 **외부 쿼리로 끌어내어 일반 조인으로 변환**한다.

```sql
-- 원본 쿼리 (세미 조인 형태)
SELECT *
FROM employees e
WHERE e.emp_no IN (
    SELECT de.emp_no
    FROM dept_emp de
    WHERE de.dept_no = 'd001'
);

-- 풀-아웃 후 (옵티마이저가 내부적으로 변환)
SELECT e.*
FROM dept_emp de
    JOIN employees e ON e.emp_no = de.emp_no
WHERE de.dept_no = 'd001';
```

### 동작 조건

풀-아웃이 적용되려면 아래 조건을 만족해야 한다.

|조건|설명|
|---|---|
|IN 절의 서브쿼리|`EXISTS` 는 적용 불가|
|서브쿼리가 **유니크한 결과**|서브쿼리 결과 컬럼이 PK 또는 유니크 인덱스일 것|
|서브쿼리가 **단순 형태**|집계 함수, GROUP BY, LIMIT 등 없을 것|

> `dept_emp.emp_no`가 PK이거나 UNIQUE라면 중복 없이 풀-아웃 가능

### 실행 계획 확인

```sql
EXPLAIN SELECT * FROM employees e
WHERE e.emp_no IN (
    SELECT de.emp_no FROM dept_emp de WHERE de.dept_no = 'd001'
);
```

```
-- 풀-아웃 적용 시
id | select_type | table
1  | SIMPLE      | de      ← 서브쿼리가 아닌 SIMPLE로 처리됨
1  | SIMPLE      | e
```

`select_type`이 `SUBQUERY`가 아닌 **`SIMPLE`로 표시**되면 풀-아웃이 적용된 것이다.

### 왜 성능이 좋아지나?

```
서브쿼리 방식:
  외부 쿼리 레코드마다 서브쿼리 반복 실행 가능성 (상관 서브쿼리)

풀-아웃 방식:
  일반 조인으로 변환 → 조인 최적화(순서 변경, 인덱스 활용 등) 모두 적용 가능
  → 옵티마이저가 더 자유롭게 실행 계획 수립
```

## 9.3.1.11 퍼스트 매치 (firstmatch)

### 개념

`IN (subquery)` 형태를 **`EXISTS (subquery)`로 변환**하는 것과 유사한 방식으로 동작한다.  
드라이빙 테이블의 레코드에 대해 서브쿼리 조건을 만족하는 **첫 번째 레코드를 찾는 즉시 더 이상 탐색하지 않고** 다음으로 넘어간다.

```sql
SELECT *
FROM employees e
WHERE e.first_name = 'Matt'
  AND e.emp_no IN (
      SELECT t.emp_no
      FROM titles t
      WHERE t.from_date BETWEEN '1995-01-01' AND '1995-01-30'
  );
```

### 동작 원리

```
기존 IN (subquery) 처리 방식:
  employees에서 first_name = 'Matt' 인 레코드 전체 추출
  → 각 레코드마다 titles 서브쿼리 전체 실행

퍼스트 매치 방식:
  employees → titles 순으로 조인
  titles에서 조건 만족하는 첫 번째 레코드 발견 즉시 → 다음 employees 레코드로 이동
  (중복 결과 발생 없음)
```

### 실행 계획 확인

```sql
EXPLAIN SELECT * FROM employees e
WHERE e.first_name = 'Matt'
  AND e.emp_no IN (
      SELECT t.emp_no FROM titles t
      WHERE t.from_date BETWEEN '1995-01-01' AND '1995-01-30'
  );
```

```
id | table | Extra
1  | e     | Using where
1  | t     | Using index condition; FirstMatch(e)  ← 퍼스트 매치 적용
```

`FirstMatch(기준테이블명)` 으로 표시된다.

### 특징 및 제약 조건

|항목|내용|
|---|---|
|적용 대상|`IN (subquery)`|
|내부 동작|EXISTS 방식과 유사하게 변환|
|서브쿼리 상관관계|상관 서브쿼리에도 적용 가능|
|GROUP BY / 집계 함수|서브쿼리에 포함되면 적용 불가|
|장점|불필요한 탐색 조기 종료 → I/O 감소|
|단점|서브쿼리 결과가 **소수**일 때 효과적, 많을 때는 비효율|

### 테이블 풀-아웃과 비교

|구분|테이블 풀-아웃|퍼스트 매치|
|---|---|---|
|변환 방식|일반 JOIN으로 완전 변환|EXISTS 방식 유사 변환|
|적용 조건|서브쿼리 결과가 유니크해야 함|유니크 조건 불필요|
|중복 처리|조인 자체가 중복 없음|첫 매치 즉시 다음으로 이동|
|실행 계획|select_type = SIMPLE|FirstMatch(테이블명)|

## 9.3.1.12 루스 스캔 (loosescan)

### 개념

`IN (subquery)` 에서 서브쿼리가 **GROUP BY 없이 중복 값을 가진 인덱스 컬럼**을 참조할 때, 인덱스를 **루스 인덱스 스캔(Loose Index Scan)** 방식으로 읽어 중복을 제거하며 최적화하는 방식이다.

> 루스 인덱스 스캔: 인덱스에서 **필요한 값만 듬성듬성 읽는 방식** (GROUP BY 최적화에서도 사용됨)

```sql
-- dept_emp.dept_no는 중복 값을 가짐
-- 인덱스: (dept_no, emp_no)
SELECT *
FROM departments d
WHERE d.dept_no IN (
    SELECT de.dept_no
    FROM dept_emp de
);
```

### 동작 원리

```
dept_emp의 (dept_no, emp_no) 인덱스:
  d001 | 10001
  d001 | 10002   ← dept_no 기준으로 중복
  d001 | 10003
  d002 | 10004
  d002 | 10005
  ...

루스 스캔: dept_no가 바뀔 때만 읽음 (대표 1건씩만 추출)
  d001 | 10001  ← 읽음
  d002 | 10004  ← 읽음
  ...

→ departments 테이블과 조인
```

중복된 `dept_no` 중 **첫 번째 값만 읽고 건너뜀** → 불필요한 레코드 스캔 대폭 감소

### 실행 계획 확인

```sql
EXPLAIN SELECT * FROM departments d
WHERE d.dept_no IN (
    SELECT de.dept_no FROM dept_emp de
);
```

```
id | table | Extra
1  | de    | Using index; LooseScan    ← 루스 스캔 적용
1  | d     | Using where
```

### 적용 조건

|조건|설명|
|---|---|
|서브쿼리 테이블에 인덱스 존재|루스 스캔은 인덱스 기반|
|서브쿼리 결과 컬럼이 인덱스 **선두 컬럼**|인덱스 앞부분만 스캔해 중복 제거|
|서브쿼리가 단순 형태|GROUP BY, 집계 함수 없을 것|

### 퍼스트 매치와 비교

|구분|퍼스트 매치|루스 스캔|
|---|---|---|
|주 관심사|외부 테이블 기준 조기 종료|서브쿼리 테이블 기준 중복 제거|
|인덱스 활용|조인 인덱스 활용|서브쿼리 테이블 인덱스 필수|
|실행 계획|FirstMatch(테이블)|LooseScan|

## 9.3.1.13 구체화 (materialization)

### 개념

서브쿼리를 **임시 테이블로 구체화(Materialization)** 한 뒤, 외부 쿼리와 조인하는 방식이다.  
앞선 최적화(풀-아웃, 퍼스트 매치, 루스 스캔)가 적용되지 않을 때 사용된다.

```sql
SELECT *
FROM employees e
WHERE e.emp_no IN (
    SELECT de.emp_no
    FROM dept_emp de
    WHERE de.from_date = '1995-01-01'
);
```

### 동작 원리

```
1단계: 서브쿼리를 먼저 실행 → 결과를 내부 임시 테이블(해시 테이블)로 저장
       (중복 제거 포함)

  임시 테이블: { emp_no: 10001, 10002, 10045, ... }

2단계: employees 테이블과 임시 테이블을 조인
  employees ⟕ 임시 테이블(emp_no 기준)
```

### 실행 계획 확인

```sql
EXPLAIN SELECT * FROM employees e
WHERE e.emp_no IN (
    SELECT de.emp_no FROM dept_emp de
    WHERE de.from_date = '1995-01-01'
);
```

```
id | select_type  | table      | Extra
1  | PRIMARY      | <subquery2>| Using where    ← 임시 테이블과 조인
1  | PRIMARY      | e          |
2  | MATERIALIZED | de         |                ← 서브쿼리 구체화
```

`select_type = MATERIALIZED` 로 표시된다.

### 구체화가 유리한 경우

```
서브쿼리 실행 비용 < 외부 쿼리 레코드 수 × 서브쿼리 반복 실행 비용
```

즉, **서브쿼리 결과가 크지 않고, 외부 쿼리 레코드가 많을 때** 효율적이다.

```
외부 쿼리 레코드: 10만 건
서브쿼리 매번 실행 비용: 크다

→ 서브쿼리를 임시 테이블로 1번만 만들고 10만 번 조인 (해시 조인)
→ 훨씬 효율적
```

### 주의 사항

> ⚠️ 구체화된 임시 테이블은 **메모리 또는 디스크**에 생성된다.  
> 서브쿼리 결과가 너무 크면 **디스크 임시 테이블** 사용 → 성능 저하 가능  
> `tmp_table_size`, `max_heap_table_size` 설정이 영향을 미친다.

### 구체화 vs 퍼스트 매치 비교

|구분|구체화|퍼스트 매치|
|---|---|---|
|서브쿼리 실행 시점|**미리 실행** 후 임시 테이블 생성|외부 쿼리 레코드마다 실행|
|상관 서브쿼리 적용|❌ 불가 (독립 서브쿼리만 가능)|✅ 가능|
|GROUP BY / 집계|✅ 적용 가능|❌ 불가|
|유리한 상황|외부 쿼리 레코드 多, 서브쿼리 결과 소|서브쿼리 매칭 레코드 소|

## 9.3.1.14 중복 제거 (duplicateweedout)

### 개념

세미 조인을 **일반 조인으로 변환하고 실행**한 뒤, 중복된 레코드를 **임시 테이블을 이용해 제거**하는 방식이다.

```sql
SELECT *
FROM employees e
WHERE e.emp_no IN (
    SELECT s.emp_no
    FROM salaries s
    WHERE s.salary > 150000
);
```

### 동작 원리

```
1단계: IN (subquery)를 일반 JOIN으로 변환
  employees JOIN salaries ON e.emp_no = s.emp_no
  WHERE s.salary > 150000

2단계: 조인 결과에서 employees 기준 중복 발생
  emp_no 10001 | salary 150001
  emp_no 10001 | salary 155000  ← 중복!
  emp_no 10002 | salary 152000

3단계: 임시 테이블에 emp_no(PK 기준) INSERT
  → 이미 존재하는 emp_no는 중복 제거
  → 최종 결과 반환
```

### 실행 계획 확인

```sql
EXPLAIN SELECT * FROM employees e
WHERE e.emp_no IN (
    SELECT s.emp_no FROM salaries s
    WHERE s.salary > 150000
);
```

```
id | table | Extra
1  | s     | Using where; Start temporary   ← 임시 테이블 시작
1  | e     | Using where; End temporary     ← 임시 테이블 종료 (중복 제거)
```

`Start temporary` / `End temporary` 쌍으로 표시된다.

### 특징

|항목|내용|
|---|---|
|변환 방식|일반 JOIN + 임시 테이블 중복 제거|
|임시 테이블 용도|조인 결과에서 외부 쿼리 PK 기준 중복 제거|
|상관 서브쿼리|✅ 적용 가능|
|GROUP BY / 집계|❌ 서브쿼리에 있으면 적용 불가|

### 구체화 vs 중복 제거 비교

|구분|구체화|중복 제거|
|---|---|---|
|임시 테이블 생성 시점|서브쿼리 **먼저** 실행|조인 **후** 중복 제거|
|임시 테이블 내용|서브쿼리 결과|외부 쿼리 PK|
|상관 서브쿼리|❌ 불가|✅ 가능|
|실행 계획 표시|MATERIALIZED|Start/End temporary|

## 9.3.1.15 컨디션 팬아웃 (condition_fanout_filter)

### 개념

옵티마이저가 **조인 순서를 결정할 때**, 각 테이블의 조건이 얼마나 레코드를 **필터링할지 예측(filtered 값)** 하는 정확도를 높이는 최적화다.

```sql
-- filtered 컬럼: 조건 적용 후 남는 레코드 비율(%)
EXPLAIN SELECT * FROM employees e
JOIN salaries s ON e.emp_no = s.emp_no
WHERE e.first_name = 'Matt'
  AND e.hire_date BETWEEN '1985-11-21' AND '1986-11-21';
```

```
table | rows  | filtered | Extra
e     | 233   | 16.31    | Using where  ← filtered가 정확할수록 조인 순서 최적화
s     | 10    | 100.00   |
```

### filtered 값이 중요한 이유

```
조인 순서 결정 공식:
  드라이빙 테이블 rows × (filtered / 100) = 드리븐 테이블 접근 횟수 예측

filtered 부정확 → 잘못된 조인 순서 선택 → 성능 저하
filtered 정확  → 최적 조인 순서 선택 → 성능 향상
```

### 컨디션 팬아웃이 filtered 예측에 사용하는 정보

우선순위 순으로 활용한다.

```
1순위: 레인지 옵티마이저 (인덱스 범위 조건 분석)
2순위: 히스토그램 (컬럼 값 분포 통계)
3순위: 인덱스 통계 (인덱스 선택도)
4순위: 추측 (위 정보 없을 때 기본값 사용)
```

### 컨디션 팬아웃 ON/OFF 비교

```sql
-- OFF 상태
SET optimizer_switch = 'condition_fanout_filter=off';
EXPLAIN ...;
-- filtered: 100 (모든 레코드가 조건 통과한다고 가정 → 부정확)

-- ON 상태 (기본값)
SET optimizer_switch = 'condition_fanout_filter=on';
EXPLAIN ...;
-- filtered: 16.31 (실제 분포 기반 정확한 예측)
```

### 주의 사항

> ⚠️ 컨디션 팬아웃은 **더 정교한 계산을 수행**하므로 실행 계획 수립 시간이 증가할 수 있다.  
> 테이블 수가 많고 조인이 복잡한 쿼리에서는 **실행 계획 수립 비용 자체**가 부담될 수 있다.  
> 대부분의 경우 ON이 유리하지만, 쿼리 최적화 시간이 오버헤드가 된다면 OFF 고려.

## 9.3.1.16 파생 테이블 머지 (derived_merge)

### 개념

`FROM` 절의 **서브쿼리(파생 테이블)** 를 외부 쿼리와 **병합(merge)** 하여 하나의 쿼리로 처리하는 최적화다.

```sql
-- 파생 테이블을 사용하는 쿼리
SELECT *
FROM (
    SELECT *
    FROM employees
    WHERE first_name = 'Matt'
) derived
WHERE derived.hire_date > '1986-04-03';
```

### 기존 방식 (머지 없음)

```
1단계: 서브쿼리 먼저 실행 → 결과를 임시 테이블(파생 테이블)에 저장
       임시 테이블: first_name = 'Matt' 인 레코드 전체

2단계: 임시 테이블을 대상으로 hire_date 조건 필터링

문제점:
  - 임시 테이블 생성 비용 발생
  - 임시 테이블에는 인덱스가 없음 → 풀 스캔
  - first_name 조건 + hire_date 조건을 동시에 인덱스로 처리 불가
```

### 파생 테이블 머지 적용 후

```
옵티마이저가 내부적으로 쿼리를 변환:

SELECT *
FROM employees
WHERE first_name = 'Matt'
  AND hire_date > '1986-04-03';

→ 임시 테이블 없이 employees를 직접 스캔
→ 인덱스 활용 가능
→ 두 조건을 한 번에 처리
```

### 실행 계획 확인

```sql
-- 머지 적용 전
EXPLAIN SELECT * FROM (
    SELECT * FROM employees WHERE first_name = 'Matt'
) derived
WHERE derived.hire_date > '1986-04-03';
```

```
-- 머지 OFF 시
id | select_type | table      | Extra
1  | PRIMARY     | <derived2> | Using where   ← 임시 테이블 스캔
2  | DERIVED     | employees  | Using where

-- 머지 ON 시 (기본값)
id | select_type | table     | Extra
1  | SIMPLE      | employees | Using where   ← 단일 쿼리로 병합
```

`select_type = DERIVED` 가 사라지고 `SIMPLE`로 처리되면 머지가 적용된 것이다.

### 머지가 불가능한 경우

파생 테이블 머지는 **항상 적용되지는 않는다.** 아래 경우 옵티마이저는 임시 테이블을 유지한다.

|불가 조건|이유|
|---|---|
|`UNION` / `UNION ALL`|결과 집합 병합 구조상 불가|
|`GROUP BY` / `HAVING`|집계 후 필터링 순서 변경 불가|
|`LIMIT`|결과 제한이 먼저 적용되어야 함|
|`집계 함수` (SUM, COUNT 등)|집계 결과를 외부에서 쓰는 구조|
|`DISTINCT`|중복 제거 순서 변경 불가|
|서브쿼리가 외부 쿼리 컬럼 참조|상관 관계 발생|

```sql
-- 머지 불가 예시 (LIMIT 포함)
SELECT *
FROM (
    SELECT * FROM employees
    WHERE first_name = 'Matt'
    LIMIT 100              -- LIMIT 때문에 머지 불가
) derived
WHERE hire_date > '1986-04-03';
```

### 제어 방법

```sql
-- 전체 세션에서 OFF
SET optimizer_switch = 'derived_merge=off';

-- 특정 쿼리에만 OFF (힌트)
SELECT /*+ NO_MERGE(derived) */ *
FROM (SELECT * FROM employees WHERE first_name = 'Matt') derived
WHERE hire_date > '1986-04-03';
```

> ✅ 기본값 ON. 불필요한 임시 테이블 생성을 줄여 성능 향상에 효과적이다.

## 9.3.1.17 인비저블 인덱스 (invisible index)

### 개념

인덱스를 **실제로 삭제하지 않고** 옵티마이저가 **해당 인덱스를 사용하지 못하도록 숨기는** 기능이다. (MySQL 8.0 도입)

### 왜 필요한가?

```
인덱스 삭제의 문제점:
  삭제 → 성능 저하 확인 → 다시 생성
  인덱스 재생성: 대용량 테이블에서 수십 분 ~ 수 시간 소요
  서비스 중단 위험

인비저블 인덱스:
  숨김 처리 → 성능 영향 확인 → 문제 없으면 실제 삭제
  숨김/해제: 메타데이터만 변경 → 즉시 적용 가능
```

### 사용법

```sql
-- 인덱스 생성 시 INVISIBLE 지정
CREATE INDEX ix_hiredate ON employees(hire_date) INVISIBLE;

-- 기존 인덱스를 INVISIBLE로 변경
ALTER TABLE employees ALTER INDEX ix_hiredate INVISIBLE;

-- 다시 VISIBLE로 복구
ALTER TABLE employees ALTER INDEX ix_hiredate VISIBLE;

-- 인덱스 상태 확인
SELECT INDEX_NAME, IS_VISIBLE
FROM information_schema.STATISTICS
WHERE TABLE_NAME = 'employees';
```

### 동작 특성

```
INVISIBLE 상태에서:
  - 옵티마이저: 해당 인덱스 무시 (사용 불가)
  - 인덱스 자체: 계속 유지 및 갱신됨 (INSERT/UPDATE/DELETE 시 동기화)

→ 데이터 변경 비용은 그대로 발생
→ 조회 시에만 무시됨
```

### 옵티마이저 스위치로 INVISIBLE 인덱스 강제 사용

```sql
-- use_invisible_indexes=on 시 INVISIBLE 인덱스도 사용 가능
SET SESSION optimizer_switch = 'use_invisible_indexes=on';

-- 특정 세션에서만 테스트 가능
-- → 운영 트래픽 영향 없이 인덱스 효과 검증 가능
```

### 활용 시나리오

```
1. 인덱스 삭제 전 영향도 검증
   INVISIBLE → 실행 계획 / 성능 확인 → 문제 없으면 DROP

2. 신규 인덱스 추가 전 테스트
   INVISIBLE로 생성 → use_invisible_indexes=on 세션에서 효과 검증
   → 문제 없으면 VISIBLE로 전환

3. 특정 인덱스가 오히려 성능을 저하시킬 때
   INVISIBLE로 임시 비활성화 → 원인 분석
```

> ⚠️ INVISIBLE이어도 인덱스 유지 비용(DML 성능 영향)은 발생한다. 장기간 불필요한 인덱스는 결국 DROP해야 한다.

## 9.3.1.18 스킵 스캔 (skip_scan)

### 개념

복합 인덱스에서 **선두 컬럼 조건이 없어도** 인덱스를 활용할 수 있게 해주는 최적화다. (MySQL 8.0 도입)

### 기존의 인덱스 제약

```
인덱스: (gender, birth_date)

-- 선두 컬럼(gender) 조건 있음 → 인덱스 사용 가능
SELECT * FROM employees WHERE gender = 'M' AND birth_date > '1965-01-01';

-- 선두 컬럼(gender) 조건 없음 → 기존에는 인덱스 사용 불가 (풀 스캔)
SELECT * FROM employees WHERE birth_date > '1965-01-01';
```

### 스킵 스캔 동작 원리

선두 컬럼의 **유니크 값을 먼저 파악**하고, 각 값에 대해 나머지 조건으로 범위 스캔을 반복한다.

```
인덱스: (gender, birth_date)
gender의 유니크 값: 'M', 'F'

스킵 스캔 내부 동작:
  gender = 'M' AND birth_date > '1965-01-01' → 범위 스캔
  gender = 'F' AND birth_date > '1965-01-01' → 범위 스캔

→ 두 결과를 합쳐서 반환
```

마치 선두 컬럼의 모든 유니크 값을 **자동으로 IN 조건처럼** 처리하는 것과 유사하다.

### 실행 계획 확인

```sql
EXPLAIN SELECT gender, birth_date
FROM employees
WHERE birth_date >= '1965-01-01';
```

```
id | type  | key            | Extra
1  | range | ix_gender_bday | Using index for skip scan
```

`Using index for skip scan` 으로 표시된다.

### 스킵 스캔이 유리한 조건

|조건|이유|
|---|---|
|선두 컬럼의 카디널리티가 **낮을 것**|유니크 값이 적어야 반복 스캔 횟수가 적음|
|후행 컬럼의 카디널리티가 **높을 것**|인덱스 범위 스캔 효율이 높아야 함|
|커버링 인덱스 가능할 것|테이블 랜덤 I/O 없이 인덱스만으로 처리 가능|

### 스킵 스캔이 불리한 경우

```
선두 컬럼 유니크 값이 많으면 (카디널리티 高):
  반복 스캔 횟수 증가 → 풀 스캔보다 오히려 느릴 수 있음

예:
  인덱스: (dept_no, salary)  → dept_no 유니크 값 9개 → 스킵 스캔 유리
  인덱스: (emp_no, salary)   → emp_no 유니크 값 30만 개 → 스킵 스캔 불리
```

### 제어 방법

```sql
SET optimizer_switch = 'skip_scan=off';

-- 힌트로 특정 쿼리에만 적용/미적용
SELECT /*+ SKIP_SCAN(employees ix_gender_bday) */ * FROM employees
WHERE birth_date >= '1965-01-01';

SELECT /*+ NO_SKIP_SCAN(employees ix_gender_bday) */ * FROM employees
WHERE birth_date >= '1965-01-01';
```

## 9.3.1.19 해시 조인 (hash_join)

### 개념

조인 조건에 인덱스를 사용할 수 없거나, 대량 데이터를 조인할 때 **해시 테이블을 빌드하고 프로브하여 조인**하는 방식이다. MySQL 8.0.18부터 도입, 8.0.20부터 BNL을 완전히 대체한다.

### 네스티드 루프 조인과 비교

```
네스티드 루프 조인:
  for each row in 드라이빙 테이블:
      드리븐 테이블에서 인덱스로 조건 검색
  → 인덱스 있을 때 효율적, 없으면 매번 풀 스캔

해시 조인:
  1단계 (빌드): 작은 테이블 → 해시 테이블 생성
  2단계 (프로브): 큰 테이블 스캔하며 해시 테이블과 매칭
  → 인덱스 없어도 효율적
```

### 동작 단계 상세

#### 1단계: 빌드 (Build Phase)

```
빌드 입력(Build Input): 두 테이블 중 작은 쪽 선택
→ 조인 키를 해시 함수로 변환하여 해시 테이블 생성
→ join_buffer_size 크기의 메모리에 저장

해시 테이블:
  hash(dept_no) → {dept_no: 'd001', dept_name: 'Marketing'}
  hash(dept_no) → {dept_no: 'd002', dept_name: 'Finance'}
  ...
```

#### 2단계: 프로브 (Probe Phase)

```
프로브 입력(Probe Input): 큰 테이블을 순차 스캔
→ 각 레코드의 조인 키를 해시 함수로 변환
→ 해시 테이블에서 매칭 레코드 탐색 (O(1))
→ 매칭 시 결과에 추가
```

### 메모리 초과 시 처리 (청크 분할)

```
join_buffer_size < 빌드 입력 크기일 때:

1. 빌드 입력을 여러 청크로 분할
   → 청크별로 디스크에 저장 (청크 파일)
2. 청크 단위로 반복 처리:
   청크 1 → 해시 테이블 빌드 → 프로브 입력 스캔 → 매칭
   청크 2 → 해시 테이블 빌드 → 프로브 입력 스캔 → 매칭
   ...

→ 메모리 부족해도 처리 가능하나 디스크 I/O 발생
```

### 실행 계획 확인

```sql
EXPLAIN SELECT *
FROM employees e
JOIN dept_emp de ON e.emp_no = de.emp_no
WHERE e.hire_date > '2000-01-01';
```

```
id | table | type | Extra
1  | e     | ALL  | Using where
1  | de    | hash | Using join buffer (hash join)
```

`Using join buffer (hash join)` 으로 표시된다.

### 해시 조인 vs 네스티드 루프 조인 정리

|구분|네스티드 루프 조인|해시 조인|
|---|---|---|
|인덱스 필요 여부|필요 (없으면 비효율)|불필요|
|첫 번째 결과 반환|**빠름** (즉시 반환)|**느림** (빌드 완료 후)|
|전체 결과 처리|대용량 시 느림|대용량 시 **빠름**|
|메모리 사용|join_buffer 사용 안 함|join_buffer_size 의존|
|적합한 상황|OLTP, 소량 데이터, 인덱스 존재|OLAP, 대용량, 인덱스 없는 조인|

### 옵티마이저의 해시 조인 선택 기준

```
1. 조인 조건 컬럼에 인덱스가 없는 경우 → 해시 조인 우선 고려
2. 등치 조건(=) 조인인 경우 → 해시 조인 가능
   비등치 조건(>, <, BETWEEN) → 해시 조인 불가, 네스티드 루프만 가능
3. 빌드 입력(작은 테이블)이 join_buffer_size에 수용 가능한 경우 → 최적
```

> ⚠️ 해시 조인은 **등치(=) 조인에만 사용 가능**하다.  
> 범위 조건 조인은 여전히 네스티드 루프 조인을 사용한다.

# 9.3.2 조인 최적화 알고리즘

### 왜 조인 순서가 중요한가?

MySQL에서 조인은 **드라이빙 테이블 → 드리븐 테이블** 순서로 처리된다.  
조인하는 테이블이 많아질수록 **가능한 조인 순서의 수가 폭발적으로 증가**한다.

```
테이블 N개를 조인할 때 가능한 순서의 수:

N = 3  →  3! = 6가지
N = 4  →  4! = 24가지
N = 5  →  5! = 120가지
N = 10 →  10! = 3,628,800가지
N = 20 →  20! = 2,432,902,008,176,640,000가지 (사실상 불가능)
```

옵티마이저는 이 중 **가장 비용이 낮은 순서**를 선택해야 하므로,  
**어떤 알고리즘으로 탐색하느냐**가 실행 계획 수립 속도와 품질을 결정한다.

MySQL은 두 가지 알고리즘을 제공한다.

```
1. Exhaustive 검색 알고리즘 → 모든 경우의 수 탐색 (완전 탐색)
2. Greedy 검색 알고리즘    → 휴리스틱 기반 부분 탐색 (탐욕 탐색)
```

---

## 9.3.2.1 Exhaustive 검색 알고리즘

### 개념

`FROM` 절에 명시된 **모든 테이블의 조인 순서 조합을 전부 계산**하고,  
그 중 **최소 비용의 조인 순서를 선택**하는 방식이다.

MySQL 5.0 이전까지 사용하던 방식으로, **완전 탐색(Brute Force)** 이라고도 한다.

### 동작 원리

```
테이블: t1, t2, t3 (3개)

탐색하는 모든 순서:
  t1 → t2 → t3
  t1 → t3 → t2
  t2 → t1 → t3
  t2 → t3 → t1
  t3 → t1 → t2
  t3 → t2 → t1

각 순서마다 비용(cost) 계산
→ 최소 비용 순서 선택
```

```
테이블 N개일 때 탐색해야 하는 경우의 수: N! (팩토리얼)

N = 5  →  120가지  → 현실적
N = 10 →  3,628,800가지  → 느림
N = 15 →  1,307,674,368,000가지  → 사실상 불가능
```

### 문제점

```
조인 테이블 수가 많아질수록 실행 계획 수립 시간이 기하급수적으로 증가

실행 계획 수립에 걸리는 시간 > 실제 쿼리 실행 시간
→ 옵티마이저 자체가 병목이 되는 상황 발생
```

실제 쿼리가 아무리 빨라도, **최적 실행 계획을 찾는 시간 자체**가 서비스 성능 저하를 유발한다.

### 언제 사용되나?

```sql
-- optimizer_search_depth 로 제어
-- 0으로 설정 시 MySQL이 자동으로 Greedy/Exhaustive 전환
SET optimizer_search_depth = 0;  -- 자동 (기본값: 62)

-- Exhaustive를 강제하려면 테이블 수만큼 설정
-- (테이블이 4개면 4 이상으로 설정)
SET optimizer_search_depth = 62; -- 사실상 Exhaustive
```

`optimizer_search_depth` 값이 **조인 테이블 수 이상**이면 Exhaustive 검색이 수행된다.

### 비용 계산 방식

각 조인 순서에 대해 아래를 누적 계산한다.

```
비용 = Σ (각 단계별 드리븐 테이블 접근 비용)

접근 비용 계산 요소:
  - 드라이빙 테이블에서 읽히는 레코드 수
  - 드리븐 테이블의 인덱스 유무
  - 드리븐 테이블의 레코드 수
  - 조인 버퍼 사용 여부
  - 통계 정보 (rows, filtered)
```

### Exhaustive 알고리즘 흐름 요약

```
INPUT:  테이블 목록 [t1, t2, t3, ..., tN]

FOR each permutation in N!:
    cost = 0
    FOR each (driving, driven) pair in permutation:
        cost += calculate_join_cost(driving, driven)
    IF cost < best_cost:
        best_cost = cost
        best_order = permutation

OUTPUT: best_order
```

### 한계 정리

|항목|내용|
|---|---|
|탐색 범위|모든 순서 (N!)|
|결과 품질|**항상 최적** (완전 탐색이므로)|
|수립 시간|테이블 수 증가 시 **기하급수적 증가**|
|실용 한계|테이블 **10개 이상**에서 현실적으로 사용 불가|
|MySQL에서 위치|`optimizer_search_depth >= 조인 테이블 수` 일 때 동작|

## 📌 Exhaustive vs Greedy 비교 (예고)

다음 챕터에서 다룰 **Greedy 검색 알고리즘**과의 비교를 미리 구조로 파악해두자.

```
Exhaustive 검색:
  장점: 항상 최적의 조인 순서 보장
  단점: 테이블 수 증가 시 탐색 시간 폭발적 증가 (N!)
```
