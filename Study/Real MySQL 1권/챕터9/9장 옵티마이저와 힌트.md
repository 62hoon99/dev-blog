# MySQL 실행 계획 & 옵티마이저

## 9.1 쿼리 실행 절차

### 9.1.1 실행 절차 3단계

MySQL 서버에서 쿼리가 실행되는 과정은 크게 세 단계로 나뉜다.

|단계|담당|설명|
|---|---|---|
|1단계|SQL 파서|SQL 문장을 토큰으로 분리해 트리 형태의 파스 트리 생성|
|2단계|SQL 옵티마이저|파스 트리를 기반으로 최적의 실행 계획 수립 (테이블 읽기 순서, 인덱스 선택 등)|
|3단계|SQL 실행기|실행 계획에 따라 스토리지 엔진을 호출해 실제 데이터를 읽고 조인/정렬 등 처리|

> **핵심:** 2단계(옵티마이저)가 실질적인 성능을 결정한다. `EXPLAIN`으로 이 단계의 결과를 확인할 수 있다.

---

### 9.1.2 옵티마이저의 종류

|구분|설명|현황|
|---|---|---|
|**규칙 기반 최적화 (RBO)**|미리 정해진 우선순위 규칙에 따라 실행 계획 결정. 데이터 분포/통계 무시|거의 사용 안 함 (구시대적)|
|**비용 기반 최적화 (CBO)**|각 실행 계획의 비용(Cost)을 예측해 가장 낮은 비용의 계획 선택|MySQL 포함 대부분의 RDBMS 채택|

> MySQL의 비용 계산 기준: **레코드 건수**, **인덱스의 선택도(Cardinality)**, **I/O 비용**, **CPU 비용** 등을 종합적으로 고려

## 9.2 기본 데이터 처리

### 9.2.1 풀 테이블 스캔 vs 풀 인덱스 스캔

#### 풀 테이블 스캔 선택 조건

옵티마이저가 아래 조건에 해당한다고 판단하면 인덱스 대신 풀 테이블 스캔을 선택한다.

|조건|설명|
|---|---|
|소규모 테이블|레코드 수가 적어 풀 스캔이 인덱스 탐색보다 오히려 빠른 경우|
|인덱스 부재|WHERE/ON 절에 인덱스를 활용할 수 있는 조건 자체가 없는 경우|
|높은 선택도|인덱스 레인지 스캔이 가능해도 일치 레코드 비율이 너무 높아 Full Scan이 유리한 경우|

> **일반적으로 전체 레코드의 20~25% 이상을 읽어야 하면** 옵티마이저는 인덱스보다 풀 테이블 스캔을 선택하는 경향이 있다.

#### 풀 인덱스 스캔

- 인덱스만으로 쿼리를 처리할 수 있을 때(커버링 인덱스), 테이블 전체 대신 **인덱스 전체를 스캔**
- 인덱스는 테이블보다 크기가 작아 **I/O 부담이 적음**

```sql
-- 예시: COUNT(*) 는 PK 인덱스만 풀 스캔해도 처리 가능
SELECT COUNT(*) FROM orders;
```

---

### 리드 어헤드 (Read Ahead)

풀 스캔 시 성능을 높이기 위한 InnoDB의 백그라운드 최적화 메커니즘.

```
[InnoDB 리드 어헤드 동작 흐름]

연속된 데이터 페이지 읽기 감지
        ↓
백그라운드 스레드가 이후 페이지를 미리 버퍼 풀에 적재
        ↓
포그라운드 스레드는 I/O 대기 없이 버퍼 풀에서 즉시 데이터 읽기
```

|항목|내용|
|---|---|
|적용 범위|풀 테이블 스캔 + **풀 인덱스 스캔 모두 적용**|
|트리거 조건|연속된 페이지를 일정 수 이상 읽을 때 자동 시작|
|관련 설정|`innodb_read_ahead_threshold` (기본값: 56)|

> `innodb_read_ahead_threshold`: 선형 리드 어헤드가 트리거되기 위해 순차적으로 읽어야 하는 페이지 수 기준값

## EXPLAIN 빠른 참고

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1;
```

|주요 컬럼|의미|
|---|---|
|`type`|접근 방식 (ALL = 풀 스캔, range, ref, const 등)|
|`key`|실제 사용된 인덱스|
|`rows`|옵티마이저가 예측한 읽을 레코드 수|
|`Extra`|Using filesort, Using temporary 등 추가 처리 정보|

> `type = ALL` → 풀 테이블 스캔. 대용량 테이블에서 나오면 인덱스 추가를 검토해야 한다.
# 9.2.2 병렬 처리

MySQL 8.0부터 제한적인 병렬 처리가 지원된다.

|항목|내용|
|---|---|
|**지원 범위**|WHERE 조건 없는 단순 전체 건수 조회만 해당|
|**관련 변수**|`innodb_parallel_read_threads` (기본값: 4)|
|**제약**|복잡한 JOIN, 서브쿼리, 일반 SELECT 등에는 미적용|

```sql
-- 병렬 처리 적용 가능 예시
SELECT COUNT(*) FROM orders;

-- 병렬 처리 미적용 (WHERE 조건 있음)
SELECT COUNT(*) FROM orders WHERE status = 'PAID';
```

> 아직 Oracle, PostgreSQL 등 다른 RDBMS에 비해 병렬 처리 지원 범위가 매우 제한적이다.

# 9.2.3 ORDER BY 처리

정렬 처리 방식은 크게 두 가지로 나뉜다.

|구분|인덱스 이용|Filesort 이용|
|---|---|---|
|**속도**|빠름 (이미 정렬된 상태)|느림 (별도 정렬 수행)|
|**부가 I/O**|없음|있음 (소트 버퍼 ↔ 디스크)|
|**EXPLAIN Extra**|표시 없음|`Using filesort`|
|**적용 조건**|인덱스 컬럼 순서와 ORDER BY 컬럼 순서 일치 필요|제약 없음|

#### 인덱스 정렬이 불가능한 대표 케이스

- 정렬 기준이 너무 많아 모든 경우의 인덱스 생성이 불가능한 경우
- `GROUP BY`, `DISTINCT` 처리 결과를 재정렬해야 하는 경우
- `UNION` 등 임시 테이블 결과를 재정렬해야 하는 경우
- `ORDER BY RAND()` 처럼 랜덤하게 결과를 가져와야 하는 경우

## 9.2.3.1 소트 버퍼 (Sort Buffer)

### 개념

MySQL이 **정렬 전용으로 할당하는 세션 레벨 메모리 공간**이다.

```
정렬 쿼리 실행
    ↓
소트 버퍼 할당 (sort_buffer_size 한도 내에서 가변 할당)
    ↓
버퍼가 가득 참 → 임시 디스크에 저장 (청크 분할)
    ↓
모든 청크 정렬 완료 후 멀티 머지(Multi-merge)로 병합
    ↓
최종 정렬 결과 반환 / 소트 버퍼 해제
```

### 핵심 특성

|항목|내용|
|---|---|
|**할당 시점**|정렬이 필요한 쿼리 실행 시에만 할당|
|**크기**|정렬 대상 레코드 크기에 따라 가변, 최대 `sort_buffer_size`|
|**범위**|세션(커넥션)별로 독립 할당|
|**기본값**|약 256KB (`sort_buffer_size`)|

```sql
-- 현재 설정 확인
SHOW VARIABLES LIKE 'sort_buffer_size';

-- 세션 레벨 조정 (대용량 정렬 쿼리 실행 전)
SET SESSION sort_buffer_size = 1024 * 1024 * 8; -- 8MB
```

### 멀티 머지 (Multi-merge)

정렬 대상이 소트 버퍼보다 클 때 발생하는 **분할 정렬 후 병합** 과정.

```
[레코드 10만 건, 소트 버퍼 1MB 가정]

1회: 1만 건 정렬 → 디스크 청크 #1 저장
2회: 1만 건 정렬 → 디스크 청크 #2 저장
...
N회: 나머지 정렬 → 디스크 청크 #N 저장
        ↓
전체 청크 머지(병합) → 최종 정렬 결과
```

- 청크 수가 많을수록 **디스크 읽기/쓰기 횟수 증가** → 성능 저하
- 멀티 머지 횟수는 `Sort_merge_passes` 상태 변수로 확인 가능

```sql
SHOW STATUS LIKE 'Sort_merge_passes';
-- 값이 크면 sort_buffer_size 증가를 검토
```

### ⚠️ OOM-Killer 주의

소트 버퍼는 **커넥션(세션)마다 독립적으로 할당**되기 때문에, 동시 커넥션이 많은 환경에서 `sort_buffer_size`를 무작정 크게 설정하면 물리 메모리를 초과할 수 있다.

```
동시 커넥션 200개 × sort_buffer_size 8MB = 최대 1.6GB 소트 버퍼 사용 가능
→ 다른 메모리(버퍼 풀, 커넥션 스택 등)까지 합산하면 OOM 발생 위험
→ Linux OOM-Killer가 mysqld 프로세스를 강제 종료할 수 있음
```

| 권장 전략            | 내용                             |
| ---------------- | ------------------------------ |
| 글로벌 값은 보수적으로     | 256KB ~ 1MB 수준 유지              |
| 대용량 정렬은 세션 레벨 조정 | 배치/분석 쿼리 실행 직전 세션 변수만 증가       |
| 근본 해결책           | 정렬 컬럼에 인덱스 추가로 Filesort 자체를 제거 |
# 9.2.3.2 정렬 알고리즘

MySQL의 Filesort는 **싱글 패스**와 **투 패스** 두 가지 알고리즘으로 나뉜다.

## 싱글 패스 (Single Pass) — 기본값

정렬 기준 컬럼 + **SELECT 대상 컬럼 전체**를 소트 버퍼에 담아 한 번에 정렬한다.

```
[실행 흐름]
테이블에서 레코드 읽기
    ↓
정렬 키 + SELECT 컬럼 전체를 소트 버퍼에 저장
    ↓
정렬 수행 (멀티 머지 포함)
    ↓
정렬된 결과를 그대로 클라이언트에 반환 (추가 읽기 없음)
```

|항목|내용|
|---|---|
|**테이블 읽기 횟수**|1회|
|**소트 버퍼 사용량**|많음 (모든 SELECT 컬럼 포함)|
|**적합한 상황**|레코드당 컬럼 크기가 작을 때|

---

## 투 패스 (Two Pass) — 레거시 방식

정렬 기준 컬럼 + **PK만** 소트 버퍼에 담아 정렬 후, 정렬된 PK로 테이블을 다시 읽는다.

```
[실행 흐름]
1️⃣ Pass 1 — 정렬
테이블에서 정렬 키 + PK만 소트 버퍼에 저장
    ↓
정렬 수행

2️⃣ Pass 2 — 데이터 조회
정렬된 PK 순서대로 테이블을 다시 읽어 SELECT 컬럼 조회
    ↓
클라이언트에 반환
```

|항목|내용|
|---|---|
|**테이블 읽기 횟수**|2회|
|**소트 버퍼 사용량**|적음 (PK + 정렬 키만)|
|**적합한 상황**|레코드당 컬럼 크기가 매우 클 때|

---

## 싱글 패스 vs 투 패스 비교

|구분|싱글 패스|투 패스|
|---|---|---|
|테이블 읽기|1회|2회|
|소트 버퍼 효율|낮음 (컬럼 전체 저장)|높음 (PK만 저장)|
|랜덤 I/O|없음|있음 (PK로 재조회 시)|
|레코드 크기 작을 때|✅ 유리|불리|
|레코드 크기 클 때|불리 (버퍼 낭비)|✅ 유리|

> MySQL은 기본적으로 싱글 패스를 사용하지만, **레코드 크기가 `max_length_for_sort_data`(기본 4KB)를 초과**하면 자동으로 투 패스로 전환한다.

```sql
SHOW VARIABLES LIKE 'max_length_for_sort_data';
```

# 9.2.3.3 정렬 처리 방법

처리 방법에 따라 EXPLAIN의 Extra 컬럼 표시가 달라진다.

|정렬 처리 방법|EXPLAIN Extra 표시|성능|
|---|---|---|
|인덱스 이용 정렬|(없음)|✅ 가장 빠름|
|드라이빙 테이블만 정렬|`Using filesort`|중간|
|임시 테이블 이용 후 정렬|`Using temporary; Using filesort`|❌ 가장 느림|

---

## ① 인덱스를 이용한 정렬

인덱스가 이미 정렬된 상태이므로 **별도 정렬 작업 없이** 인덱스 순서대로 읽어 반환한다.

```sql
-- (user_id, created_at) 복합 인덱스가 있을 때
SELECT * FROM orders
WHERE user_id = 1
ORDER BY user_id, created_at;
-- → Extra: (없음) — 인덱스 순서 그대로 읽으면 됨
```

**적용 조건 (모두 만족해야 함)**

- ORDER BY 컬럼이 인덱스 컬럼과 순서/방향 일치
- WHERE + ORDER BY 컬럼이 동일 인덱스 내에 존재
- 조인 시 드라이빙 테이블의 컬럼으로만 정렬

---

## ② 드라이빙 테이블만 정렬 (조인 전 정렬)

조인 전에 드라이빙 테이블의 레코드를 먼저 정렬하고, 이후 드리븐 테이블과 조인한다. 조인 후 전체를 정렬하는 것보다 **정렬 대상 레코드 수가 적다.**

```
드라이빙 테이블 조회
    ↓
소트 버퍼에서 정렬 수행 (Filesort)
    ↓
정렬된 순서대로 드리븐 테이블과 조인
    ↓
결과 반환
```

```sql
-- orders가 드라이빙, users가 드리븐 테이블일 때
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
ORDER BY o.created_at;
-- → Extra: Using filesort (드라이빙 테이블 기준 정렬)
```

**조건:** ORDER BY 컬럼이 **드라이빙 테이블 소속**이어야 함

---

## ③ 임시 테이블을 이용한 정렬 (조인 후 정렬)

조인 결과 전체를 임시 테이블에 저장한 뒤 정렬한다. 레코드 수가 가장 많은 상태에서 정렬하므로 **가장 비효율적이다.**

```
드라이빙 테이블 조회
    ↓
드리븐 테이블과 조인
    ↓
전체 결과를 임시 테이블에 저장
    ↓
임시 테이블 대상으로 Filesort 수행
    ↓
결과 반환
```

```sql
-- ORDER BY 컬럼이 드리븐 테이블(users) 소속일 때
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
ORDER BY u.name;
-- → Extra: Using temporary; Using filesort
```

**발생 조건:** ORDER BY 컬럼이 **드리븐 테이블 소속**이거나, `UNION` / `GROUP BY` + `ORDER BY` 조합

---

## 정렬 튜닝 체크리스트

```
1. EXPLAIN Extra에 Using filesort 가 있는가?
   → ORDER BY 컬럼에 인덱스 추가 검토

2. Using temporary; Using filesort 가 같이 있는가?
   → 조인 순서 변경 또는 서브쿼리 리팩토링 검토

3. Sort_merge_passes 값이 높은가?
   → sort_buffer_size 증가 검토 (단, OOM 주의)

4. ORDER BY 컬럼이 드리븐 테이블 소속인가?
   → 드라이빙/드리븐 테이블 순서 변경 검토
```

# 정렬 처리 방법의 성능 비교

웹 서비스용 쿼리에서는 `ORDER BY`와 함께 `LIMIT`이 거의 필수로 사용된다. 일반적으로 `LIMIT`은 테이블이나 처리 결과의 일부만 가져오기 때문에 MySQL 서버가 처리해야 할 작업량을 줄이는 역할을 한다.

그러나 `ORDER BY`나 `GROUP BY` 같은 작업은 `WHERE` 조건을 만족하는 레코드를 `LIMIT` 건수만큼만 가져와서 처리할 수 없다. 우선 조건을 만족하는 **모든 레코드를 가져온 후** 정렬하거나 그루핑해야만 비로소 `LIMIT`으로 건수를 제한할 수 있다. 그렇기 때문에 `WHERE` 조건이 아무리 인덱스를 잘 활용해도 잘못된 `ORDER BY`나 `GROUP BY` 때문에 쿼리가 느려지는 경우가 자주 발생한다.

쿼리가 처리되는 방식을 **스트리밍 처리**와 **버퍼링 처리** 2가지로 구분해보자.

---

## 스트리밍 방식 (Streaming)

서버 쪽에서 처리할 데이터가 얼마인지에 관계없이, **조건에 일치하는 레코드가 검색될 때마다 즉시 클라이언트로 전송**하는 방식이다.

클라이언트는 MySQL이 레코드를 찾는 즉시 전달받기 때문에 **데이터를 받으면서 동시에 가공 작업을 시작**할 수 있다. 또한 `LIMIT`처럼 결과 건수를 제한하는 조건은 쿼리의 전체 실행 시간을 상당히 줄여줄 수 있다.

**핵심 포인트**

- 첫 번째 레코드가 준비되는 즉시 전송하므로 **첫 번째 레코드까지의 응답 시간(Time To First Row)**이 빠르다.
- `LIMIT n`이 걸려 있으면 n개 레코드가 모이는 순간 쿼리 실행을 중단할 수 있어 전체 실행 시간이 단축된다.
- 인덱스 레인지 스캔으로 처리되는 단순 `SELECT`가 대표적인 스트리밍 처리 예시다.

---

## 버퍼링 방식 (Buffering)

`ORDER BY`나 `GROUP BY` 같은 처리는 스트리밍을 **불가능하게** 만든다. `WHERE` 조건에 일치하는 **모든 레코드를 가져온 후**, 정렬하거나 그루핑한 뒤에 차례대로 보내야 하기 때문이다.

MySQL 서버에서 모든 레코드를 검색하고 정렬하는 동안 **클라이언트는 아무것도 하지 않고 기다려야 하므로** 응답 속도가 느려진다.

**핵심 포인트**

- `LIMIT`이 있어도 도움이 되지 않는다. 정렬/그루핑 연산은 전체 결과를 확정하기 전까지 몇 개를 클라이언트에 보낼지 알 수 없기 때문이다.
- MySQL 내부적으로 **소트 버퍼(Sort Buffer)**를 사용한다. 정렬 대상 데이터가 소트 버퍼 크기를 초과하면 **임시 파일(External Sort, 디스크 I/O)**을 활용한 **멀티 패스 병합 정렬**이 발생해 성능이 크게 저하된다.
- `SHOW STATUS LIKE 'Sort_%'` 명령으로 정렬 관련 상태 변수를 확인할 수 있다.

|상태 변수|설명|
|---|---|
|`Sort_rows`|정렬된 전체 레코드 수|
|`Sort_merge_passes`|소트 버퍼 간 병합(Merge) 횟수. 이 값이 높으면 소트 버퍼 크기를 늘리거나 인덱스 정렬을 검토해야 한다|
|`Sort_range`|인덱스 레인지 스캔 후 정렬한 횟수|
|`Sort_scan`|풀 테이블 스캔 후 정렬한 횟수|

---

## JDBC의 버퍼링

MySQL 서버는 스트리밍 방식으로 데이터를 반환하지만, **JDBC 드라이버는 내부적으로 결과셋 전체를 메모리에 버퍼링**한 뒤 애플리케이션에 전달한다. 즉, 애플리케이션 입장에서는 항상 버퍼링 방식처럼 동작한다.

진정한 스트리밍 처리(서버 사이드 커서)가 필요하다면 JDBC URL에 `useCursorFetch=true` 옵션을 추가하거나, `Statement.setFetchSize(Integer.MIN_VALUE)` 등을 활용해야 한다. 단, 이 경우 커넥션 점유 시간이 길어지므로 커넥션 풀 설정과 트레이드오프를 고려해야 한다.

---

## 정렬 처리 방식의 성능 우선순위

어떤 테이블이 먼저 드라이빙되어 조인되는지도 중요하지만, **어떤 정렬 방식으로 처리되는지가 더 큰 성능 차이**를 만든다. 성능이 좋은 순서는 아래와 같다.

```
1순위: 인덱스를 이용한 정렬 (소트 버퍼 사용 없음)
2순위: 드라이빙 테이블만 정렬 후 조인 (소트 버퍼 사용량 최소화)
3순위: 조인 결과 전체를 정렬 (소트 버퍼 사용량 최대)
```

가능하다면 인덱스를 사용한 정렬을 유도하고, 그렇지 못하다면 최소한 **드라이빙 테이블만 정렬**해도 되는 수준으로 유도하는 것이 좋은 튜닝 방법이다.

---

## 정렬 관련 상태 변수

MySQL은 정렬 처리 실행 횟수를 상태 변수로 저장한다. 아래 명령으로 확인할 수 있다.

```sql
FLUSH STATUS;
-- 쿼리 실행
SHOW STATUS LIKE 'Sort_%';
```

`Sort_merge_passes`가 높게 나온다면 `sort_buffer_size` 시스템 변수를 늘리거나, 인덱스 정렬로 전환하는 것을 검토해야 한다.

## GROUP BY 처리

`GROUP BY` 역시 `ORDER BY`와 마찬가지로 **스트리밍 처리를 불가능하게 만드는** 연산이다.

- `HAVING` 절은 `GROUP BY` 결과에 대한 필터링 역할을 수행한다.
- `GROUP BY`에 사용된 조건은 인덱스를 사용해서 처리될 수 없으므로, `HAVING` 절 튜닝을 위해 인덱스를 생성할 필요는 없다. `HAVING`이 아닌 `WHERE` 절에서 미리 필터링하는 것이 훨씬 효과적이다.

`GROUP BY` 처리 방식은 크게 3가지로 나뉜다.

---

### 1. 인덱스 스캔을 이용하는 GROUP BY (타이트 인덱스 스캔)

`GROUP BY` 컬럼이 인덱스의 선두 컬럼과 일치할 때 사용된다. 인덱스를 순서대로 읽으면서 그루핑을 수행하므로 **별도의 정렬 작업이 필요 없다**. 가장 빠른 처리 방식이다.

```sql
-- (col1, col2) 복합 인덱스가 있을 때
SELECT col1, col2, COUNT(*) FROM t GROUP BY col1, col2;
-- → 인덱스 순서와 GROUP BY 순서가 일치 → 타이트 인덱스 스캔
```

`EXPLAIN` 결과의 `Extra` 컬럼에 `Using index for group-by`가 표시되거나, 별다른 추가 정렬 표시 없이 인덱스를 활용한다.

---

### 2. 루스 인덱스 스캔을 이용하는 GROUP BY (Loose Index Scan)

인덱스의 **일부 레코드만 건너뛰면서** 필요한 그룹의 대표값만 읽는 방식이다. 주로 `MIN()`, `MAX()` 같은 집계 함수와 함께 사용될 때 최적화된다.

```sql
-- (col1, col2) 인덱스가 있을 때
SELECT col1, MIN(col2) FROM t GROUP BY col1;
-- → col1별로 인덱스의 첫 번째 값만 읽으면 되므로 루스 인덱스 스캔 가능
```

`EXPLAIN`의 `Extra` 컬럼에 `Using index for group-by`가 표시된다. 인덱스를 전부 읽지 않고 건너뛰기 때문에 **매우 효율적**이다.

---

### 3. 임시 테이블을 이용하는 GROUP BY

인덱스를 전혀 사용할 수 없을 때 MySQL은 **내부 임시 테이블**을 생성해 그루핑 작업을 수행한다. 가장 느린 방식이며, `EXPLAIN`의 `Extra` 컬럼에 `Using temporary`가 표시된다.

인덱스 설계 시 자주 쓰는 `GROUP BY` 컬럼을 인덱스 선두에 배치하면 이 케이스를 피할 수 있다.

---

## 9.2.5 DISTINCT 처리

특정 컬럼의 유니크한 값만 조회하려면 `SELECT` 쿼리에 `DISTINCT`를 사용한다. `DISTINCT`는 **집합 함수와 함께 사용되는 경우**와 **집합 함수 없이 단독으로 사용되는 경우**로 나누어 살펴봐야 한다. 각 경우에 `DISTINCT`가 영향을 미치는 범위가 달라지기 때문이다.

---

### SELECT DISTINCT

`DISTINCT`는 **레코드(행) 단위**로 동작한다. 컬럼 단위가 아니다.

```sql
SELECT DISTINCT first_name, last_name FROM employees;
```

위 쿼리는 `first_name`만 유니크하게 가져오는 것이 아니라, `(first_name, last_name)` 조합이 유니크한 레코드를 가져온다.

```sql
-- 아래 두 쿼리는 완전히 동일하다. 괄호는 의미 없다.
SELECT DISTINCT(first_name), last_name FROM employees;
SELECT DISTINCT first_name, last_name FROM employees;
```

`DISTINCT` 바로 뒤에 괄호를 붙이더라도 해당 컬럼에만 작용하는 것이 **아니다**. `DISTINCT`는 함수가 아니기 때문에 괄호가 있어도 `SELECT` 절 전체 컬럼 조합에 대해 중복을 제거한다. 이 점은 실수하기 쉬운 부분이므로 주의가 필요하다.

**인덱스 활용 여부**

`DISTINCT`만 단독으로 사용될 때, `DISTINCT` 처리 컬럼에 인덱스가 있다면 인덱스를 순서대로 읽으면서 중복을 제거할 수 있으므로 **임시 테이블 없이** 처리된다. 반면 인덱스가 없으면 임시 테이블을 사용하게 된다.

```sql
-- employees 테이블의 first_name에 인덱스가 있다면
SELECT DISTINCT first_name FROM employees;
-- → 인덱스 스캔만으로 처리 가능 (Using index, 임시 테이블 불필요)
```

---

### 집합 함수와 함께 사용된 DISTINCT

집합 함수(`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) 내부에서 사용된 `DISTINCT`는 **해당 집합 함수의 인자로 전달된 컬럼값이 유니크한 것들**만 대상으로 집계한다. `SELECT DISTINCT`와는 영향 범위가 다르다.

```sql
SELECT COUNT(DISTINCT first_name), COUNT(DISTINCT last_name)
FROM employees
WHERE emp_no BETWEEN 10001 AND 10100;
```

위 쿼리는 `first_name`의 중복을 제거한 COUNT와 `last_name`의 중복을 제거한 COUNT를 **동시에** 구한다. 이 경우 MySQL은 각 `DISTINCT` 집합 함수마다 **별도의 임시 테이블**을 내부적으로 생성한다. 즉, 위 쿼리는 임시 테이블이 **2개** 생성된다.

```sql
-- 임시 테이블 1개가 생성되는 경우
SELECT COUNT(DISTINCT first_name)
FROM employees
WHERE emp_no BETWEEN 10001 AND 10100;
```

```sql
-- 인덱스를 타는 경우 (임시 테이블 불필요)
-- first_name 컬럼에 인덱스가 있다면
SELECT COUNT(DISTINCT first_name)
FROM employees;
-- → 인덱스를 루스 인덱스 스캔으로 읽어 임시 테이블 없이 처리
```

**정리**

|상황|임시 테이블|
|---|---|
|`COUNT(DISTINCT col)` 1개, 인덱스 없음|1개 생성|
|`COUNT(DISTINCT col1)`, `COUNT(DISTINCT col2)`|2개 생성|
|`COUNT(DISTINCT col)`, 해당 컬럼에 인덱스 있음|생성 안 함|

## 내부 임시 테이블 활용

MySQL 엔진은 스토리지 엔진으로부터 받은 레코드를 정렬하거나 그루핑할 때 내부적으로 임시 테이블을 사용한다.

- 내부 임시 테이블은 **실제 물리적인 테이블을 만드는 것이 아니며**, 쿼리 처리가 완료되면 **자동으로 삭제**된다.
- 사용자가 직접 생성하는 `CREATE TEMPORARY TABLE`과는 다르다.
- `EXPLAIN` 결과의 `Extra` 컬럼에 `Using temporary`가 표시되면 내부 임시 테이블이 사용된다는 신호다.

임시 테이블을 유발하는 대표적인 연산은 아래와 같다.

- `ORDER BY`와 `GROUP BY`에 사용된 컬럼이 다를 때
- `ORDER BY`나 `GROUP BY`가 조인의 드라이빙 테이블이 아닌 컬럼을 참조할 때
- `DISTINCT`와 `ORDER BY`가 동시에 사용될 때
- `UNION`, `UNION ALL`
- 서브쿼리나 뷰의 일부 경우

---

### 메모리 임시 테이블과 디스크 임시 테이블

임시 테이블은 처음에는 메모리에 생성되었다가, 크기가 특정 임계값을 초과하면 디스크로 변환된다.

**MySQL 8.0 이전**

|위치|스토리지 엔진|특징|
|---|---|---|
|메모리|MEMORY|고정 길이 컬럼만 지원, BLOB/TEXT 불가|
|디스크|MyISAM|트랜잭션 미지원, 크래시 취약|

MEMORY 엔진은 가변 길이 타입(`VARCHAR`, `BLOB`, `TEXT`)을 고정 길이로 처리하기 때문에 메모리 낭비가 심하고, MyISAM은 트랜잭션을 지원하지 않아 비정상 종료 시 데이터 무결성 문제가 발생할 수 있었다.

**MySQL 8.0 이후**

|위치|스토리지 엔진|특징|
|---|---|---|
|메모리|TempTable|가변 길이 타입 지원, 메모리 효율 개선|
|디스크|InnoDB|트랜잭션 지원, 크래시 복구 가능|

`TempTable` 엔진은 `VARCHAR`, `VARBINARY` 등 가변 길이 타입을 그대로 처리할 수 있어 메모리 낭비가 줄었고, 디스크 임시 테이블도 `InnoDB`로 변경되어 안정성이 향상됐다.

관련 시스템 변수:

```sql
-- 메모리 임시 테이블 최대 크기 (기본값: 16MB)
SHOW VARIABLES LIKE 'tmp_table_size';
SHOW VARIABLES LIKE 'max_heap_table_size';

-- TempTable 엔진 최대 메모리 크기 (MySQL 8.0, 기본값: 1GB)
SHOW VARIABLES LIKE 'temptable_max_ram';
```

메모리 임시 테이블이 `tmp_table_size` 또는 `max_heap_table_size` 중 작은 값을 초과하면 디스크 임시 테이블로 변환된다.

---

### 임시 테이블이 디스크에 생성되는 경우

아래 조건에 해당하면 처음부터 디스크에 임시 테이블이 생성된다.

- `UNION`이나 `UNION ALL`에서 `SELECT`되는 컬럼 중 **512바이트 이상**인 컬럼이 있는 경우
- `GROUP BY`나 `DISTINCT` 컬럼 중 **512바이트 이상**인 컬럼이 있는 경우
- 메모리 임시 테이블의 크기가 `tmp_table_size` 또는 `max_heap_table_size` 설정값보다 커진 경우
- `BLOB`, `TEXT` 타입의 컬럼이 포함된 경우 (MySQL 8.0 이전 MEMORY 엔진의 한계)

디스크 임시 테이블은 메모리 임시 테이블보다 훨씬 느리므로, 자주 실행되는 쿼리에서 `Using temporary`가 보인다면 인덱스 튜닝이나 쿼리 재작성을 검토해야 한다. `SHOW STATUS LIKE 'Created_tmp_disk_tables'` 값이 높다면 디스크 임시 테이블이 자주 생성되고 있다는 신호다.

```sql
-- 임시 테이블 생성 현황 확인
SHOW STATUS LIKE 'Created_tmp%';
-- Created_tmp_disk_tables : 디스크에 생성된 임시 테이블 수
-- Created_tmp_tables      : 전체 임시 테이블 생성 수 (메모리 + 디스크)
```

`Created_tmp_disk_tables / Created_tmp_tables` 비율이 높다면 `tmp_table_size`와 `max_heap_table_size`를 늘리는 것을 고려해볼 수 있다. 단, 메모리 자원 한도 내에서 조정해야 한다.

## 드라이빙 테이블 (Driving Table)

조인(JOIN)을 실행할 때 MySQL은 두 테이블을 동시에 처리하지 않고, **한 테이블을 먼저 읽은 뒤 그 결과를 기준으로 다른 테이블을 검색**하는 방식으로 동작한다.

- **드라이빙 테이블** (Driving Table): 조인에서 **먼저** 읽히는 테이블. 외부 테이블(Outer Table)이라고도 한다.
- **드리븐 테이블** (Driven Table): 드라이빙 테이블을 읽은 후 **나중에** 검색되는 테이블. 내부 테이블(Inner Table)이라고도 한다.

---

### 동작 방식

MySQL의 기본 조인 알고리즘인 **중첩 루프 조인(Nested Loop Join)** 기준으로 보면 아래와 같다.

```
for each row in 드라이빙 테이블:         -- 외부 루프 (1회 풀스캔)
    for each row in 드리븐 테이블:       -- 내부 루프 (드라이빙 행 수만큼 반복)
        if 조인 조건 일치:
            결과에 추가
```

드라이빙 테이블은 **한 번만 읽히고**, 드리븐 테이블은 **드라이빙 테이블의 레코드 수만큼 반복해서 검색**된다. 따라서 드리븐 테이블의 조인 컬럼에 인덱스가 없으면 매 루프마다 풀 테이블 스캔이 발생해 성능이 급격히 떨어진다.

---

### 드라이빙 테이블이 중요한 이유

드라이빙 테이블이 어떤 테이블이냐에 따라 성능 차이가 크게 난다.

**드라이빙 테이블 선택 기준 (옵티마이저 관점)**

- 드라이빙 테이블은 **결과 행 수가 적을수록** 유리하다. 외부 루프 횟수가 줄어들기 때문이다.
- 드리븐 테이블은 **조인 컬럼에 인덱스가 있어야** 한다. 인덱스가 없으면 매 루프마다 풀스캔이 발생한다.

```sql
SELECT *
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = 'PAID';
```

위 쿼리에서 `WHERE` 조건으로 `orders`가 먼저 필터링되어 행 수가 줄어든다면, MySQL 옵티마이저는 `orders`를 드라이빙 테이블로 선택하고 `order_items`를 드리븐 테이블로 사용할 가능성이 높다. 이때 `order_items.order_id`에 인덱스가 있어야 효율적이다.

---

### EXPLAIN으로 확인하기

```sql
EXPLAIN SELECT * FROM orders o JOIN order_items oi ON o.order_id = oi.order_id;
```

`EXPLAIN` 결과에서 **위에 출력되는 테이블이 드라이빙 테이블**, 아래가 드리븐 테이블이다.

```
+----+-------------+-------+------+...
| id | select_type | table | type |...
+----+-------------+-------+------+...
|  1 | SIMPLE      | o     | ref  |...   ← 드라이빙 테이블
|  1 | SIMPLE      | oi    | ref  |...   ← 드리븐 테이블
+----+-------------+-------+------+...
```

옵티마이저가 잘못된 드라이빙 테이블을 선택했다고 판단되면 `STRAIGHT_JOIN` 힌트로 순서를 강제할 수 있지만, 대부분의 경우 인덱스를 올바르게 설계하면 옵티마이저가 알아서 좋은 순서를 선택한다.
