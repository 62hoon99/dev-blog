
MySQL 엔진은 스토리지 엔진을 제외한 나머지 부분을 가리킨다. MySQL 엔진 레벨의 잠금은 모든 스토리지 엔진에 영향을 미치지만, 스토리지 엔진 레벨의 잠금은 엔진 간 상호 영향을 미치지 않는다.

---

## 5.2.1 글로벌 락 (Global Lock)

MySQL이 제공하는 잠금 중 범위가 가장 크다. 한 세션에서 글로벌 락을 획득하면, 다른 세션의 `SELECT`를 제외한 대부분의 DDL·DML 문장은 잠금이 해제될 때까지 대기 상태가 된다. 작업 대상 테이블이나 데이터베이스가 달라도 MySQL 서버 전체에 동일하게 영향을 미친다.

InnoDB는 트랜잭션을 지원하기 때문에, MyISAM과 달리 데이터 일관성을 위해 모든 변경 작업을 멈출 필요가 없다. InnoDB가 대중화되면서 MySQL 8.0부터는 백업 툴의 안정적인 실행을 위해 **백업 락**이 도입됐다.

### 백업 락

- 일반적인 테이블 데이터 변경은 **허용**한다.
- 백업 중 DDL 명령이 실행되면 백업을 **중단**한다.
- 복제는 정상적으로 계속 실행되지만, 백업 실패를 방지하기 위해 DDL 명령이 들어오면 복제를 **일시 중지**시킨다.

---

## 5.2.2 테이블 락 (Table Lock)

개별 테이블 단위로 설정되는 잠금이며, 명시적·묵시적 두 가지 방식으로 획득할 수 있다.

**명시적 획득**

```sql
LOCK TABLES table_name [READ | WRITE];
```

**묵시적 획득**

MyISAM이나 MEMORY 테이블에 데이터를 변경하는 쿼리를 실행할 때 자동으로 설정된다. 단, InnoDB는 스토리지 엔진 차원에서 레코드 기반 잠금을 제공하므로, 단순 데이터 변경 쿼리로는 묵시적 테이블 락이 설정되지 않는다.

---

## 5.2.3 네임드 락 (Named Lock)

`GET_LOCK()` 함수를 이용해 임의의 문자열에 대해 잠금을 설정하는 방식이다. 테이블·레코드·`AUTO_INCREMENT` 같은 데이터베이스 객체가 아닌, **사용자가 지정한 문자열** 자체를 대상으로 잠금을 획득하고 해제한다.

```sql
SELECT GET_LOCK('lock_name', timeout);
SELECT RELEASE_LOCK('lock_name');
```

> 배치 프로그램처럼 한꺼번에 많은 레코드를 변경하는 쿼리는 데드락을 일으키기 쉽다. 이때 동일 데이터를 변경·참조하는 프로그램끼리 같은 네임드 락 문자열을 사용하도록 분류하면 간단하게 동시성 문제를 해결할 수 있다.

---

## 5.2.4 메타데이터 락 (Metadata Lock)

데이터베이스 객체(테이블, 뷰 등)의 이름이나 구조를 변경할 때 자동으로 획득되는 잠금이다. 명시적으로 획득하거나 해제하는 것이 아니며, 예를 들어 테이블 이름을 변경하면 MySQL이 내부적으로 메타데이터 락을 설정한다.

### 활용 패턴 — 무중단 스키마 변경

대용량 테이블의 스키마를 무중단으로 변경할 때는 아래 순서로 진행한다.

1. 신규 구조의 테이블을 생성하고 데이터를 복사한다.
2. 트랜잭션과 테이블 쓰기 락을 함께 사용해 복사 완료 시점의 데이터 정합성을 확보한다.
3. `RENAME TABLE`로 테이블 이름을 교체한다. — 이 단계에서 메타데이터 락이 짧게 획득·해제된다.

```sql
-- 예시
RENAME TABLE original_table TO backup_table,
             new_table TO original_table;
```

# 부록
## InnoDB 의도 잠금 (Intention Lock)

### 잠금의 종류

InnoDB는 **행(row) 수준 잠금**과 **테이블 수준 잠금**을 함께 사용하는데, 이 둘을 효율적으로 공존시키기 위해 의도 잠금이 도입됐다.

### 4가지 잠금 타입

|잠금|표기|레벨|설명|
|---|---|---|---|
|**읽기 잠금** (Shared Lock)|`S`|행(row)|해당 행을 읽는 동안 다른 트랜잭션의 **쓰기를 차단**. 읽기는 허용|
|**쓰기 잠금** (Exclusive Lock)|`X`|행(row)|해당 행을 변경하는 동안 다른 트랜잭션의 **읽기/쓰기 모두 차단**|
|**의도 읽기 잠금** (Intention Shared Lock)|`IS`|테이블|"이 테이블의 **일부 행에 S 잠금**을 걸겠다"는 의사 표시|
|**의도 쓰기 잠금** (Intention Exclusive Lock)|`IX`|테이블|"이 테이블의 **일부 행에 X 잠금**을 걸겠다"는 의사 표시|

### 왜 의도 잠금이 필요한가?

행 잠금 없이 테이블 전체 잠금(`LOCK TABLES`)을 걸 때 문제가 생긴다.

```
트랜잭션 A: 특정 행에 X 잠금 보유 중
트랜잭션 B: 테이블 전체에 S 잠금 시도
```

B가 테이블 잠금을 걸기 위해 **모든 행을 순회하며 잠금 여부를 확인**해야 한다면 매우 비효율적이다.

의도 잠금을 사용하면, 행에 X 잠금을 거는 순간 **테이블 레벨에 IX도 자동으로 설정**된다. 테이블 잠금을 시도하는 트랜잭션은 **테이블 레벨만 확인**하면 충돌 여부를 즉시 알 수 있다.

### 잠금 호환성 행렬

|        | IS  | IX  | S   | X   |
| ------ | --- | --- | --- | --- |
| **IS** | ✅   | ✅   | ✅   | ❌   |
| **IX** | ✅   | ✅   | ❌   | ❌   |
| **S**  | ✅   | ❌   | ✅   | ❌   |
| **X**  | ❌   | ❌   | ❌   | ❌   |

핵심 규칙:

- `IS ↔ IX` : 둘 다 **의사 표시**일 뿐이라 서로 호환 ✅
- `IX ↔ S` : 호환 안 됨 ❌ — "행을 바꾸겠다" vs "테이블 전체를 읽겠다" 충돌
- `X` : 무엇과도 호환 안 됨 ❌

### 실제 흐름 예시

```sql
-- 트랜잭션 A: 행 수준 X 잠금
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
-- → 테이블에 IX 자동 설정, id=1 행에 X 설정

-- 트랜잭션 B: 테이블 전체 S 잠금 시도
LOCK TABLES orders READ;
-- → 테이블의 IX와 충돌 → 대기 or 실패
```

```sql
-- 트랜잭션 A: id=1 행에 X 잠금 (테이블 IX 설정)
-- 트랜잭션 B: id=2 행에 X 잠금 시도 (테이블 IX 설정)
-- IS ↔ IX는 호환되므로 → 동시에 진행 가능 ✅
```

### 한 줄 요약

> 의도 잠금은 **"나 이 테이블의 어떤 행에 잠금 걸 거야"** 라고 테이블 레벨에 미리 선언하는 것. 덕분에 InnoDB는 행 잠금과 테이블 잠금의 충돌을 **전체 행 탐색 없이 O(1)로 감지**할 수 있다.
