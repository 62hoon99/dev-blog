
> MySQL 서버 레벨의 잠금과 별개로, **스토리지 엔진 내부에서 레코드 기반 잠금**을 관리한다. 잠금 정보가 작은 공간으로 관리되므로 **락 에스컬레이션(레코드 락 → 페이지 락 → 테이블 락)이 발생하지 않는다.**

---

## 5.3.1 잠금 종류

### 레코드 락 (Record Lock)

레코드 자체가 아닌 **인덱스의 레코드**를 잠근다.

> **💡 왜 인덱스를 기준으로 잠그는가?**
> 
> InnoDB는 클러스터링 인덱스 구조로, 실제 레코드 데이터가 인덱스 B-Tree 리프 노드에 저장된다. 즉, 인덱스 자체가 곧 레코드이므로 **인덱스 레코드를 잠그는 것 = 레코드를 잠그는 것**이다. 이 구조 덕분에 조건절의 인덱스 사용 여부에 따라 잠금 범위가 크게 달라진다.

---

### 갭 락 (Gap Lock)

레코드와 레코드 **사이의 간격(Gap)** 을 잠근다. 실제 존재하는 레코드가 아닌, 그 사이 공간에 새 레코드가 **INSERT되는 것을 방지**한다.

```sql
-- id = 3, 7이 존재할 때
-- 아래 쿼리는 (3, 7) 사이 갭에 갭 락을 건다
SELECT * FROM t WHERE id BETWEEN 3 AND 7 FOR UPDATE;

-- 다른 트랜잭션에서 id = 5 INSERT 시도 → 블로킹
INSERT INTO t (id) VALUES (5); -- 대기
```

---

### 넥스트 키 락 (Next-Key Lock)

**레코드 락 + 갭 락**의 조합. InnoDB의 기본 잠금 방식이다.

> **📌 주 목적**
> 
> 바이너리 로그 기반 복제(Replication) 환경에서 **소스 서버와 레플리카 서버의 결과 일관성 보장**. STATEMENT 포맷 바이너리 로그에서 팬텀 리드가 발생하면 복제 결과가 달라질 수 있기 때문이다.

**격리 수준과의 관계**

- `READ COMMITTED` → 갭 락, 넥스트 키 락 거의 미사용
- `REPEATABLE READ` (InnoDB 기본값) → 팬텀 리드 방지를 위해 넥스트 키 락 활성화

```sql
-- 테이블 t에 id = 50, 100, 150 레코드가 존재한다고 가정

-- [트랜잭션 A]
SELECT * FROM t WHERE id > 100 FOR UPDATE;
-- 잠금 범위:
--   레코드 락: id = 150 (실제 존재하는 레코드)
--   갭 락:    (100, 150) 사이 갭 + (150, +∞) 슈프리멈(supremum) 갭
-- → 즉, id > 100 범위의 레코드 + 그 사이/이후 모든 갭을 잠근다

-- [트랜잭션 B] — 아래 쿼리들은 모두 트랜잭션 A가 커밋/롤백될 때까지 대기
INSERT INTO t (id) VALUES (120); -- (100, 150) 갭 락에 의해 블로킹
INSERT INTO t (id) VALUES (200); -- (150, ∞) 갭 락에 의해 블로킹
UPDATE t SET val = 'x' WHERE id = 150; -- 레코드 락에 의해 블로킹
```

> **슈프리멈(Supremum)**
> 
> InnoDB는 테이블의 마지막 레코드 이후 가상의 경계값(supremum)을 두어, `id > 100` 같은 열린 범위 쿼리에서 아직 존재하지 않는 미래 레코드의 INSERT도 차단할 수 있다.

---

### AUTO_INCREMENT 락

`INSERT`, `REPLACE` 시에만 발생하는 **테이블 수준의 잠금**이다. `UPDATE`, `DELETE`에는 걸리지 않는다.

> **AUTO_INCREMENT 값이 롤백 후에도 줄어들지 않는 이유**
> 
> 락 점유 시간을 최소화하기 위해 채번 즉시 락을 해제한다. INSERT가 실패 또는 롤백되더라도 이미 해제된 락을 되돌리지 않으므로 값은 증가한 채로 유지된다.

|`innodb_autoinc_lock_mode`|설명|
|---|---|
|0|항상 테이블 락 사용 (레거시)|
|1|단순 INSERT는 경량 락, Bulk INSERT는 테이블 락 (MySQL 5.x 기본값)|
|2|항상 경량 락 (MySQL 8.0 기본값, 복제 시 STATEMENT 포맷 주의)|

## 5.3.2 인덱스와 잠금

InnoDB는 **인덱스를 기준으로 쓰기 락(X-Lock)** 을 건다. 따라서 조건절이 인덱스를 타지 못하면 불필요하게 많은 레코드에 락이 걸린다.

```sql
-- 상황: first_name 인덱스만 존재, last_name 인덱스 없음
-- first_name = 'Georgi' 해당 레코드 253건, 실제 변경 대상 1건

UPDATE employees SET hire_date = NOW()
WHERE first_name = 'Georgi' AND last_name = 'Klassen';

-- 실제 변경: 1건
-- 실제 잠금: first_name = 'Georgi' 조건을 만족하는 253건 전체
```

> **⚠️ 인덱스 설계가 곧 잠금 범위 설계**
> 
> 인덱스가 아예 없으면 **테이블 풀스캔 → 전체 레코드 잠금**으로 이어진다. InnoDB에서 인덱스 설계가 중요한 이유가 바로 이것이다. 잠금 범위가 성능과 동시성에 직결된다.

## 5.3.3 레코드 수준의 잠금 확인 및 해제

`performance_schema`를 통해 현재 잠금 상태를 조회할 수 있다.

### 1단계 — 잠금 대기 중인 트랜잭션 확인

```sql
SELECT
    r.trx_id              AS waiting_trx_id,
    r.trx_mysql_thread_id AS waiting_thread,
    r.trx_query           AS waiting_query,
    b.trx_id              AS blocking_trx_id,
    b.trx_mysql_thread_id AS blocking_thread,
    b.trx_query           AS blocking_query
FROM performance_schema.data_lock_waits w
JOIN information_schema.innodb_trx r
    ON r.trx_id = w.requesting_engine_transaction_id
JOIN information_schema.innodb_trx b
    ON b.trx_id = w.blocking_engine_transaction_id;
```

### 2단계 — 현재 보유 중인 잠금 목록 확인

```sql
SELECT
    engine_transaction_id,
    object_schema,
    object_name,
    lock_type,    -- TABLE / RECORD
    lock_mode,    -- X, S, GAP, NEXT-KEY 등
    lock_status,  -- GRANTED / WAITING
    lock_data
FROM performance_schema.data_locks;
```

### 3단계 — 블로킹 트랜잭션 스레드 강제 종료

```sql
-- 1단계에서 확인한 blocking_thread 값 사용
KILL {blocking_thread_id};
```

> **MySQL 8.0 이전 (5.7 이하)**
> 
> `performance_schema.data_locks` 대신 `information_schema.innodb_locks`, `innodb_lock_waits` 사용 (MySQL 8.0에서 deprecated)
