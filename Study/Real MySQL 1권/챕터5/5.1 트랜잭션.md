## 트랜잭션 (Transaction)

### 트랜잭션이란?

트랜잭션은 **작업의 완전성을 보장**하는 기능이다. 논리적인 작업 셋이 **전부 성공하거나, 전부 실패하거나** 둘 중 하나만 가능하도록 보장하며, 일부만 적용되는 부분 반영 현상(Partial Update)을 방지한다.

자주 혼동하는 개념인 **잠금(Lock)** 과의 차이는 다음과 같다.

|개념|목적|
|---|---|
|잠금 (Lock)|**동시성 제어** — 동일 자원에 대해 한 시점에 하나의 커넥션만 변경 가능하도록 순서 보장|
|트랜잭션 (Transaction)|**정합성 보장** — 작업 셋이 완전히 반영되거나 완전히 롤백되도록 보장|
|격리 수준 (Isolation Level)|**공유 범위 결정** — 트랜잭션 간 작업 내용을 어디까지 공유하고 차단할지 결정|

### 잠금 (Lock)
#### InnoDB 락 메커니즘

##### 락의 종류

|락|획득 조건|충돌 대상|
|---|---|---|
|**S-Lock** (공유락)|`SELECT ... FOR SHARE`|X-Lock|
|**X-Lock** (배타락)|`UPDATE`, `DELETE`, `SELECT ... FOR UPDATE`|S-Lock, X-Lock|

> 일반 `SELECT`는 기본적으로 락을 걸지 않는다. (MVCC로 처리)

---

##### 락의 범위

|락|범위|설명|
|---|---|---|
|**Record Lock**|단일 row|인덱스 레코드 자체에 걸리는 락|
|**Gap Lock**|레코드 사이 구간|구간에 새로운 row가 삽입되는 것을 방지|
|**Next-Key Lock**|Record + Gap|Record Lock + Gap Lock의 조합. InnoDB의 기본 락 단위|

> InnoDB의 락은 **테이블이 아닌 인덱스**에 걸린다. 인덱스가 없으면 풀 스캔 → 테이블 전체에 락이 걸릴 수 있다.

---

##### 락 생명주기

```
쿼리 실행 (UPDATE/DELETE 등)
    → X-Lock 획득
    → 언두 로그 백업 + 버퍼 풀 수정
    → COMMIT or ROLLBACK
    → 락 해제
```

- 락은 **쿼리 단위가 아니라 트랜잭션 단위**로 유지된다.
- 트랜잭션이 끝나기 전까지 다른 트랜잭션은 해당 row에 X-Lock을 걸 수 없다.

---

##### 락 대기와 데드락

```
트랜잭션 A: row 1 X-Lock 보유 → row 2 X-Lock 대기
트랜잭션 B: row 2 X-Lock 보유 → row 1 X-Lock 대기
                    ↓
               Deadlock 감지 → 한 쪽 트랜잭션 강제 롤백
```

- InnoDB는 **데드락을 자동 감지**하고 비용이 적은 트랜잭션을 롤백시킨다.
- `innodb_lock_wait_timeout` (기본 50초) 초과 시 Lock Wait Timeout 에러 발생.

---

### 5.1.1 MySQL에서의 트랜잭션

MyISAM이나 MEMORY 엔진이 InnoDB보다 빠를 것 같지만, **실제로는 그렇지 않다.** 트랜잭션을 지원하지 않는 엔진은 성능상 이점도 없으면서 정합성 문제라는 짐을 개발자에게 떠넘긴다.

**트랜잭션은 단일 쿼리에도 의미가 있다.** 여러 쿼리가 묶인 경우에만 필요한 개념이 아니라, 쿼리가 하나든 여러 개든 논리적 작업 셋 전체가 100% 적용되거나 아무것도 적용되지 않아야 함을 보장한다.

**예시 — 중복 데이터 INSERT 시 동작 차이**

```sql
INSERT INTO users (id, name) VALUES (1, 'A'), (2, 'B'), (2, 'C'); -- id=2 중복
```

|엔진|결과|
|---|---|
|MyISAM|`(1, 'A')`, `(2, 'B')` 부분 삽입 후 에러 → **데이터 불일치 상태**|
|InnoDB|전체 롤백 → **아무것도 삽입되지 않은 상태 유지**|

> InnoDB는 `AUTO_COMMIT` 모드에서도 단일 쿼리를 내부적으로 트랜잭션으로 감싸서 처리한다. 즉, 쿼리 실행 전 트랜잭션을 시작하고 완료 후 자동으로 커밋(또는 롤백)한다.

MyISAM은 트랜잭션이 없으므로, 정합성이 중요한 로직을 애플리케이션 코드에서 `if/else`와 데이터 클렌징 로직으로 직접 처리해야 한다. 이는 코드 복잡도를 높이고, 실수 여지도 늘린다.

---

### 5.1.2 주의사항 — 트랜잭션 범위를 최소화하라

트랜잭션이 열려 있는 동안 **DB 커넥션은 계속 점유**된다. 트랜잭션 내부에서 외부 I/O(API 호출, 파일 읽기 등)가 발생하면 그 시간만큼 커넥션이 낭비되어 커넥션 풀이 고갈될 위험이 있다.

**나쁜 예시 (I/O가 트랜잭션 안에 있음)**

```java
transaction.begin();
   db.insert(order);
   externalApi.sendEmail();   // 외부 I/O — 커넥션 낭비
   db.insert(payment);
transaction.commit();
```

**좋은 예시 (I/O를 트랜잭션 밖으로 분리)**

```java
externalApi.sendEmail();     // 트랜잭션 밖에서 처리

transaction.begin();
   db.insert(order);
   db.insert(payment);
transaction.commit();
```

**트랜잭션 설계 원칙:** 트랜잭션은 DB 작업만 포함하고, 외부 I/O·네트워크 호출·무거운 연산은 트랜잭션 바깥으로 꺼내는 것이 기본이다.

# 5.2 MySQL 엔진의 잠금

MySQL 엔진은 스토리지 엔진을 제외한 나머지 부분을 가리킨다. MySQL 엔진 레벨의 잠금은 모든 스토리지 엔진에 영향을 미치지만, 스토리지 엔진 레벨의 잠금은 엔진 간 상호 영향을 미치지 않는다.

---

## 5.2.1 글로벌 락 (Global Lock)

MySQL이 제공하는 잠금 중 범위가 가장 크다. 한 세션에서 글로벌 락을 획득하면, 다른 세션의 `SELECT`를 제외한 대부분의 DDL·DML 문장은 잠금이 해제될 때까지 대기 상태가 된다. 작업 대상 테이블이나 데이터베이스가 달라도 MySQL 서버 전체에 동일하게 영향을 미친다.

InnoDB는 트랜잭션을 지원하기 때문에, MyISAM과 달리 데이터 일관성을 위해 모든 변경 작업을 멈출 필요가 없다. InnoDB가 대중화되면서 MySQL 8.0부터는 백업 툴의 안정적인 실행을 위해 **백업 락**이 도입됐다.

### 백업 락

- 일반적인 테이블 데이터 변경은 **허용**한다.
- 백업 중 DDL 명령이 실행되면 백업을 **중단**한다.
- 복제는 정상적으로 계속 실행되지만, 백업 실패를 방지하기 위해 DDL 명령이 들어오면 복제를 **일시 중지**시킨다.

---

## 5.2.2 테이블 락 (Table Lock)

개별 테이블 단위로 설정되는 잠금이며, 명시적·묵시적 두 가지 방식으로 획득할 수 있다.

**명시적 획득**

```sql
LOCK TABLES table_name [READ | WRITE];
```

**묵시적 획득**

MyISAM이나 MEMORY 테이블에 데이터를 변경하는 쿼리를 실행할 때 자동으로 설정된다. 단, InnoDB는 스토리지 엔진 차원에서 레코드 기반 잠금을 제공하므로, 단순 데이터 변경 쿼리로는 묵시적 테이블 락이 설정되지 않는다.

---

## 5.2.3 네임드 락 (Named Lock)

`GET_LOCK()` 함수를 이용해 임의의 문자열에 대해 잠금을 설정하는 방식이다. 테이블·레코드·`AUTO_INCREMENT` 같은 데이터베이스 객체가 아닌, **사용자가 지정한 문자열** 자체를 대상으로 잠금을 획득하고 해제한다.

```sql
SELECT GET_LOCK('lock_name', timeout);
SELECT RELEASE_LOCK('lock_name');
```

> 배치 프로그램처럼 한꺼번에 많은 레코드를 변경하는 쿼리는 데드락을 일으키기 쉽다. 이때 동일 데이터를 변경·참조하는 프로그램끼리 같은 네임드 락 문자열을 사용하도록 분류하면 간단하게 동시성 문제를 해결할 수 있다.

---

## 5.2.4 메타데이터 락 (Metadata Lock)

데이터베이스 객체(테이블, 뷰 등)의 이름이나 구조를 변경할 때 자동으로 획득되는 잠금이다. 명시적으로 획득하거나 해제하는 것이 아니며, 예를 들어 테이블 이름을 변경하면 MySQL이 내부적으로 메타데이터 락을 설정한다.

### 활용 패턴 — 무중단 스키마 변경

대용량 테이블의 스키마를 무중단으로 변경할 때는 아래 순서로 진행한다.

1. 신규 구조의 테이블을 생성하고 데이터를 복사한다.
2. 트랜잭션과 테이블 쓰기 락을 함께 사용해 복사 완료 시점의 데이터 정합성을 확보한다.
3. `RENAME TABLE`로 테이블 이름을 교체한다. — 이 단계에서 메타데이터 락이 짧게 획득·해제된다.

```sql
-- 예시
RENAME TABLE original_table TO backup_table,
             new_table TO original_table;
```
