## 격리 수준별 문제 발생 여부

|격리 수준|DIRTY READ|NON-REPEATABLE READ|PHANTOM READ|
|---|---|---|---|
|READ UNCOMMITTED|✅ 발생|✅ 발생|✅ 발생|
|READ COMMITTED|❌ 없음|✅ 발생|✅ 발생|
|REPEATABLE READ|❌ 없음|❌ 없음|✅ 발생 (InnoDB는 대부분 없음¹)|
|SERIALIZABLE|❌ 없음|❌ 없음|❌ 없음|

> [!note] ¹ InnoDB REPEATABLE READ의 팬텀 리드
> 
> - 일반 `SELECT` → **MVCC 스냅샷**으로 팬텀 리드 차단
> - `SELECT ... FOR UPDATE` → **갭 락/넥스트 키 락**으로 팬텀 리드 차단
> - 단, **일반 SELECT 후 FOR UPDATE 혼용** 시에는 팬텀 리드가 발생할 수 있다. → [[#REPEATABLE READ에서의 팬텀 리드]] 참고

## 5.4.1 READ UNCOMMITTED

다른 트랜잭션이 **커밋하지 않은 변경사항도 읽을 수 있는** 격리 수준.

### DIRTY READ

```
트랜잭션 A: UPDATE users SET name = '김철수' WHERE id = 1; -- 아직 커밋 안 함
트랜잭션 B: SELECT name FROM users WHERE id = 1;
            → '김철수' 읽힘 (커밋되지 않은 데이터)
트랜잭션 A: ROLLBACK;
            → B가 읽은 '김철수'는 실제로 존재한 적 없는 데이터
```

> [!warning] 정합성 문제가 심각하여 RDBMS에서 거의 사용하지 않는다.

---

## 5.4.2 READ COMMITTED

다른 트랜잭션이 **커밋한 데이터만** 읽을 수 있는 격리 수준. Oracle의 기본 격리 수준이며, 온라인 서비스에서 많이 사용한다.

### MVCC로 DIRTY READ 해결

커밋되지 않은 데이터는 undo log에만 존재하고, READ COMMITTED는 **항상 가장 최근에 커밋된 버전**을 읽는다.

```
트랜잭션 A (trx_id=200): UPDATE users SET name = '김철수' WHERE id = 1; -- 미커밋
트랜잭션 B: SELECT name FROM users WHERE id = 1;
            → undo log에서 커밋된 버전인 '홍길동' 읽힘 ✅
트랜잭션 A: COMMIT;
트랜잭션 B: SELECT name FROM users WHERE id = 1;
            → 이번엔 '김철수' 읽힘
```

### NON-REPEATABLE READ (반복 불가 읽기)

같은 트랜잭션 내에서 같은 레코드를 두 번 읽었을 때 **결과가 달라지는** 문제. READ COMMITTED는 매 SELECT마다 그 시점의 최신 커밋 버전을 읽기 때문에 발생한다.

```
트랜잭션 B: SELECT name FROM users WHERE id = 1; → '홍길동'

  트랜잭션 A: UPDATE users SET name = '김철수' WHERE id = 1;
  트랜잭션 A: COMMIT;

트랜잭션 B: SELECT name FROM users WHERE id = 1; → '김철수' (달라짐 ❌)
```

## 5.4.3 REPEATABLE READ

**InnoDB의 기본 격리 수준.** 트랜잭션이 시작된 시점의 스냅샷을 기준으로 데이터를 읽는다.

### MVCC와 스냅샷 읽기

트랜잭션이 시작될 때 **자신의 trx_id를 기록**하고, 이후 SELECT는 항상 그 시점 이전에 커밋된 버전만 읽는다. 자신의 trx_id보다 이후에 커밋된 변경은 undo log 체인을 역추적하여 무시한다.

```
트랜잭션 A 시작 (trx_id=100)

이후 트랜잭션 B (trx_id=200), C (trx_id=300)가 같은 레코드 수정 후 커밋

A가 해당 레코드 SELECT 시:

현재 레코드 (trx_id=300) → 300 > 100, 무시
        ↓ undo log 체인 역추적
undo log (trx_id=200)    → 200 > 100, 무시
        ↓
undo log (trx_id=100 이전) → ✅ 이 버전 반환
```

> [!note] undo log가 유지되는 이유 trx_id=100 트랜잭션이 살아있는 동안, B와 C가 만든 undo log는 Purge 스레드가 삭제하지 못한다. A가 이전 버전을 읽으려면 해당 체인이 남아있어야 하기 때문이다. → **읽기 전용 트랜잭션이라도 오래 열어두면 undo log가 누적**되는 이유

### NON-REPEATABLE READ 해결

같은 트랜잭션 내에서는 항상 동일한 스냅샷을 읽으므로, 다른 트랜잭션이 커밋해도 결과가 변하지 않는다.

```
트랜잭션 A 시작 (trx_id=100)
트랜잭션 A: SELECT name FROM users WHERE id = 1; → '홍길동'

  트랜잭션 B (trx_id=200): UPDATE ... SET name = '김철수'; COMMIT;

트랜잭션 A: SELECT name FROM users WHERE id = 1; → '홍길동' (동일 ✅)
            -- trx_id=200의 변경은 스냅샷 기준으로 무시됨
```

### REPEATABLE READ에서의 팬텀 리드

#### 일반 SELECT — MVCC 스냅샷으로 차단

MVCC 스냅샷을 기반으로 읽으므로, 다른 트랜잭션이 INSERT를 커밋해도 보이지 않는다.

```
트랜잭션 A 시작 (trx_id=100)
트랜잭션 A: SELECT COUNT(*) FROM users WHERE age > 20; → 5건

  트랜잭션 B: INSERT INTO users (age) VALUES (25); COMMIT;

트랜잭션 A: SELECT COUNT(*) FROM users WHERE age > 20; → 5건 (동일 ✅)
            -- MVCC 스냅샷이 trx_id=100 이후 변경을 차단
```

#### SELECT ... FOR UPDATE — 갭 락/넥스트 키 락으로 차단

잠금 읽기는 최신 데이터를 읽지만, 조회 범위에 **넥스트 키 락**을 걸어 다른 트랜잭션의 INSERT 자체를 차단한다.

```
트랜잭션 A 시작 (trx_id=100)
트랜잭션 A: SELECT * FROM users WHERE age > 20 FOR UPDATE; → 5건
            -- age > 20 범위 전체에 넥스트 키 락이 걸림

  트랜잭션 B: INSERT INTO users (age) VALUES (25);
              -- 넥스트 키 락 범위에 걸려 블로킹 ✅

트랜잭션 A: SELECT * FROM users WHERE age > 20 FOR UPDATE; → 5건 (동일 ✅)
```

#### 팬텀 리드가 발생하는 예외 — 일반 SELECT와 FOR UPDATE 혼용

같은 트랜잭션 내에서 **일반 SELECT(락 없음)로 먼저 읽고, 이후 FOR UPDATE로 읽을 때** 팬텀 리드가 발생할 수 있다. 첫 번째 일반 SELECT 시점에는 락이 없어서 다른 트랜잭션의 INSERT를 막지 못하고, 두 번째 FOR UPDATE는 최신 데이터를 읽으므로 그 사이에 INSERT된 레코드가 보인다.

```
트랜잭션 A: SELECT * FROM users WHERE age > 20;
            -- 일반 SELECT → MVCC 스냅샷, 락 없음, 5건 조회

  트랜잭션 B: INSERT INTO users (age) VALUES (25); COMMIT;
              -- 락이 없으므로 INSERT 성공

트랜잭션 A: SELECT * FROM users WHERE age > 20 FOR UPDATE;
            -- 잠금 읽기 → 최신 데이터 읽음 → 6건 조회 (팬텀 리드 ✅)
```

## 5.4.4 SERIALIZABLE

모든 `SELECT`를 **`SELECT ... FOR SHARE`(공유 락)** 로 자동 변환하여 처리하는 격리 수준. 읽기조차 잠금을 걸기 때문에 팬텀 리드를 포함한 모든 정합성 문제가 해결된다.

> [!warning] 동시성 저하 읽기/쓰기 모두 락 경합이 발생하므로 동시성이 크게 떨어진다. InnoDB는 REPEATABLE READ에서도 MVCC로 대부분의 문제를 해결하므로, 일반적인 웹 서비스에서는 SERIALIZABLE을 사용할 필요가 없다.
