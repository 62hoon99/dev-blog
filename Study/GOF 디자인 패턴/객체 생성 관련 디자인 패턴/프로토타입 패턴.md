# Java의 clone() 메서드
- Java에서는 clone() 메서드를 사용하여 프로토타입 패턴을 구현할 수 있다.
- clone 하려는 클래스가 Cloneable interfece를 구현하도록 하고, clone을 override 한다.
	- Cloneable 을 구현해야 하는 이유는 객체 복제를 함부로 할 수 없도록 막기 위해 Cloneable interface를 구현한 클래스만 clone() 메서드 사용이 가능하도록 의도적으로 설계되었다.

**예시 코드**
``` Java
public class Basket implements Cloneable {  
      
    private List<Fruit> fruits;  
    private List<Bread> breads;  
  
    public Basket(List<Fruit> fruits, List<Bread> breads) {  
        this.fruits = fruits;  
        this.breads = breads;  
    }  
  
    @Override  
    public Basket clone() {  
        try {  
            return (Basket) super.clone();  
        } catch (CloneNotSupportedException e) {  
            throw new AssertionError();  
        }  
    }  
}
```

> 주의할 점: clone()은 얕은 복사다. 예를 들어 Basket을 clone 했을 때 복제된 인스턴스의 fruits와 원본 인스턴스의 fruits 는 같은 레퍼런스 참조이다. 즉, 복제된 인스턴스의 fruits에 element를 추가하면 원본 인스턴스의 fruits도 element가 추가된다.

## clone 메서드의 주요 문제점

1. 생성자 우회로 인한 설계 혼란
	- clone()은 생성자를 호출하지 않으며, 생성자로 구현해도 규약 위반은 아니다.
    - 하지만 생성자로 구현하면 상속 구조에서 super.clone() 호출 시 의도와 다른 타입의 인스턴스가 반환될 수 있다.
    - 결국 생성자를 쓸 거라면 clone()을 사용할 의미가 없다.
    
2. 얕은 복사로 인한 불변식 파괴
    - 기본 clone()은 얕은 복사만 수행한다.
    - 가변 객체(배열, 컬렉션 등)를 참조하면 원본과 복제본이 내부 상태를 공유하게 되어 불변식이 깨질 수 있다.
    - clone()은 생성자와 동일하게 **복제 객체의 불변식을 보장해야 한다**.
        
3. 불변 클래스 설계와의 충돌
    - 깊은 복사를 위해 final 필드를 제거하면 **불변 클래스를 가변 클래스로 바꾸는 결과**가 된다.
    - 이는 “가변 객체를 참조하는 필드는 final로 선언하라”는 일반 원칙과 충돌한다.
    
4. 복잡한 내부 구조에서의 deep copy 문제
    - 연결 리스트 등 내부에 복잡한 자료구조가 있으면 반드시 깊은 복사가 필요하다.
    - 재귀적 deep copy는 **스택 오버플로 위험**이 있으며, 반복자 기반 구현이 필요하다.
    - 구현 난이도와 오류 가능성이 매우 높다.
    
5. 스레드 안전성 문제
    - Cloneable을 구현한 스레드 안전 클래스는 clone()도 **동기화 처리**가 필요하다.
    - 그렇지 않으면 복제 과정에서 일관성이 깨질 수 있다.
