# MSA 구조에서의 분산 트랜잭션
MSA 환경에서는 각 서비스가 독립적인 데이터베이스를 가지므로, 서비스 간 데이터 정합성을 보장하기가 어렵다.

예를 들어 ‘결제’ 기능에서 상품 재고 감소, 포인트 적립, 쿠폰 차감이 각각 다른 서비스에서 처리될 때 일부만 성공하고 나머지가 실패하면 데이터 불일치가 발생한다.

이러한 문제를 해결하기 위해 **분산 트랜잭션 전략**이 필요하다.

---

# 2PC (Two-Phase Commit)
2PC는 분산 시스템에서 **트랜잭션의 원자성(Atomicity)을 보장하기 위한 프로토콜**이다.
트랜잭션을 두 단계로 나누어 처리한다.

- **Prepare 단계**: 모든 참여자에게 커밋 가능 여부를 확인    
- **Commit 단계**: 모든 참여자가 준비 완료(YES)일 경우 최종 커밋 수행

대표적인 구현 방식으로 **XA 트랜잭션**이 있다.

## 2PC 동작 과정

### 1단계: Prepare Phase (투표 단계)
Coordinator가 모든 Participant에게 커밋 준비 여부를 요청한다.

각 Participant는:
- 트랜잭션 실행
- 변경 내용 로그 기록 (디스크 flush)
- 필요한 락 유지
- 실제 commit은 수행하지 않음
- YES / NO 응답

YES 응답은 **“나는 언제든 commit 가능 상태”임을 의미**한다.

### 2단계: Commit Phase (결정 단계)
- **모두 YES인 경우** → Coordinator가 COMMIT 요청 전송    
- **하나라도 NO인 경우** → Coordinator가 ROLLBACK 요청 전송

이를 통해 모든 참여자의 원자성이 보장된다.

## XA 프로토콜
XA는 X/Open Distributed Transaction Processing 모델에서 정의한 **분산 트랜잭션 표준 인터페이스**이다.

DB, 메시지 큐, WAS 등 다양한 리소스가 동일한 규격으로 트랜잭션에 참여할 수 있도록 한다.

## Prepare 와 Commit 을 분리하는 이유
Prepare 단계는 각 참여자가 **커밋 가능한 상태로 동결(freeze)** 되었는지를 확인하는 과정이다.

모든 참여자로부터 YES를 받으면, 전체 시스템이 커밋 가능한 상태임이 보장되고 이후 최종 커밋을 수행한다.
이를 통해 일부만 커밋되는 상황을 방지한다.

## 실무에서 2PC가 잘 사용되지 않는 이유

MSA 환경에서는 다음과 같은 한계가 있다:

- Prepare 이후 락이 유지되어 **Blocking 문제 발생**
- 네트워크 왕복으로 인한 **성능 저하**
- Coordinator 장애 시 **전체 시스템 대기 상태 발생**    
- 장애 전파 범위가 큼

따라서 현대 MSA 환경에서는 2PC 대신 **Saga 패턴과 같은 보상 기반 트랜잭션 방식**을 주로 사용한다.
