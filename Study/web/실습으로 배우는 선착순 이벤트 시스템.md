# 강의 목표
- 선착순 100명에게 쿠폰을 발급하는 시스템을 만들며 동시성 제어와 부하 분산을 학습한다.
- 순간적으로 몰리는 트래픽을 견딜 수 있는 구조를 설계하는 것을 목표로 한다.


# **1. 동시성 문제**

- 쿠폰 발급 API에서 정확히 선착순 100명에게만 발급되었는지 판단하는 것은 단순 if 문으로 해결할 수 없다.
    
- 여러 요청이 동시에 같은 자원에 접근하면서 race condition 이 발생하고, 이로 인해 발급 수가 정확하지 않게 된다.
    
- 애플리케이션 단에서 lock을 걸 수도 있지만, 서버가 여러 대로 분산된 환경에서는 여전히 race condition 이 발생한다.
    
- 이를 해결하기 위해 Redis를 사용한다. Redis의 원자적 연산인 INCR 명령을 이용해 발급 수를 안전하게 카운팅할 수 있다.
    
- Redis는 싱글 스레드 기반이기 때문에 여러 애플리케이션에서 동시에 요청해도 race condition 없이 안정적으로 처리된다.
    
- 이렇게 동시성 문제는 해결할 수 있지만, 여전히 트래픽이 몰릴 때마다 매번 DB에 결과를 저장하면 DB에 큰 부하가 발생한다. 이 문제를 Kafka 같은 메시지 브로커로 완화할 수 있다.
    

  

# **2. 부하 분산**

- 메시지 브로커(이하 Kafka)를 사용하면 DB 부하를 크게 줄일 수 있다.
    
- 예를 들어 선착순 1만 명에게 쿠폰을 발급한다고 가정하자.
    
    만약 API 서버에서 직접 DB에 저장한다면, 하나의 DB로 1만 개의 insert 요청이 동시에 몰리게 된다.
    
- 하지만 Kafka를 사용하면 우선 Kafka에 1만 개의 메시지가 쌓이고, Consumer가 이를 순차적으로 읽어 DB에 저장한다.
    
- 결과적으로 대량의 동시 insert 요청이 **순차적 처리로 변경**되며, DB 부하를 효과적으로 분산할 수 있다.

# 2. 부하 분산
- 메시지 브로커(이하: Kafka)를 사용하면 DB 부하를 줄일 수 있다.
- 1만개의 쿠폰을 선착순 발급한다고 가정해보자. API 서버가 분산되어 있는 환경에서 하나의 DB를 사용한다고 하면 DB에 1만개의 insert 요청이 동시다발적으로 발생할 것이다. 그런데 Kafka를 사용하면 Kafka에 메시지만 1만개가 쌓이고, Consumer 프로세스가 순차적으로 메시지를 받아서 처리하기 때문에 1만개의 insert 요청이 순차적으로 이뤄진다. 그렇기 때문에 Kafka를 사용하면 DB 부하를 줄일 수 있다.
